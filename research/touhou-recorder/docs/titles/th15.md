# 東方紺珠伝 (th15)

## 基本情報

- 画面解像度: 1280x960相当 (4:3)
- 描画API: Direct3D9
- 推奨クラウドアスペクト: **GPUインスタンス (`g6f`系、wined3d+OpenGL経由) 推奨**、または低速録画 (`FPS_LIMIT_TARGET_HZ=30`)

## 固有仕様・運用ルール

- **エンジン・設定配置**: 内部描画解像度は960p相当。設定ファイルおよびリプレイは `%APPDATA%/ShanghaiAlice/th15/` 配下に配置されます。
- **入力ポーリング方式**: DirectInput の `GetDeviceState` を使用します（`PressKey` によるDIKコード送信）。Win32 の `GetKeyboardState` ではありません。
- **処理落ちとGPU運用方針**:
  - Extraステージ等の激しいエフェクト区間では、CPUコア数を増やしても（c7i.4xlarge等でも）fpsが15〜18前後まで低下し平均43〜44fps程度と処理落ちが発生します。
  - GPUインスタンス（`g6f`系、wined3d+OpenGL経由）を使用することで全地点60.0fps前後を維持でき、理論尺超過も+0.9%に改善します。
  - GPU利用が難しい場合は、低速録画（`FPS_LIMIT_TARGET_HZ=30`）をフォールバックとして使用します。
- **低速録画時の重複フレーム率閾値**: 30fps録画時は正常時でも重複フレーム率が約50%となるため、`--max-duplicate-rate` の既定値は `MENU_TIME_SCALE` に応じて動的にスケールされます（`recorder/timing.py` の `default_max_duplicate_rate()`）（30fps時は既定65%）。
- **ウィンドウ再配置対策**: GPU描画面（Xorg+nvidia）では録画開始直前に原点座標の再確認・再移動処理が行われます。

- **倍速録画(検証中)**: `SPEED_HACK_MULTIPLIER`(`mods/common/speed_hack_hook.h`、QueryPerformanceCounter偽装)と`FPS_LIMIT_TARGET_HZ`(倍率相当)を併用することで、ゲーム進行を2〜4倍速化できることを確認済み(reports/85)。th15はQPCのビジーポーリングでフレームレートを制御しており、Present間引き方式の`fps_limiter_hook`単体では倍速化できない。**g6f.2xlarge(8vCPU)なら2倍速は重複フレーム率2.0%で実用的**。g6f.xlarge(4vCPU)はCPU競合(libx264エンコードスレッド)により2倍速でも処理落ちする。3倍速以上はキャプチャ自体のCPU負荷増加で品質が不安定になり始める(詳細・既知の落とし穴はreports/85参照)。
- **倍速録画の倍率別比較(reports/87)**: フェーズ85・86の改善をすべて適用した g6f.2xlarge + NVENC で、**2倍速はExtra・Hard全6面とも実用品質**(試行1回目成功・スコア完全一致・復元後の落ちフレーム0.0〜0.1%・音声帯域は等倍と0.5dB以内・録画時間は等倍の約52%)。1.5倍速は周期的なカクつきと0.0756%の音声ドリフトで非推奨、3・4倍速はゲーム本体の単一スレッド律速で処理落ち(復元後14〜20%のフレーム停止)。倍速録画の音声が等倍録画より遅れる問題は同期マーカー方式で解決した(reports/88、2倍速Extraで等倍比+0.45秒→+0.06〜0.08秒)。

- **CPU低速録画(reports/91)**: GPUを確保できないときのフォールバック。通常ステージは`c7i.4xlarge`の1/2倍速(`FPS_LIMIT_TARGET_HZ=30`、`--cpu-display`)で配信版の落ち0.5%・理論尺比-0.10%・実時間は尺の2.03倍。Extraは1/2倍速でも最低19.8Hzまで落ちてBGMが先行するため(落ち1.3%)、1/3倍速(20Hz、落ち0.5%・3.09倍)を推奨。20Hzは重複フレーム率の既定閾値で誤って破棄される。CPU等倍は`c7i.4xlarge`でも落ち3.4〜6.8%で実用にならない。画面上のfps表示は`fps_display_hook`で等倍換算される(reports/93)。

- **CPU描画の律速(reports/99)**: llvmpipeの塗りつぶし(アルファブレンド・フィルタ付きのスプライト、加算エフェクト)そのもので、CPU量にほぼ比例する。特定の遅い形式・描画は無い(A4R4G4B4の格上げ、深度テストの間引き、等倍コピーのStretchRect化、DXVKは効果なし)。**画面サイズはth15.cfgのオフセット0x1F**(3=640x480、4=960x720、5=1280x960)。960x720にすると4コア8スレッドで1280x960の8コア16スレッドと同等(Extra 平均88.8Hz・下位5% 50.1)になり、`c7i.2xlarge`の1/2倍速で足りる見込みだが、画質が下がるため未採用(視聴とクラウド実測が条件)。

- **文字のジャギー対策は対象外(reports/102)**: 内部解像度 1280x960 では文字列を 1024x40 のまま等倍で転送する(`D3DX_FILTER_NONE`)ため、`D3DX_AREA_FILTER=1` は効かない(有効にしても画面は同じ)。

- **フレーム同期キャプチャ (`--frame-sync`、reports/109)**: CPU 描画 (`--cpu-display`) でも `c7i.4xlarge` で **Extra 1.20倍速・Hard 1.48倍速**（従来の CPU 低速録画比でコスト・課金時間を Extra 62.5%・Hard 52.7% 削減し、1/3倍速の120分実時間上限も解消）、`c7i.2xlarge` で **0.67倍速 (Extra) / 0.80倍速 (Hard)**（46〜58%削減）、`m7i.xlarge` で **0.35倍速 (Extra)**、GPU 4 vCPU の `g6f.xlarge`（NVENC）で **1.00倍速** を達成。ローカル並列/16w 100%負荷(`0.11x`)や `c7i.2xlarge` 8w負荷(`0.30x`)を含め、全本で試行1回目成功・スコア一致・ドリフト`[0,0,0]`・`A/V差=0.0ms`・プレイ区間落ち`0.0% (実効 60.00fps)`を確認済み。ただし `m7i.xlarge` は変換比が大きく総コスト高（`ratio=1.2711`, 尺1時間`$0.167`）のため、CPU は `c7i.4xlarge`（または `c7i.2xlarge`）を推奨。
