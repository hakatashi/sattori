# フェーズ51: 自宅ワーカーの深刻な処理落ち(sattori-dev#162)の原因調査 → CPU冷却系のハードウェア障害を特定

日付: 2026-08-24

前提: `sattori-dev`リポジトリのissue #162で、自宅ワーカー(本マシン、`HakataMatrix`)でth11リプレイ(`<JOB_ID>.rpy`, Lunatic ReimuA)の録画が約6割速度まで処理落ちし、リプレイが終端に到達しなかった事象が報告されていた。issue内では以下を否定済みとされていた: サーマルスロットリング(`thermald`の状態変化なし、cgroupの`throttled`は0)、CPU周波数低下(-7.7%のみ)、`--cpus`制限、他コンテナ競合、GPU状態変化、タイトル/リプレイ固有の問題。

**結論: 原因はCPU冷却系のハードウェア障害によるサーマルスロットリングであり、ソフトウェア・環境設定の問題ではない。issueで「サーマルスロットリングを否定した」根拠(`thermald`の状態・cgroup `throttled`カウンタ)は、いずれもハードウェアレベル(SMU/PROCHOT)のスロットリングを検知できない指標だったため、誤って否定されていた。**

## 再現実験

同じリプレイ(`games/th11/replay/<JOB_ID>.rpy`)を`scripts/25_record_replay_e2e_multigame.py --game th11 --replay <JOB_ID>.rpy --record-seconds 1500 --no-audio`で本マシン上で再現録画した(`runs/162_stutter_investigation/`)。

まず健全性確認として`th11_03.rpy`(過去に正常録画実績あり)を90秒だけ録画したところ、重複フレーム率0.5%・FpsMonitor 60.1Hzと完全に正常だった。**つまり本マシンは軽い/短時間の負荷では全く異常を示さない**。

続けて問題のリプレイを25分間(1500秒)録画したところ、`mods/common/fps_monitor.cpp`が5秒おきに出力する`GetDeviceState`呼び出し頻度(=ゲーム内部の実効ポーリングレート、ほぼ実効fpsに比例)が以下のように推移した(`instances/th11-multigame-recording-test/th11_autoplay.log`より抜粋):

| 経過時間(録画開始基準) | Hz |
| --- | --- |
| 0:00 〜 12:35 | 安定して59〜60Hz |
| 12:35 (08:53:21) | 崩れ始め、47〜59Hzへ変動 |
| 15:15 (08:56:01) | 32Hz まで低下する瞬間が出現 |
| 20:40 (09:01:00)以降 | 恒常的に40〜46Hz |
| 25:00 (09:05:47) | 23〜28Hz まで悪化 |

録画全体(15〜1507秒)の重複フレーム率は**11.8%**で、issueの閾値(30%)は超えなかったが、明確な進行性の劣化が確認できた。**issueの記載(58.7fps→36.6fpsへの低下)と整合する再現に成功した。**

## 温度データによる原因特定(netdataの実績値)

上記再現実験と同じ時間帯のCPU温度(`k10temp` Tctl、AMD Ryzen 7 5700X)をnetdataから取得したところ、劣化開始のタイミングと明確に一致した:

| 時刻 | Tctl | 備考 |
| --- | ---: | --- |
| 08:40 (録画開始直後) | 84.6°C |  |
| 08:48〜08:53 | 96.4〜96.6°C(ピーク) | **この直後(08:53:21)からHzが崩れ始める** |
| 08:53〜09:07 | 95.2〜95.9°C(高止まり) | Hzは40Hz台まで悪化したまま |
| 09:09(録画終了の数分後、負荷ゼロ) | 92.6°C | **無負荷でも高温が全く下がらない** |

**さらに重要なのは、issue本文が報告した実際の障害発生時刻(2026-08-24 03:23〜04:23)の温度も同時に確認できたこと**:

| 時刻 | Tctl | CPU負荷(system.cpu) |
| --- | ---: | --- |
| 01:47〜02:58(再起動直後、home-workerはジョブ未受注でほぼアイドル) | 82〜88°C、緩やかに上昇 | 6〜7%(ほぼアイドル) |
| 03:35〜05:13(録画ジョブ実行中を含む) | **95°C前後で高止まり** | (issue記載: python3プロセス844%) |

**つまり、当該ジョブが始まる前、CPUがほぼアイドル状態(負荷6〜7%)の時点で、すでにTctlが82℃→88℃へじわじわ上昇していた。** 通常アイドル時のRyzen 7 5700Xは40〜50℃台に収まるはずであり、この時点で既に冷却系に異常があったことを示す。ジョブ開始後は95℃前後まで到達し、Tjmax(Ryzen 5000シリーズは概ね90℃前後からPROCHOTによるハードウェアスロットリングが入り始める)に張り付いたまま推移していた。

CPU平均クロック(全16スレッド平均、netdata `cpu.cpufreq`)も、温度が95℃台に到達した08:53以降に2700MHz台→2300〜2500MHz台へ低下しており、周波数低下の傾向も温度上昇と時系列的に一致する。

## ファン回転数の確認: 「常時ほぼ一定」という異常

`sensors`/netdata `sensors.fan_nct6798-isa-0290_fan3_input`(推定CPU用ファンヘッダ)を01:38(起動直後)〜09:18まで確認したところ、**2740〜2836RPMの範囲でほぼ完全に一定**だった。温度が82℃の時も96℃の時も、負荷が0%の時も844%の時も、回転数はほとんど変化していない。

一方、`/etc/fancontrol`(`fancontrol.service`、稼働中)が制御しているのは`hwmon2/pwm2`のみで、その温度ソースは`hwmon1/temp2_input`(**GPU=amdgpu側の温度**)であり、**CPU温度(Tctl)に連動して回転数を調整するソフトウェア制御は元々存在しない**(マザーボードBIOS側のファン端子制御に委ねられている)。

**「ファンは(BIOSまたはハードウェア制御で)ほぼ一定速度で回り続けているにもかかわらず、CPUがほぼアイドルでも80℃台後半まで上昇し、高負荷では95℃に張り付き、負荷除去後も長時間高温が持続する」というパターンは、ファン単体の不調ではなく、CPUクーラーの放熱経路そのものの異常(簡易水冷のポンプ停止、ヒートシンク/ラジエーターの目詰まり、または大幅な熱伝導不良〈グリス劣化・グリス切れ・接触不良〉)を強く示唆する。** ファンが回っていること自体は正常に見えるため、外見上気づきにくい。

## issueで「サーマルスロットリングを否定した」根拠が誤りだった理由

issue #162は以下を根拠にサーマルスロットリングを否定していた:
- `thermald`の状態変化なし
- cgroupの`throttled`カウンタが0

しかし、`thermald`はIntel系CPU向けのユーザー空間デーモンで、AMD Ryzenでは実質関与しない(そもそも本マシンで`thermald.service`は`inactive`)。cgroupの`cpu.stat`の`throttled`カウンタは**CFSバンド幅制限(`--cpus`等)によるスロットリングのみ**を計測するものであり、**CPU自体がSMU/PROCHOTでハードウェアレベルに周波数を落とす現象(本件)は一切反映されない**。したがって、この2つの指標だけでハードウェアサーマルスロットリングを否定することはできない。今回、直接`k10temp`のTctlをnetdataの実績値として時系列で確認したことで、初めて温度上昇とfps低下の相関が可視化できた。

## 結論と推奨対応

1. **原因はソフトウェア環境(カーネル更新6.8.0-124→138、Docker/containerdのCPU増加等)ではなく、CPU冷却系のハードウェア障害である。** カーネル更新やcontainerd CPU増加は、CPU効率悪化(=スロットリング)の**結果**であって原因ではないと考えられる(スロットリングで処理が遅れるほど同じ処理により多くのCPU時間・ログ処理が必要になるため、`python3`/`containerd`/`dockerd`のCPU使用率が軒並み上昇したことも合理的に説明できる)。
2. **本マシンは現時点でも、無負荷でも80℃台後半、録画のような継続的な高負荷下では90℃台後半に達する状態が継続しており、危険な状態が解消されていない。** 本フェーズの検証後(負荷ゼロ)数分経過してもTctlは92.6℃のままで、正常な冷却なら数分でアイドル温度(40〜50℃台)まで下がるはずである。
3. **物理的な点検(特に簡易水冷を使用している場合はポンプの動作音・水温を直接確認、空冷の場合はヒートシンクの目詰まり・ファンの実際の風量・グリスの状態)が必要。** これはソフトウェア側から修復できない。
4. **冷却系が修復されるまで、本マシン(自宅ワーカー)で新たに長時間・高負荷な検証(th10の録画検証等)を行うことは推奨しない。** 継続的に95℃前後のジャンクション温度に晒すことはCPUの寿命・安定性の観点からも望ましくない。`sattori-home-worker.service`は既にユーザーの手で停止済み(2026-08-24 08:25 JST)であり、本フェーズの調査時点でも`inactive`のままであることを確認した(再起動すると`enabled`のため自動復帰する点に注意)。
5. ソフトウェア側での緩和策としては、sattori本体(`home-worker`側、本リポジトリ外)にCPU温度監視を組み込み、閾値超過時にジョブ受注を自動停止する仕組みを追加することが考えられるが、これはあくまで症状の悪化防止であり、根本解決には物理的な冷却系の修復が必須である。

## 追記(同日): 物理対応後の温度正常化を確認

ユーザーが電源断・エアフロー調整の物理対応を実施し、Geekbench 6による高負荷テストでも90℃近い高温が観測されなくなったとの報告を受けた。対応後にマシンは再起動されており(uptime確認で新しいboot)、本フォローアップ時点の`sensors`実測値は以下の通り、アイドル時の正常範囲まで回復していることを確認した:

| センサー | 対応前(本フェーズ前半、負荷ゼロ時) | 対応後 |
| --- | ---: | ---: |
| Tctl | 91.6〜98.4°C(高止まり・悪化傾向) | **57.6°C** |
| Tccd1 | 88.2〜94.2°C | **51.2°C** |
| CPUTIN | 75.5〜84.5°C(アラーム継続) | **48.0°C(アラームなし)** |

`sattori-home-worker.service`もユーザーの手で改めて`inactive`にされていることを確認した(`enabled`のままなので再起動で自動復帰する点は変わらず注意が必要)。

以上より、**本件の根本原因はハードウェアの冷却系異常であり、物理的な対応(エアフロー調整等)で解消したと判断できる。** 引き続きissue #158・th10録画検証など、CPUに高負荷をかける追加検証を再開する。
