## 2. 64bit DXライブラリ (`th06c` / `th06nc`) への実装詳細

### 2.1 プローブと静的分析結果 (`FRAME_SYNC_DXLIB_PROBE=1`)
`th06c.exe` (`th6_05.rpy`, 20s) の実機プローブと `th06c.exe` / `th06nc.exe` の PE インポート解析で以下を確認した:
- **描画**: `CreateDXGIFactory2` → `D3D11CreateDevice` → `IDXGIFactory2::CreateSwapChainForHwnd` (`vtable[15]`)。バックバッファは `DXGI_FORMAT_R8G8B8A8_UNORM` (`fmt=28`)。FFmpeg の `rawvideo` 入力は `pix_fmt=rgb0` を指定する必要がある（D3D8/D3D9 の `bgr0` のままでは R/B が反転する）。メインスレッド (`tid=280`) が `IDXGISwapChain::Present(SyncInterval=1, 0)` を呼ぶ。
- **音声**: ワーカスレッド（`th06c.exe` `0x140248ee0..0x14024905e`）が WASAPI 共有ポーリングモード（`flags=0x0`, `dur=100000`, `44100Hz/2ch/32bit float` `wFormatTag=0xFFFE`, `GetBufferSize=1323` [`30ms`]）で `Sleep(sleepMs)` → `GetCurrentPadding` → `GetBuffer(avail)` → `ReleaseBuffer(avail)` を回す。
- **タイマーと動的解決・ローダーロック**: 両 exe とも `CreateWaitableTimerExW`, `SetWaitableTimerEx`, `WaitForSingleObject`, `QueryPerformanceCounter` を静的インポートし、さらに `Sleep`, `GetTickCount`, `WaitForSingleObject`, `QueryPerformanceCounter`, `CoCreateInstance` を `KERNEL32!GetProcAddress` で動的解決する（メインスレッドは `SetWaitableTimerEx(due=-9500)` を高頻度で呼ぶ）。特に `th06nc` は起動時ローダーロック保持中に `GetProcAddress` へ入るため、`DllMain` / `MyGetProcAddress` 内での `Log()`・`CreateFile*()`・`CreateThread()`・`EnumWindows()` 呼び出しはデッドロックを招く。

### 2.2 追加・改修モジュール
- **`mods/common/frame_sync_wasapi.{h,cpp}`**（新規, `_WIN64`）:
  - `MyGetMixFormat` で `g_realMixRate` を退避した上でクライアントへ `44100Hz` を返し、`MyInitialize` ではコピーした `WAVEFORMATEX` のサンプルレートを `g_realMixRate` へ戻して実 `g_origInitialize` へ渡す一方、仮想リングはゲーム形式（`g_inRate=44100Hz`）で動作させる（非44.1kHzシンク時は線形補間リサンプラで吸収）。
  - `FrameSyncWasapiHandleSleep`: WASAPI スレッド (`g_wasapiThreadId`) からの `Sleep()` のみを横取りし、仮想リングに空きがあれば (`g_ringCount < g_bufFrames`) 即復帰して 0ms ロックステップ補充させ、満杯時は `g_needSamplesEvent`（上限50ms）で待機する。
  - `FrameSyncWasapiMixFrame`: 毎 `Present`（1/60s = `735` サンプル）で仮想リングから混合・`s16le` 書き出し（`refill_wait_ms=500`）。`Duplicate` 概念が不要な WASAPI 単一ミキサ出力のため、効果音漏れは原理的に発生しない。
- **`mods/common/frame_sync_d3d11.{h,cpp}`**（新規, `_WIN64`）:
  - D3D11 用 2面ステージングテクスチャ（`D3D11_USAGE_STAGING` / `D3D11_CPU_ACCESS_READ`）によるパイプライン化（`CopyResource` → 次フレーム `Map(D3D11_MAP_READ)` → FIFO 書出し）。`fmt=28/29` → `rgb0`、`fmt=87/88/91` → `bgr0` 自動判別。`IDXGISwapChain::ResizeBuffers` (`vtable[13]`) 時のリソース再生成対応。
  - exe IAT（QPC / `timeGetTime` / `GetTickCount*` / `Sleep` / WaitableTimer 6種 / `WaitForSingleObject`）と `Wrap*ForFrameSync` 動的解決ラッパを提供。WaitableTimer ハンドルを `TrackTimer` で追跡し、対象ハンドルへの `WaitForSingleObject` 等のみを仮想時計で即完了させる。
  - **ローダーロック厳守**: `InstallFrameSyncD3D11`・`InstallFrameSyncWasapi`・`Wrap*ForFrameSync` はログ・ファイル・スレッド生成を行わず、初回 `MyPresent` / `MyInitialize` 時点で遅延開局する。
- **`mods/th06c_replay_autoplay/{dllmain.cpp,build_mingw.sh}` & `mods/th06nc_replay_autoplay/{dllmain.cpp,build_mingw.sh}`**:
  - `FRAME_SYNC_PIPE` 有効時は `InstallFrameSyncD3D11(64)` を有効化（既存の倍速用 `InstallSpeedHackHook`/`InstallWasapiHook` は抑止）。`th06nc` では `d3d11_bc7_hook` の外側に D3D11 フレーム同期ラッパを直列接続した。
- **DXLib `PressVKey` 2フレーム保持修正（実測トラブル原因の恒久対策）**:
  - 初回の `th06nc` フル尺2本 (`full_th6_24`, `full_th6_20`) が両方ともメインメニューで **"Spell Practice"** へ誤進入した。原因は、(1) DXLib が `GetKeyboardState` を **1 `Present` あたり2回** 呼ぶため、従来の `holdFrames=1`（`g_pollCount` 基準）が **0.5描画フレーム相当** にしかならず約50%で `VK_DOWN` を取りこぼしていた点（`th06c` は `ReadMenuIndex()` リトライループの `WARNING: カーソルが動きませんでした` 1〜4回で自動回復していたが、`th06nc` は固定3回 `Down` の1回欠落で `0:Start → (Extraスキップ) → 1:Practice Start → 2:Spell Practice` へ入った）、および (2) `f_5.5s.png` 目視でタイトル待機 5.0s 時点がスライドイン途中だった点の2点。
  - `FrameSyncD3D11WaitPresentFrames(int frames)` を追加し、`FrameSyncD3D11Active()` 時は `PressVKey` で押下 `2 Present`・解放 `3 Present` 待機、さらに `th06nc` タイトル待機 `7000ms`・Step 1 後待機 `1200ms`（`th06c` も Step 1 後 `1200ms`）へ拡張したことで以降は100%リプレイへ進入した。

## 6. 本番サービス (`../sattori`) 反映に向けた推奨事項・注意点

1. **640x480 9タイトル (`th06`, `th06c`, `th07`〜`th13`) は CPU 先頭構成へ統合可能**:
   - `c7i.2xlarge`（`1.56〜2.57x`, `$0.034〜$0.063`/時）と `m7i.xlarge`（`0.99〜1.64x`, `$0.037〜$0.058`/時）および同世代 `c7a.2xlarge` / `m7i.2xlarge` / `c7i.xlarge` を CPU 段で組み合わせて使うことで、**G系クォータ消費ゼロ・`eu-north-1` レプリカ依存ゼロ**のまま現行 GPU 2倍速以上の品質・同等以下の費用を実現できる。特に `th11` / `th12` / `th128` への 4vCPU 解禁、`th13`（旧 `c7i.4xlarge` 4.3%落ち `$0.136` → `$0.044〜$0.058` 0%落ち）の劇的改善が大きい。
2. **`th06nc` 720p CPU+BC7・`th14`・`th15`・`th20` の GPU / CPU ハイブリッド**:
   - `th06nc` 720p は従来 GPU (`g6f.2xlarge` 2x) と併用しつつ、CPU フォールバック先 `c7i.2xlarge` に `--frame-sync` + `D3D11_DECODE_BC7=1` を入れることで Extra 7.6% 落ち問題を解消し、速度2倍・費用42%減（`~1.00x` / `$0.068〜$0.092`/時）になる。
   - `th15`・`th20`（および追補の `th14`）は従来通り GPU (`g6f` 系) が枯渇・待ち超過した際の CPU フォールバック先 `c7i.4xlarge`（`th14`/`th15`/`th20` `1.11〜1.48x`, `$0.105〜$0.142`/時、約43〜63%削減 + 局所落ち・120分上限解消）として即時導入効果が高い。さらに `g6f.xlarge` (`4vCPU`) も `1.00x` (`$0.098`/時)・0%落ちで動作する（Gクォータ半分消費）。
3. **本番変更前の必須条件 (`../sattori/AGENTS.md` §3 準拠)**:
   - 上記のうち `th12`・`th15` 以外の12タイトル（追補 `th14` 含む）は **ローカル Xvfb 実測値から校正した推定** であり、`c7i-flex.xlarge` / `g6f.2xlarge`（`--frame-sync` 下）や `th06nc` CPU+BC7 の `c7i.2xlarge` は AWS 実機未測定である。`recordingPlan.ts` のインスタンス候補・速度を更新する前には必ず対象タイトル・対象インスタンスの AWS Spot 実機検証を経ること。
4. **`sattori` ワーカー・API 側の実装調整箇所**:
   - **録画呼び出し**: `--frame-sync` 付与（`th06nc` の CPU 時は既存の `D3D11_DECODE_BC7=1 WINEDLLOVERRIDES="d3d11,dxgi,d3d10core=b"` を付与、`th06` のローカルテスト時と異なり本番は正常な `th06_05.wav` を使うこと）。
   - **監視・品質チェック**: `--frame-sync` 時は生録画時点で 60fps 固定（`frames_written == video_frames == audio_frames`）になるため、現行の `重複フレーム率異常検知`（`default_max_duplicate_rate`）と `FpsMonitor` 下限/上限アラート・処理落ち早期検知を無効化し、必要に応じ `th15 c7i.2xlarge` 等の遅い構成向けに `MAX_WALL_CLOCK_TIMEOUT_SEC`（120分）を見直す。
   - **完了時間見積り・変換比率 (`packages/shared/src/recordingSpeed.ts`, `worker/convert.py`)**: 倍速/低速時のフレーム復元フィルタを外した状態で `ratio`（640x480: `c7i.2xl 0.237` / `m7i.xl 0.402`, 1280x960: `c7i.4xl 0.375` 等）を更新する。
