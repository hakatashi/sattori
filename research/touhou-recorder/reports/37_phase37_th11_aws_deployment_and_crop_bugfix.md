# フェーズ37: th11(地霊殿)のAWS実機検証とクロップ座標バグの発見・修正

日付: 2026-07-25

## 目的

フェーズ36までにローカル環境(Xvfb)でth11のE2E録画パイプラインを構築した。本フェーズでは、th08・th06と同様の方法論でth11をAWS EC2上のDockerコンテナで実際に録画し、より新しい(高い描画スペックを要求しうる)タイトルであるth11がクラウド環境固有の問題を抱えていないかを検証した。録画対象は新たに配置された`games/th11/replay/th11_ud16gm.rpy`(Lunaticステージ、約32分)。

## `cloud/docker/aws/Dockerfile.multigame`へのth11追加

既存のth07/th08/th06対応イメージに、`games/th11/`・`prefixes/th11-wined3d-gl/`・`mods/th11_replay_autoplay/build/th11_hook.dll`のCOPYを追加した。あわせて、Dockerビルドコンテキストがこれまで`.dockerignore`無しでリポジトリ全体(19GB超、`instances/`や`runs/`の生成物込み)を毎回daemonへ転送していた問題に気づき、`.dockerignore`を新規作成して不要なディレクトリを除外した。

## 発見・修正1: リプレイ画面のクロップ座標ズレ(ウィンドウ装飾問題)

AWS実機でのフル尺録画後、ユーザーから「録画データを確認したが画面がズレている」との指摘を受けた。抽出したフレームを確認すると、ウィンドウのタイトルバー(青い帯)が録画領域に写り込み、右側のスコア/グレイズパネルが枠外に切れていた。

### 原因

フェーズ36で追加された「ウィンドウをopenboxの初期配置から強制的に(0,0)へ移動する」対策(`xdotool windowmove <winid> 0 0`)は、移動後の実座標を再取得せず`x, y = 0, 0`と決め打ちしていた。ローカルホスト環境ではth11のウィンドウがopenboxにより装飾されない(タイトルバーなし)ため座標のズレが発生しなかったが、**AWS上のDockerコンテナ環境ではopenboxがウィンドウを装飾していた(タイトルバー付き)ため、`windowmove`はウィンドウ枠を(0,0)へ移動する一方、クライアント領域(実際のゲーム画面)は装飾分だけ内側にずれる**。この結果、`x,y=0,0`という誤った前提でx11grabのクロップ座標を決めてしまい、録画にタイトルバーが写り込み、右端が切れるバグとなっていた。

### 修正1回目: 移動後の座標を再取得

`xdotool windowmove`実行後、`find_window()`を再度呼び出して実際のクライアント座標を取得するよう修正。ローカル・AWS双方でこの修正のみを検証したところ、ローカルでは問題なく動作したが、**AWS実機では`xdotool windowmove`の反映が非同期であり、直後の1回きりの再取得では移動前の座標(画面外にはみ出す座標)がそのまま返ってくることがあり、x11grabが`Capture area ... outside the screen size 800x600`で起動失敗する**という、フェーズ35/36の元々の問題が別の形で再発した。

### 修正2回目: windowmoveの再試行ループ

座標がXVFB_SCREEN(800x600)の範囲内に収まるまで、`xdotool windowmove`を最大20回(0.1秒間隔)再試行するよう修正。この修正によりAWS実機でもクロップ座標が正しく`:95+0,0`に収束することを確認し、視覚的にも画面全体(タイトルバーなし、スコアパネル欠けなし)が正しく録画されることを確認した。

修正箇所: `scripts/25_record_replay_e2e_multigame.py`の`attempt_recording()`内、ウィンドウ移動処理。

## 発見2: `th11_ud16gm.rpy`固有の画面静止検知タイムアウト問題

修正版での通常実行(画面静止検知による自然終了判定)を試みたところ、フル尺録画が2400秒(40分)のハードタイムアウトに到達し、mux失敗を伴って試行1が失敗、試行2も同様に長時間化する兆候が見られた。

`poll_log`を確認したところ、リプレイ終了後のPause Menu画面において**MAD値が2.2〜3.0程度で推移し続け、静止判定の閾値(2.0)をわずかに上回ったまま8回連続の閾値未満を満たせない**ことが原因と判明した。フェーズ36で`th11_03.rpy`を検証した際はPause Menu画面のMADが0.01〜0.09まで明確に下がり静止判定が機能していたが、`th11_ud16gm.rpy`ではこの静止具合がわずかに閾値を超えたままとなり、静止検知に失敗する。

これはフェーズ36の「th11は画面静止検知のみに依存しており、他のリプレイでも同様に安全かは未検証」という懸念が実際に顕在化した事例である。

### 対応(今回の一時回避)

既に確認済みの正しい尺(1894秒前後)を根拠に、`--record-seconds 1900`で固定秒数録画に切り替えて確実に録画を終了させた。これは今回の検証を完了させるための一時的な回避策であり、恒久対応(MAD閾値の見直し、またはth11専用の別の終了検知方式の検討)は今後の課題として残る。

## 発見3: `--entrypoint`直接指定時のPulseAudio起動漏れ

検証中、`docker run --entrypoint python3 ... /app/scripts/25_...`のように`entrypoint.py`を経由せず直接スクリプトを呼び出す方式を用いた際、`entrypoint.py`が担っていたPulseAudio起動処理がスキップされ、音声用ffmpegが`auto_null.monitor`のオープンに失敗(`No such process`)して録画全体が失敗する事象が発生した。`--entrypoint bash -c "pulseaudio -D ... && python3 /app/scripts/25_..."`のようにPulseAudioを明示的に起動してから本処理を呼び出すことで回避した。今回のような`entrypoint.py`非対応のオプション(`--record-seconds`等)を使う一時的な検証では、この点に注意が必要。

## AWS実機検証結果(最終)

### 環境構築

フェーズ32の方法論を踏襲し、`aws ec2 run-instances`(Spot、`c7i.xlarge`、us-east-1)で直接構築した。キーペア・セキュリティグループ・IAMロール/インスタンスプロファイル・ECRリポジトリを`touhou-recorder-verify-*`の命名で作成。AMIはUbuntu 24.04(SSM Parameter Store経由で最新イメージIDを取得)、ルートEBSは40GiBに拡張。IAMロールにはECR読み取り権限のみ付与し、S3バケットは作成しなかった(動画取得はscpで実施)。

### フル尺録画(`th11_ud16gm.rpy`、Lunaticステージ)

| 項目 | 結果 |
|---|---|
| インスタンス | `c7i.xlarge`(Spot、us-east-1) |
| 総録画時間 | 1914.1秒(約31.9分) |
| 検知方式 | `--record-seconds 1900`による固定尺停止(自然終了検知は上記の理由により不使用) |
| A/V同期補正 | 0.603秒(自動補正、正常に機能) |
| 出力ファイルサイズ | 約1.30GB |
| 重複フレーム率(全体、15〜1909秒) | **6.3%**(区間サンプリング7点の平均も同じく6.3%、区間ごとの幅は0.6%〜18.4%) |
| 視覚確認 | 画面全体が正しくフレームに収まり、日本語フォント(スペルカード名等)も文字化けなく表示 |

`runs/th11_aws_c7i_xlarge_full/video.mp4`にフル尺動画を配置(gitignore対象)。

th08の`c7i.xlarge`基準(1.9〜7.4%)・th11ローカル検証(フェーズ36、0.3%)と比較すると重複フレーム率はやや高めだが、致命的な水準ではなく、th08がAWS初回検証で経験したような90%超の破滅的な劣化は見られなかった。th11は他タイトルで得られた教訓(音声分離録画、A/V同期補正)を`scripts/25`が既に標準装備していたため、th08のような多段階の真因調査を要さなかった。

## クリーンアップ

検証終了後、本フェーズで作成した全AWSリソースを削除済み。

- EC2インスタンス(`c7i.xlarge`、Spot): `terminate-instances`で終了・`terminated`状態を確認済み
- キーペア(`touhou-recorder-verify-key`)・セキュリティグループ(`touhou-recorder-verify-sg`)・IAMロール/インスタンスプロファイル(`touhou-recorder-verify-role`/`-profile`)・ECRリポジトリ(`touhou-recorder-multigame`): いずれも削除済み、削除後に存在しないことを確認済み

## 今後の課題

- **`th11_ud16gm.rpy`で顕在化した画面静止検知のタイムアウト問題は未解決**。他のth11リプレイでも同様の問題が起こりうる。恒久対応としては、MAD閾値の緩和(ただしフェーズ14の教訓通り誤検知リスクとのトレードオフ)、あるいはPause Menu画面の特徴部分(「Pause Menu」の文字表示領域等、フェーズ36で示唆された案)を使った別の終了検知方式の検討が必要
- ウィンドウ移動の再試行ループ(最大20回×0.1秒=2秒)はth11のAWS実機で機能したが、より遅い/不安定な環境では収束しない可能性がある。その場合は`WARNING`ログを出力した上で最後に取得できた座標を使う(録画自体は継続する)フォールバック動作になっているため、致命的な失敗にはならないことは確認済み
- ローカルホスト環境の別件として、本フェーズの作業中にホストのルートディスクが100%枯渇する事象が発生し、`docker system prune -af --volumes`で149GB解放して対応した。この際、本プロジェクトと無関係な他プロジェクト用のDockerイメージも巻き添えで削除してしまった。今後はdocker prune系のコマンド実行前に必ずユーザーに確認を取る方針とする
