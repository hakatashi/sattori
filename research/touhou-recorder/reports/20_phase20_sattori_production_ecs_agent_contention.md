# フェーズ20: Webサービス(Sattori)本番環境での重複フレーム率悪化とECSエージェント競合の特定

日付: 2026-07-17

## 背景

PoC完了後に開発された東方リプレイ録画Webサービス「Sattori」(別リポジトリ`sattori`、モノレポ)の本番環境(AWS, us-east-1)で、ユーザーから「録画した動画がカクついているような気がする」との報告を受けた。本レポートは`sattori`リポジトリ側のセッションで行った調査・対策・検証の記録だが、**原因がPoCで確立した知見(本レポートの前提)から外れた本番固有のインフラ差異だった**ため、今後同種の構成でハマらないよう本リポジトリにも記録する。

Sattoriの録画バックエンドはPoCの成果(`scripts/11_record_th07_replay_e2e.py`相当のロジック、`c7i.xlarge`、Xvfb 800x600x24、ffmpeg `libx264 veryfast crf18`、ウォーターマーク合成)をほぼそのまま移植したものであり、`worker/record_th07.py`のffmpegコマンド構築・Xvfb起動・エンコード設定はPoCと完全に一致していた。

## 症状の定量化

本番で録画された動画(640x480/60fps/851.7秒、`th7_07.rpy`)に対し、本リポジトリの`scripts/measure_duplicate_frame_rate.sh`で重複フレーム率を計測したところ、**全体で8.0%**(51101フレーム中46990ユニーク)だった。フェーズ19で確立した「同構成(`c7i.xlarge`+ウォーターマークあり)のベースラインは全編4.7%」より明確に悪化していた。

区間別(10秒刻み)に見ると、フェーズ12・13のような**一様な劣化ではなく、特定区間への偏りが見られた**:

- 冒頭0-60秒: 5〜26%(タイトル画面・メニュー自動操作を含むため一部は正当な静止)
- 道中(80-300秒): 1〜7%と良好
- **八雲藍(Extraボス)のスペルカード「ユーニラタルコンダクト」を含む580-670秒区間: 15〜26%**(全区間中最悪)
- 830秒以降: 85〜98%(リプレイ終了検知後の一覧画面静止で正当)

ゲーム内蔵のFPSカウンター(画面右下表示)をフレーム抽出で目視したところ、**最悪区間(600秒・620秒)でもゲーム側は60.00fps/60.03fpsを維持しており、ゲームプレイ自体の処理落ちではないことを確認した**。これはフェーズ12・13で確立した「録画の重複フレームはゲーム側ではなくx11grabキャプチャ側の取りこぼしに起因する」という前提と整合する。

## 調査の過程(検証して棄却した仮説)

1. **リプレイ内容(キャラ・ステージ)の違い説**: 当初、本番録画がPoCと異なるリプレイ(Extraステージ)を使っている可能性を疑ったが、**ユーザー確認により本番も`th7_07.rpy`(PoCと同一ファイル)であることが判明**。この仮説は完全に否定された
2. **ウォーターマーク合成のCPU負荷説**: フェーズ19で「ウォーターマーク合成(overlay+libvpx-vp9デコード)を追加しても全編4.7%で無しの場合と実質同一」と既に実証済みであり、この観点からも否定された(ユーザーからフェーズ19レポートを直接指摘され撤回)
3. **エンコード設定・Xvfb解像度の差異説**: `sattori`リポジトリの`worker/record_th07.py`とPoCの`scripts/11_record_th07_replay_e2e.py`を直接diff的に比較したところ、`XVFB_SCREEN="800x600x24"`、`ffmpeg -f x11grab ... -c:v libx264 -preset veryfast -crf 18`など、キャプチャ・エンコード関連の設定は完全に一致しており、この観点でも差異は無かった

## 真因: ホストAMIの違い(ECS最適化AMI vs 標準AMI)によるECSエージェントとのCPU競合

`sattori`のインフラ(AWS CDK)は、ワーカーEC2インスタンスのAMIとして**SSMパラメータ`/aws/service/ecs/optimized-ami/amazon-linux-2023/recommended/image_id`(ECS最適化AL2023)**を参照していた。理由は「Dockerが同梱されているためUserDataでの追加インストールが不要」という運用上の利便性からだったが、**ECS最適化AMIは(ECSクラスタに参加させなくても)ECSエージェントが常駐したまま**であり、UserDataは`docker`サービスだけを明示起動し、ECSエージェント自体は無効化していなかった。

一方、本リポジトリのPoC(`cloud/terraform/aws/main.tf`)は`data "aws_ami" "amazon_linux"`で**標準のAL2023 AMI**(`al2023-ami-*-x86_64`)を使い、UserDataで`dnf install -y docker`を実行してからdockerを起動しており、**ECSエージェントは最初から存在しない**。

4vCPU(`c7i.xlarge`)というPoCで既に「実用下限」と結論している構成では、通常のゲームプレイ中は余裕があるが、**八雲藍のような弾幕密度が最大になるExtraボス戦でCPU使用率が飽和し、そこにECSエージェント(Dockerイベント監視・メタデータポーリングを行う常駐Goプロセス)のCPU消費が加わることで、ffmpegのx11grabキャプチャがフレームを取りこぼす**と推測される。これはフェーズ17が示唆した「ffmpegのx11grab+エンコードとWineレンダリングスレッド間のCPUコンテンション」の構図に、**第3の競合者(ECSエージェント)が本番環境だけに追加されていた**という説明になる。

## 検証

同一リプレイ(`th7_07.rpy`)・同一ECRイメージ・同一インスタンスタイプ(`c7i.xlarge`)で、AWS CLIから`run-instances`を直接呼び出し、3構成を比較した(`JOBS_TABLE`環境変数を渡さずDynamoDB更新をスキップすることで、本番のジョブレコードを汚さずに検証した)。

| 構成 | 全編重複率(0-852s) | 八雲藍戦(580-670s) |
|---|---|---|
| 本番(ECS最適化AMI, ECSエージェント有効、対照) | 8.0% | **15〜26%** |
| ECS最適化AMI + `systemctl disable --now ecs` | **6.1%** | **4.8%** |
| 標準AL2023 + `dnf install docker`(PoC構成の再現) | 7.2% | 3.3% |

**両対策とも本番比で明確に改善し、特に最悪区間だった八雲藍戦の取りこぼしが15〜26%から3〜5%へ激減した**。この桁違いの改善幅は、フェーズ17が警告した「単一60秒サンプルの1.3%〜17.4%のブレ」では説明できない大きさであり、ECSエージェント常駐が原因であったことを裏付ける。

対策として、**ECS最適化AMIを維持したまま`systemctl disable --now ecs`をUserDataに1行追加する方式を採用**した(標準AMI化はDocker導入の追加インストールでインスタンス起動オーバーヘッドが増えるため見送った)。本番デプロイ後、実際にWebサービスのAPIフロー(署名付きURL発行→S3 PUT→ジョブ起動→EC2 Spot起動→録画→S3アップロード)を通して同一リプレイを再録画し、全編6.1%を再現できることを確認した(八雲藍戦は11.5%で、実験時の4.8%よりは高いが、本番対照の15〜26%からは明確に改善しており、単一ラン間の自然な変動の範囲内と判断した)。

## 教訓

- **「Dockerが同梱されているから」という理由だけでECS最適化AMIをプレーンなDockerホストとして流用すると、ECSエージェントが常駐CPU消費者として残る**。ECSクラスタに参加させない用途で使う場合は、`systemctl disable --now ecs`(または標準AMI+Docker個別インストール)を必ず行うこと。この教訓はPoC実施時点(本リポジトリ)では踏んでいなかった罠であり、Webサービス側で初めて顕在化した
- **4vCPU構成は「実用下限」であり、ボス戦・高密度弾幕のような最高負荷区間ではわずかな追加CPU消費者でも処理落ちとして顕在化する**。平常時の負荷(道中)では問題が見えず、特定の高負荷区間だけで悪化するため、**全編通しての計測に加えて、最も負荷の高い区間(Extraボスのスペルカード等)を意図的にサンプリングして評価することが望ましい**(フェーズ17の「全編で評価すべき」という教訓をさらに一歩進めた形)
- **ゲーム内蔵のFPSカウンター(存在するタイトルでは画面に表示される)を目視することで、「ゲーム側の処理落ち」と「キャプチャ側の取りこぼし」を即座に切り分けられる**。本件でも最悪区間でゲーム側が60fpsを維持していることを確認できたことが、原因をキャプチャ側に絞り込む決め手になった
- 一見無関係に見える「ホストAMIの選定」がキャプチャ品質を左右し得ることが分かった。今後、他のクラウド環境(GCP等)やインスタンスタイプを新規に検証する際も、**OS/AMIに何が常駐しているか(監視エージェント、コンテナオーケストレーションのエージェント等)を事前に確認する**べきである

## 副次的な改善: ワーカーログの永続化

調査の過程で、本番ワーカーの`docker run --rm`にログドライバ指定が無く(デフォルトの`json-file`)、かつコンテナは`--rm`で即削除・インスタンスも録画完了後に自己終了(`shutdown -h now`)するため、**録画完了後はワーカーのログが一切残らず、事後診断ができない**ことが判明した(本件の調査でも、問題発生時の録画自体のffmpegドロップ統計は取得できず、状況証拠からの推測と再現実験に頼らざるを得なかった)。

対策として、Sattori側に以下を追加した:
- CloudWatch Logsロググループを新設し、`docker run`に`--log-driver awslogs`を指定してジョブIDごとのログストリームに送出
- ffmpegの標準エラー出力はファイル(`ffmpeg.log`)にリダイレクトされコンテナのstdoutに乗らない実装だったため、録画終了後にその末尾数行(dup/drop等の最終統計を含む)をentrypointのログ経由でも出力するよう変更

この対策は`sattori`リポジトリ側のみの変更であり、本リポジトリのPoCスクリプトには影響しない。

## 成果物(すべて`sattori`リポジトリ側)

- `apps/api/src/ec2.ts`: UserDataに`systemctl disable --now ecs`を追加、`docker run`に`--log-driver awslogs`を配線
- `infra/lib/sattori-stack.ts`: CloudWatch Logsロググループ`/sattori/worker`を新設、ワーカーIAMロールに書き込み権限を付与
- `worker/record_th07.py`: ffmpegの最終統計行をentrypointログにも出力するよう変更(次回workerイメージ再ビルド時に反映、本レポート作成時点では未反映)
- 検証用録画3本(本番対照・ecs無効化・標準AL2023)は一時的に起動したEC2インスタンスで生成し、比較後は自己終了(`shutdown -h now`)により削除済み。動画ファイル自体はローカル一時ディレクトリに保存したのみでリポジトリには含めていない

## 未検証・今後の課題

- 八雲藍戦のような最高負荷区間は対策後も4.8%〜11.5%とラン間でブレが残る。より確実な余裕を持たせたい場合、フェーズ17で実証済みの`c6i.2xlarge`(8vCPU、価格約2倍)への切り替えが選択肢になる(Sattori側では月間利用規模とコストのトレードオフとして未検討)
- 本レポートの検証は`c7i.xlarge`1構成・各1回のみ。ECSエージェント無効化の効果が他インスタンスタイプでも同様かは未確認
- ECS最適化AMI上でECSエージェント以外に常駐しうる他のエージェント・デーモン(SSMエージェント等)のCPU消費については個別に切り分けておらず、`disable --now ecs`の効果に一元化して説明している。より厳密な要因分解にはプロファイリング(`perf`等)が必要
