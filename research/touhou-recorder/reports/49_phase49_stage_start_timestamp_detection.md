# フェーズ49: ステージ開始タイムスタンプの検出と記録

## 背景・目的

録画した動画をYouTube等にアップロードする際、動画説明欄にそのまま貼れる「各ステージの
開始時刻」(チャプター)を一緒に出力できると便利、というユーザー要望を受けた調査。

要件は「録画と同時に、インジェクトされているDLLの仕組みを利用して、各ステージがロード
された瞬間を検知し、その時刻を外部から記録する」こと。

ユーザーから、既存の録画動画を目視した実測値(グラウンドトゥルース)の提供を受けた:

| タイトル | リプレイ | 1面 | 2面 | 3面 | 4面 | 5面 | 6面 |
|---|---|---|---|---|---|---|---|
| th07 | `th7_09.rpy` | 00:04 | 03:05 | 07:05 | 12:18 | 19:44 | 25:53 |
| th08 | `th8_06.rpy` | 00:05 | 03:01 | 06:44 | 11:37 | 17:48 | 23:48 |
| th20 | `th20_01.rpy` | 00:15 | 03:18 | 07:01 | 11:39 | 16:55 | 21:30 |

## 結論(先に要約)

**実現可能。** th07・th08・th20の3タイトルで実装・フル尺録画での実機検証まで完了した。

検出方式はタイトルによって2通りが必要だった:

| タイトル | 方式 | 実装 | ユーザー実測との差 |
|---|---|---|---|
| th07 | ステージ番号変数のポーリング(`th07.exe+0x0022583c`) | `stage_marker_hook` | **±1秒以内** |
| th08 | 同上(`th08.exe+0x000e4850`、0始まり) | `stage_marker_hook` | **±2秒以内** |
| th20 | `th20.dat`のアセットロードバースト検出 | `stage_marker_io` | ゲーム内時間換算で**±5秒以内**(下記) |

- ステージ番号変数のRVAは、本フェーズで作成した差分メモリスキャン用の診断フック
  (`mods/common/stage_probe_hook.*`)で**実測により自動的に絞り込める**ため、
  他タイトルへの横展開もリバースエンジニアリングの勘に頼らずに行える
- th20はステージ番号が静的変数に無く(`.data`が0.217MBしかない)、差分メモリスキャン
  自体もゲームをフリーズさせるため、代替としてファイルI/O方式を実装した
- 記録した時刻(UNIXエポックms)は、既存の`-copyts`によるffmpegの絶対開始時刻
  (`ffprobe_start_time()`、フェーズ28で音ズレ補正のために導入済み)との差分で、
  **動画先頭からの経過秒に厳密に変換できる**。録画開始時刻の推定は不要
- th20の等倍録画は処理落ちするため実時間ではユーザー実測から最大53秒ズレたが、
  これは**検出誤差ではなく実際に落ちたフレーム**であることを定量的に確認した
  (ゲーム内時間に換算すると±5.2秒以内で一致)

## 「リプレイファイルから計算すればよいのでは?」を最初に否定した

DLLを使わずとも、リプレイファイルにはステージごとのフレーム数が入っている
(`@sattori/touhou-replay-parser`の`ReplayStageSplit.frameCount`)。東方本編の
ゲームロジックは60fps固定なので、累積フレーム数÷60で計算できるはずである。

しかし**実測値と合わない**。ユーザー提供のグラウンドトゥルースと突き合わせると:

| | th07 (`th7_09.rpy`) | th08 (`th8_06.rpy`) |
|---|---|---|
| リプレイの累積フレームから予測した各面開始 | 00:04 / 03:07 / 07:15 / 12:41 / 20:20 / 26:47 | 00:05 / 03:00 / 06:43 / 11:37 / 17:50 / 23:55 |
| 実測 | 00:04 / 03:05 / 07:05 / 12:18 / 19:44 / 25:53 | 00:05 / 03:01 / 06:44 / 11:37 / 17:48 / 23:48 |
| 末尾の誤差 | **-54秒** | -8秒 |

ステージごとに「リプレイのフレーム数 ÷ 実測の所要時間」を出すと、**th07は約62.5fps、
th08は約60fps**で進行していることがわかる。TH06〜TH09系が60fpsちょうどではない
(1フレーム16ms = 62.5fps)のは東方コミュニティでは既知の事実で、th07で顕著に出た形。

| ステージ | th07 実効fps | th08 実効fps |
|---|---|---|
| 1面 | 60.8 | 59.9 |
| 2面 | 62.1 | 59.8 |
| 3面 | 62.5 | 60.2 |
| 4面 | 61.8 | 59.1 |
| 5面 | 62.8 | 60.8 |

さらに、ステージごとに値がばらついている(1面だけ低い等)ことからも分かるとおり、
**ステージ間のロード時間やステージ導入演出など、リプレイのフレーム数に現れない実時間**が
乗る。60fps固定を前提にした単純計算ではこれらを一切扱えない。

したがって**オフライン計算では実用精度に届かず、実時間の実測が必要**である、という
前提が確認できた。これが本フェーズの出発点になっている。

## 検出手段の候補と、診断フックによる実測

`mods/common/stage_probe_hook.*`(`STAGE_PROBE=1`のときのみ有効な診断専用コード)を
新規作成し、2系統を同時に観測した。

### (A) ファイルI/O観測

KERNEL32の`CreateFileA/W`・`ReadFile`・`SetFilePointer(Ex)`・`CloseHandle`をIATフック
し、「どのファイルのどのオフセットを何バイト読んだか」を250ms窓で集計する。5タイトル
(th06/07/08/11/20)いずれもこれらをインポートしていることはPEのインポートテーブルで
事前確認済み。

th07で`th7_09.rpy`を9分20秒再生した実測結果:

| 事象 | 観測されたシグネチャ |
|---|---|
| BGMトラック切り替え | `thbgm.dat`を`seeks=3`+`bytes=705600`(初期バッファ充填)で読む |
| BGMループ | `seeks=1`で読み出しオフセットが後方へ戻る |
| ステージ開始 | 上記トラック切り替え + `th07.dat`から約1930バイトの小さな読み出し |

```
t=00:08.02 frame=368   offset 1719916  -> 16545584  (リプレイ開始 = 1面)
t=01:44.44 frame=6237  offset 21589300 -> 32044848  (1面ボス曲)
t=03:08.58 frame=11363 offset 37192532 -> 44332844  (2面)
t=07:07.76 frame=26255 offset 70170904 -> 78899120  (3面)
t=09:10.73 frame=34085 offset 80643676 -> 100917680 (3面ボス曲)
```

**BGM切り替えは1ステージあたり2回(道中曲・ボス曲)起きるため、これ単独ではステージ
境界を確定できない**。道中曲とボス曲を区別するにはトラックオフセット→曲番号の対応表が
必要で、ゲームデータのバージョンごとに作り直す必要がある。

また、th07はアセットを起動時にまとめて読み込む作りで、**ステージ境界に大きな
`th07.dat`読み出しバーストは発生しない**(100KB超のバーストは起動直後の4回のみ)。
「ステージロード時のアセット読み込みバーストを検出する」という当初のアイデアは、
少なくともth07では成立しない。

### (B) メモリ差分スキャン(ステージ番号変数の探索)

プロセスの書き込み可能領域のシャドウコピーを保持し、250msごとに1バイト単位で差分を
取る。バイト単位で見るのは、BYTE変数でもDWORD変数(リトルエンディアンの下位バイト)でも
同じ仕掛けで拾えるようにするため。

素朴に「値が`old+1`に変化したバイト」を全部ログに出すとノイズに埋もれるため、
**ウォームアップ期間(既定90秒)は一切ログを出さずに変化回数だけを蓄積する**方式に
した。毎フレーム変化するような雑多な変数はこの間に変化回数が飽和して恒久的に除外され、
ウォームアップ後は「めったに変化しない変数」だけが残る。

結果、9分20秒の実行(2面・3面の2回の遷移を含む)で、
**両方の遷移時刻で同時に、かつ値が`1->2`・`2->3`と推移した静的変数**は2つに絞れた:

```
0x0062583c (th07.exe+0x0022583c) : 1->2@03:08.47  2->3@07:07.58
0x0133dfa8 (th07.exe+0x00f3dfa8) : 1->2@03:08.47  2->3@07:07.58
```

いずれもBGM切り替え(03:08.58 / 07:07.76)の**約0.1〜0.2秒前**に変化しており、
「ステージがロードされた瞬間 → その後BGMが切り替わる」という因果とも整合する。

なお、副産物として`0x00340100`(ヒープ)が`01:44.37 / 03:08.47 / 05:19.44 / 07:07.58 /
09:10.83`で変化する「BGM切り替え回数カウンタ」であることも判明した(道中曲・ボス曲の
両方で増える)。

## 実装

### `mods/common/stage_marker_hook.*`(本番用)

特定したRVAの値を5msごとにポーリングし、変化した瞬間に1行出力するだけの軽量フック。

```
StageMarker: stage=2 prev=1 frame=11353 epoch_ms=1786270380176
```

- `epoch_ms`はUNIXエポックms(`GetSystemTimeAsFileTime`由来)。ローカル時刻文字列では
  なくエポックを出すのは、タイムゾーン・日付跨ぎの解釈を挟まずに引き算できるようにする
  ため
- `frame`は`g_hookCallCount`(既存のフレーム相当カウンタ)。リプレイファイルの
  ステージ別フレーム数との突き合わせ検証に使える
- 想定外の値(`maxStage`超)は無視する。ゲームデータが更新されてRVAの意味が変わった
  場合に誤ったマーカーを出さないための安全側フォールバック
- RVAは`STAGE_MARKER_RVA`環境変数で上書きできる(候補の検証用)

### `scripts/25_record_replay_e2e_multigame.py`へのチャプター出力追加

`write_stage_chapters()`を追加し、録画完了後に`StageMarker`行を動画内時刻へ変換して
2ファイルを書き出す。

- `<出力名>.chapters.txt` — YouTube説明欄にそのまま貼れる形式
- `<出力名>.chapters.json` — `stage` / `time_sec` / `timestamp` / `game_frame`

変換式は `動画内時刻 = epoch_ms/1000 - 動画のt=0に対応する絶対時刻`。後者は
**フェーズ28のA/V同期補正のために既に取得していた`-copyts`のstart_time**をそのまま
再利用できる(映像が音声より遅れて始まった場合はmux後のt=0が音声側になるため、
そのケースでは`a_start`を基準にする)。録画開始時刻の推定に頼らないので、ffmpegの
初期化レイテンシによる誤差が入らない。

th20のスローモーション録画(`FPS_LIMIT_TARGET_HZ`、reports/47)に対しては、
`scripts/47_descale_th20_slowmo.py`で等倍化した後の動画に合わせて`1/MENU_TIME_SCALE`を
掛ける。

## 実機検証

### スモークテスト(th07、4分20秒)

```
[19:09:51.808] StageMarker: baseline stage=0 frame=0
[19:09:59.529] StageMarker: stage=1 prev=0 frame=356
[19:13:00.176] StageMarker: stage=2 prev=1 frame=11353
```

`11353 - 356 = 10997`フレーム。リプレイファイルが記録している1面のフレーム数は
**11000**なので、**誤差3フレーム(50ms)**。ステージ境界を正しく捉えられている。

同区間の実時間は180.647秒で、実効60.87fps。60fpsちょうどではないことがここでも確認
できる。

### フル尺録画(th07 `th7_09.rpy`)

`scripts/25`で`th7_09.rpy`をフル尺録画し、自動生成された`video.chapters.txt`を
ユーザー提供のグラウンドトゥルース(**別マシン・別録画**、AWS実機で録画したもの)と
突き合わせた。

| ステージ | ユーザー実測(AWS録画) | 自動出力(ローカル録画) | 差 |
|---|---|---|---|
| 1面 | 00:04 | 00:05 | +1s |
| 2面 | 03:05 | 03:05 | 0 |
| 3面 | 07:05 | 07:04 | -1s |
| 4面 | 12:18 | 12:18 | 0 |
| 5面 | 19:44 | 19:44 | 0 |
| 6面 | 25:53 | 25:52 | -1s |

**全ステージで±1秒以内**。目視実測側の読み取り精度(1秒単位)を考えると、実質誤差なしと
言ってよい。YouTubeのチャプター用途には十分すぎる精度である。

出力された`video.chapters.txt`:

```
00:00 動画開始
00:05 1面
03:05 2面
07:04 3面
12:18 4面
19:44 5面
25:52 6面
```

なお、この録画は終了検知が働かず40分のタイムアウトで停止した
(`template_MAD=39.10`で閾値15.0を下回らない)。これは`AGENTS.md`の既知課題
「th08/th07の録画クロップにタイトルバーが写り込みテンプレート照合が一致しない」
がローカルのth07でも起きているもので、**本フェーズの変更とは無関係**。チャプター
出力自体は正常に行われた。

## th08への横展開

同じ手順(プローブ → 候補絞り込み → マーカーフック)をth08(`th8_06.rpy`)に適用し、
**手順がそのまま通用することを確認した**。

- ステージ番号変数: `th08.exe+0x000e4850`(DWORD、**0始まり**)。`stageBase=1`を
  指定して1始まりに補正する
- ステージ遷移はth07同様、BGMトラック切り替えの直前に起きる。加えて**th08では
  ステージ境界に`th08.dat`のアセットロードバーストが出る**(2面で725KB、3面で912KB)。
  この点はth07(起動時にまとめて読み込む作りで、ステージ境界にバーストが出ない)と
  異なる

### th08固有の問題1: 1面のマーカーが取れない

th08のステージ番号変数は**メニュー表示中から既に0(=1面相当)**になっており、リプレイ
開始時に「値の変化」が起きないため、ポーリングでは1面のマーカーが出ない。

代わりに、メニュー中も含めて何度も変化する別の候補(`th08.exe+0x000cbcbc`)を使う案も
試したが、メニュー操作中に3回も変化してしまい誤マーカーの原因になるため不採用とした。

採用した解決策は、**MODのメニュー自動操作スレッドが、リプレイ再生を開始する最後の
Enterを押した直後に補助マーカーを出す**方式(`LogReplayStartMarker()`)。実測では
最後のEnterからステージ番号変数が実際に動き出すまで**th07で43ms、th08で35ms**しか
なく、1面の開始時刻として使って差し支えない精度である。`scripts/25`側は、ステージ番号
変数から1面のマーカーが取れているゲーム(th07)ではそちらを優先する。

### th08固有の問題2: 内部ステージIDが飛び番

th08は4面A/4面B・Final A/Finalの分岐があるため、ステージ番号変数の値は**連番では
ない**。実測した`th8_06.rpy`(Normal・幽々子)では`0, 1, 2, 4, 5, 7`(`stageBase=1`
適用後は`1, 2, 3, 5, 6, 8`)と観測され、内部IDをそのまま「N面」と表示すると
4面が「5面」、6面が「8面」になってしまった。

対策として、**表示上の「N面」は内部IDではなく出現順で振る**ようにした。内部IDは
`stage_id`としてJSONに残してある。

なお、観測値から内部IDの割り当ては`0=1面, 1=2面, 2=3面, 3=4面A, 4=4面B, 5=5面,
6=Final A, 7=Final`と推測されるが、今回のリプレイが通っていない3・6は未確認のため、
ID→表示名の対応表は作っていない。**Extraステージやスペルプラクティスなど、出現順の
連番が適切でないリプレイ種別への対応も未実装**。

### th08のフル尺録画結果

| ステージ | ユーザー実測 | 自動出力 | 差 |
|---|---|---|---|
| 1面 | 00:05 | 00:04 | -1s |
| 2面 | 03:01 | 03:00 | -1s |
| 3面 | 06:44 | 06:43 | -1s |
| 4面 | 11:37 | 11:35 | -2s |
| 5面 | 17:48 | 17:46 | -2s |
| 6面 | 23:48 | 23:46 | -2s |

**全ステージ±2秒以内**。1面のみ`replay_start`(最後のEnterの時刻)由来で、他は
ステージ番号変数由来。一貫して1〜2秒早いのは、1面の基準が「Enterを押した瞬間」で
実際の画面表示より僅かに早いことと、実効fpsの微差の累積による。

### th08固有の問題3: 診断フックのメモリスキャンでフリーズ(原因特定・修正済み)

th08は`.data`が20.08MBあり、これをスキャン対象に含めると**リプレイ開始と同時にゲームが
フリーズ**した(IOフックを切っても再現、`.data`を除外すると再現しない、と切り分け済み)。

th07(`.data` 14.79MB)では起きなかったことから、単なるサイズ・負荷の問題ではなく、
**th08の`.data`内に、リプレイ開始時に読み出せなくなるページが含まれている**と判断した。

対策として、スキャン対象を**1MBのチャンクに分割**し、各スキャンパスの直前に
`VirtualQuery`でそのチャンクが今も`MEM_COMMIT`かつ書き込み可能かを確認して、条件を
満たさないチャンクをスキップするようにした。これでth08でも32MB(exeイメージ21チャンクを
含む)をスキャンしながら60Hz安定を維持できるようになった。

## th20への横展開: ステージ番号変数が使えず、ファイルI/O方式に切り替えた

th20(TH10以降のエンジン)は、**ステージ番号変数をポーリングする方式が採れなかった**。

### 理由1: `.data`が小さくステージ番号は静的変数にない

th20.exeのセクション構成は`.text` 1.4MB / `.rdata` 0.26MB / **`.data` 0.217MB**で、
th07(14.8MB)・th08(20.1MB)のように巨大な静的領域を持たない。TH10以降のエンジンは
ゲーム状態をヒープ上の管理構造体に置いており、**アドレスが実行ごとに変わるためRVA
直指定ができない**。

### 理由2: 差分メモリスキャン自体がth20をフリーズさせる

ヒープ側の候補を探すため88MBをスキャン対象にしてプローブを走らせたところ、
**ちょうど2面のロードが始まった瞬間(t=03:18)にth20がフリーズ**した。th08で入れた
チャンク分割+`VirtualQuery`による到達可能性チェックでも防げなかった。ステージ遷移では
ヒープが大きく再構成されるため、`VirtualQuery`とその直後の読み出しの間で領域が解放
される競合を完全には排除できない。

なお、IO観測のみ(`STAGE_PROBE_MEM=0`)にすると同じリプレイを520秒間フリーズなしで
完走できたため、**原因がメモリスキャンであることは切り分け済み**。またこれは診断用
ツールの制約であって、本番のマーカーフックには影響しない。

### 採用した方式: アセットロードバーストの検出

th20のIO観測では、**ステージ開始のたびに`th20.dat`から5〜7MBを10回前後の読み出しで
一気に取り込むバースト**が発生することがわかった。BGM切り替えは1ステージあたり2回
(道中曲・ボス曲)起きるので単独では使えないが、**アセットロードのバーストは
ステージ開始時にしか起きない**ため一意に判定できる。

| 事象 | `th20.dat`バースト | BGM切り替え | ユーザー実測 |
|---|---|---|---|
| 1面 | 00:15.29 (7.43MB / 12 reads) | 00:16.54 | 00:15 |
| 2面 | 03:18.30 (5.41MB / 10 reads) | 03:19.81 | 03:18 |
| 2面ボス曲 | — | 05:44.21 | — |
| 3面 | 07:03.46 (6.49MB / 9 reads) | 07:04.97 | 07:01 |

バーストの**先頭の読み出し**の時刻がユーザーの目視値と最もよく一致する
(1面・2面は誤差0秒、3面で+2.5秒)。

これを`mods/common/stage_marker_io.*`として実装した。`CreateFileA/W`・`ReadFile`・
`CloseHandle`をIATフックし、対象アーカイブへの読み出しが閾値(既定1MB)を超えて
一定時間(既定500ms)途切れたらバースト完了として1行出力する。

```
StageMarker: stage_load file=th20.dat bytes=5407503 reads=10 frame=11824 epoch_ms=...
```

ゲーム起動時にも巨大なバースト(実測20MB)が出るため、メニュー自動操作がリプレイ
選択の直前で`ArmStageMarkerIo()`を呼ぶまでは検出を無効にしてある。

### th20のフル尺録画結果と、処理落ちによるズレの定量化

`th20_01.rpy`をフル尺録画(1774.6秒、画面静止検知で自然終了、重複フレーム率1.7%)し、
6ステージすべてでアセットロードバースト(5.1〜9.7MB)を1回ずつ検出できた。

ユーザーの事前指摘どおり、**等倍録画のth20はローカルでは処理落ちし、実時間ベースでは
ユーザー提供値から徐々にズレていく**。ただし、検出したマーカーのフレーム番号を
ゲーム内時間(フレーム数÷60)に換算すると、**ユーザー実測とほぼ完全に一致する**:

| 面 | 今回の実時間 | ユーザー実測 | 実時間差 | 今回のゲーム内時間換算 | ゲーム内差 |
|---|---|---|---|---|---|
| 1面 | 00:14 | 00:15 | -1s | 00:14.0 | ±0.0s |
| 2面 | 03:19 | 03:18 | +1s | 03:16.5 | -0.5s |
| 3面 | 07:09 | 07:01 | +8s | 06:59.8 | -0.2s |
| 4面 | 11:55 | 11:39 | +16s | 11:36.1 | -1.9s |
| 5面 | 17:26 | 16:55 | +31s | 16:51.5 | -2.5s |
| 6面 | 22:23 | 21:30 | **+53s** | 21:23.8 | **-5.2s** |

つまり**検出そのものは正確で、実時間のズレは全て「今回のローカル録画で実際に落ちた
フレーム」で説明できる**(6面までの累積で約59秒ぶんのフレーム落ち)。

このことは同時に、**チャプターの正しさは録画環境の性能に直結する**ことも意味する。
生成されるタイムスタンプは「その動画の実際の時刻」なので動画としては常に正しいが、
処理落ちした録画では動画自体がユーザーの手元にある別録画とは違う進行になる。th20を
本番運用する際は、フェーズ46の結論どおり`.4xlarge`帯を使うか、フェーズ47の
スローモーション録画+等倍化を使うことで処理落ちを避ける必要がある。

### この方式の副次的な利点と限界

th08でも同じバースト(2面725KB・3面912KB)が観測されており、**この方式はth08にも
適用できる**(th08はステージ番号変数方式で足りているので切り替えていない)。一方
**th07はアセットを起動時にまとめて読み込む作りで、ステージ境界にバーストが出ない**
ため、この方式は使えない。つまり2方式は相互補完の関係にある。

| タイトル | ステージ番号変数 | アセットロードバースト | 採用方式 |
|---|---|---|---|
| th07 | あり(`+0x0022583c`) | **出ない** | 変数 |
| th08 | あり(`+0x000e4850`) | あり(0.7〜0.9MB) | 変数 |
| th20 | **静的変数にない** | あり(5〜7MB) | バースト |

## 追加調査: 弾幕パターン(通常弾幕・スペルカード)の開始時刻(th07)

ユーザーからの追加要望「各ボスの通常弾幕やスペルカードの開始タイミングも取りたい」に
対する調査。**th07で実現し、ユーザー提供の目視実測値と全8イベントで±1秒以内の一致を
確認した**(名前の解決を除く)。

### 決め手になった変数

差分メモリスキャンに**カウンタ反転検出モード**(`STAGE_PROBE_COUNTER=1`)を追加した。
4バイト値ごとに「直近の変化方向」と「その方向が何スキャン続いたか」を保持し、一定期間
同方向に動き続けた値が反転した瞬間だけを記録する。弾幕パターンの制限時間タイマーの
ように「カウントダウンし、パターンが変わるとリセットされる」変数を狙い撃ちできる。

これで2つの変数を特定した:

| 用途 | RVA | 内容 |
|---|---|---|
| パターン開始 | `th07.exe+0x00095bec` | 弾幕パターンの制限時間(秒)。パターン開始のたびにリセット |
| スペル判別 | `th07.exe+0x005ac82b` | スペルカード発動中フラグ(1バイト) |

制限時間変数は、**リセット値と次のリセット時の残り値が秒単位で完全に整合する**ことで
裏付けた(例: 中ボススペルは制限37秒で開始し17.4秒後に撃破 → 次のリセット時の残りが
20秒。37−17.4=19.6≒20)。

### 実装と検出ルール

`InstallPatternMarkerHook()`(制限時間の**増加**=リセットを検出)と
`InstallSpellFlagMarkerHook()`(フラグの変化を検出)を`mods/common/stage_marker_hook.*`に
追加し、それぞれ5ms間隔でポーリングする。カウントダウン中は単調減少なので、増加は
必ずリセットを意味する。

`scripts/25`側(`parse_boss_patterns()` / `label_boss_patterns()`)の判定ルール:

| ログ | 判定 |
|---|---|
| `pattern`行 + ほぼ同時(実測2ms差)に`spell flag=1` | スペルカード開始 |
| `pattern`行のみ | 通常弾幕開始 |
| `pattern`行を伴わない`spell flag=0` | ボス撃破(スペルカード中に撃破) |

「中ボス/ボス」の区別はステージ内の撃破イベントで分割し(1つ目の撃破までが中ボス)、
「通常N」「スペルカードN」の番号は種別ごとに出現順で振る。

### 未解決・未対応

- **スペルカードの名前(「霜符「フロストコラムス」」等)は取得できていない**。

  対応表を別途用意する必要がある(名前自体はth07.dat内にあるはずだが未調査)
- **th07以外は未対応**。RVAはタイトル・ゲームデータのバージョン固有のため、
  タイトルごとに同じ手順(カウンタ反転検出モードでの特定)が必要
- 中ボスがスペルカードを持たない場合や、ボスが通常弾幕で撃破された場合など、
  th07 1面以外のパターン構成での検証は未実施。「中ボス/ボス」の分割ロジックも

- **フル尺録画での通し検証は未実施**(1面での検証のみ)

### 調査中に踏んだ落とし穴

診断ログを緩い条件(`STAGE_PROBE_STRICT=0`)で出すと、210秒の実行でログが188MBに達し、
**そのログI/O負荷でゲーム自体が実時間比で10倍以上遅くなった**。この状態のログは
イベント時刻がまったく別物になるため相関分析に使えず、最初はこれに気づかず候補を
探して空振りしていた。診断ログの量は「ゲームの進行を歪めない範囲」に収める必要がある
(カウンタ反転検出モードは同じ210秒で880KBに収まる)。

## 他タイトルへの横展開について

th07で確立した手順は次の通りで、そのまま他タイトルに適用できる:

1. `STAGE_PROBE=1`で`scripts/49_stage_probe_run.py`を実行し、ステージ遷移を2回以上
   含む長さ(概ね8〜10分)のログを取る
2. `scripts/49_stage_probe_analyze.py`で、複数の遷移時刻すべてで同時に、かつ連続した
   値(`1->2`, `2->3`)に推移した静的変数を絞り込む
3. 得られたRVAを`InstallStageMarkerHook()`に渡してビルドし、実機で`StageMarker`行が
   正しいフレームで出ることを確認する

ステージ番号変数が見つからない、あるいは差分スキャン自体が動かないタイトル
(th20が該当)では、代わりにアセットロードバーストを使う(上記th20の節を参照)。

**留意点**:

- 「TH10以降のエンジンではステージ番号がヒープにある」という懸念はth20で現実の
  ものとなった。**th11も同じエンジン系のため、同様にファイルI/O方式が必要になる
  可能性が高い**(th11は未検証)
- RVAはゲームデータのバージョン固有(`fps_display_hook`の`kTargetRva`と同じ性質)。
  ゲームデータが更新された場合は再特定が必要
- アセットロードのバイト数閾値(th20は1MB)も、ゲームごとに実測して決める必要がある

## 実装上ハマった点

### 診断フックのメモリスキャンでゲームが事実上フリーズした

初回実装(スキャン上限64MB・1領域あたりのサイズ無制限)では、リプレイ開始と同時に
th07が応答しなくなった(プロセスは生存、CPU約9%で進行しない)。巨大な`MEM_PRIVATE`
領域にはwined3d/llvmpipeのフレームバッファ等、読み出し自体が極端に遅いメモリが含まれる
ためと考えられる。

**1領域あたり4MB以下・合計16MBまでに制限**したところ、1スキャンあたり3〜4msで完了し、
ゲームへの影響も観測されなくなった。th07.exeの書き込み可能イメージ領域は約14.8MBあり、
ステージ番号のような制御変数はここに収まるので、この制限で実用上問題ない。

### ログ出力のスループット

ステージ遷移の瞬間は大量のメモリが再初期化されるため、2秒間に4万行以上のログが出る
ことがある(ログのタイムスタンプが実際の観測時刻より数秒遅れる)。解析はログ行に
埋め込んだ`t=`を使うので問題ないが、診断フックを長時間動かすとログが数十MBになる
(今回の9分20秒で33.7MiB)。
