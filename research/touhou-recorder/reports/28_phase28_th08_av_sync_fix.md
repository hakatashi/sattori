# フェーズ28: th08 AWS録画の音ズレ問題の根本原因特定と修正

日付: 2026-07-23

## 背景

フェーズ27追補3で、AWS `c7i.xlarge`でのth08フル尺録画(`runs/th08_c7i_xlarge_full/video.mp4`)をユーザーが視聴したところ、**音声が映像よりも約700ms先行する明確な音ズレ**が発覚した。フェーズ26の「音声分離+後mux」方式は重複フレーム率の問題は解決したが、A/V同期の絶対オフセットまでは検証していなかった(尺の差が8msという確認は、ドリフトが無いことの確認に過ぎなかった)。本フェーズでは、この音ズレの根本原因をローカル環境で定量的に特定し、修正を実装した。

## 原因調査

### 仮説

`scripts/23`・`scripts/25`の`attempt_recording()`は、映像用ffmpeg(`x11grab`)を`Popen()`した直後に音声用ffmpeg(`pulse`)を`Popen()`するが、両者が実際にキャプチャを開始するまでの内部初期化レイテンシは異なりうる。mux時(`ffmpeg -c copy -shortest`)は両ストリームの開始タイミングのズレを一切補正しないため、レイテンシ差がそのまま音ズレとして焼き付く可能性がある。

### 検証1: フラッシュ+ビープによる直接計測

ローカルXvfb(`:77`)上で本番コードと同じPopen順序(映像→音声)を再現し、録画開始4秒後に画面を黒→白に切り替える(`xsetroot`)と同時にビープ音を再生(`paplay`)するテストハーネスを作成した。生成された動画を解析した結果:

- 映像ストリーム内でのフラッシュ検出時刻: 3.95s
- 音声ストリーム内でのビープ検出時刻: 2.726s(`silencedetect`)

**ズレ = 3.95 - 2.726 = 1.224秒。音声が映像より約1.2秒先行しており、AWSで報告された約700msの音ズレと同方向・同オーダーの現象をローカルでも再現できた。**

### 検証2: 起動レイテンシの直接測定

`ffmpeg -f pulse -i auto_null.monitor -t 3`を単独実行したところ、壁時計上4.39秒かかったにもかかわらず、得られた音声の長さは2.27秒しかなかった。**pulse入力は起動から実際にサンプルを取り込み始めるまでに1〜2秒程度のレイテンシがある**ことが分かった(`auto_null`シンクを事前に`RUNNING`状態にしておいても改善は限定的。`-fragment_size`の調整も効果なし)。一方、x11grabは起動後ほぼ即座(0.05秒未満)にフレームの取り込みを開始する。この非対称性がズレの直接の原因である。

### 検証3: `-copyts`による絶対時刻の可視化

ffmpegのx11grab・pulseはいずれもデフォルトでwallclock(実時刻)ベースの内部pts(`-wallclock`オプション、pulseはデフォルト有効)を使用しているが、通常のエンコード・muxではこの情報が失われ、各ファイルの`start_time`は0に正規化される。録画コマンドに`-copyts`を追加したところ、出力ファイルのメタデータに実際のepoch秒がそのまま残ることを確認した:

```
x11grab出力: start_time=1784765161.591758
pulse出力:   start_time=1784765162.984179
差分: 1.392421秒
```

この差分を使って音声側に`-itsoffset`を与えてmuxしたところ、フラッシュ/ビープ双方の検出時刻がほぼ一致(3.970s vs 3.980s、10ms程度の誤差は検出フィルタの粒度によるもの)し、**音ズレが解消することを確認した**。

## 修正内容

`scripts/25_record_replay_e2e_multigame.py`・`scripts/23_record_th08_ver100d_replay_e2e.py`の`separate_audio`(音声分離)経路を修正:

1. 映像用・音声用ffmpegの両方に`-copyts`を追加し、実際の絶対キャプチャ開始時刻(wallclockベースのepoch秒)を出力ファイルの`start_time`として保持する
2. 録画停止後、mux前に両ファイルの`start_time`を`ffprobe`で取得し、差分(`delta = audio_start - video_start`)を計算
3. 遅く始まった側に`-itsoffset delta`を与えてmuxすることで、実測した差分を自動補正する(ハードコードされた定数(700ms等)は使わず、毎回実測する方式)

この方式は環境(ローカル/AWS、インスタンスタイプ)ごとに実際の起動レイテンシが変動しても、録画ごとに正しく自動補正される。

## 実機検証

ローカル環境でth08(ver1.00d)を`scripts/25`(`--record-seconds 90`)で録画し、修正が実際に機能することを確認した。

```
A/V同期補正: video_start=1784765442.643 audio_start=1784765443.231 delta=+0.588s
mux実行: ffmpeg -y -i video.video.mp4 -itsoffset 0.588000 -i video.audio.m4a -c copy -shortest video.mp4
[RESULT] 総録画=96.1s 計測区間=15..91s 重複フレーム率=1.8%
```

このローカル環境では実測ズレは0.588秒で、これが自動検出・補正された。重複フレーム率1.8%も既存の良好な水準を維持しており、`-copyts`追加による録画品質(重複フレーム率)への悪影響は無いことも確認できた。動画は`runs/th08_avsync_fix_local_test/video.mp4`に配置し、ユーザーに目視確認を依頼した。

## 今後の課題

- 本フェーズの検証はローカル環境のみ。**AWS環境での修正版の実機検証(フル尺録画を含む)がまだ残っている**。ローカルとAWSで起動レイテンシの絶対値は異なりうるが(ローカル0.6〜1.4秒 vs AWS報告値約700ms)、補正ロジック自体は実測ベースなので環境差を自動的に吸収できるはずである
- `--muxed-audio`(単一プロセス音声取り込み)経路には今回の修正を適用していない(この経路はAWSでth08の重複フレーム率を悪化させるため非推奨のまま)
- ユーザーによる`runs/th08_avsync_fix_local_test/video.mp4`の目視確認結果待ち
