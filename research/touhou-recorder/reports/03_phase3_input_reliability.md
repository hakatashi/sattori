# フェーズ3: メニュー自動操作(xdotool)の信頼性に関する調査

日付: 2026-07-14

## 背景

th07をXvfb上で起動し、タイトルメニューから「Replay」を選択して実際の.rpyファイルを再生させる自動操作を構築しようとした。

## 分かったこと

### 1. Xvfbにはウィンドウマネージャが無いとxdotoolの`windowactivate`が機能しない

- 素のXvfbには`_NET_ACTIVE_WINDOW`等のEWMHをサポートするWMが存在せず、`xdotool windowactivate`が「Your windowmanager claims not to support _NET_ACTIVE_WINDOW」で失敗する
- 軽量WM `openbox --sm-disable` をXvfb上で起動することで解決した(`sudo apt-get install openbox`で導入)

### 2. キー入力の到達自体は可能だが、単発のキー送信の信頼性が低い

openbox導入後、`xdotool key`/`keydown`+`keyup`でタイトルメニューのカーソルを動かせることは確認できた(スクリーンショットで「Replay」项目まで到達させることに複数回成功している)。しかし以下の不可解な現象が再現性をもって観測された:

- **同じ「Down」キー送信でも、保持時間(100ms/300ms/1000ms等)や実行タイミングによって、移動量が0/1/2/3項目とばらつく**(押しっぱなしによるキーリピートと、ゲーム側のフレームポーリングに送信タイミングが合わないことによる取りこぼしの両方が混在していると考えられる)
- **「Up」キーが期待通りに逆方向へ移動したことは一度もなく、常に「Down」と同じ方向(またはノーモーション)としてしか観測されなかった**
- **決定キーとして試した「z」「Return」「space」のいずれも、メニュー項目の選択を確定させる代わりに、カーソルを(Downと同じ方向に)動かしてしまう現象が複数回再現した**
- 現在のXキーマップ自体は`xmodmap -pke`で確認する限り標準的(Up=111, Down=116, Return=36, Escape=9 とすべて別々の妥当なキーコード)であり、**xdotoolによる動的キーコード割り当ての衝突が原因ではない**ことは確認済み。したがって問題はWine側のキーボード状態取得(DirectInput/XQueryKeymapのポーリングタイミング)にあると推測されるが、根本原因は未特定
- また、タイトル画面はアイドル状態が数秒続くと自動でアトラクトモードのデモ再生に遷移する仕様があり、これが上記のキー入力デバッグを難しくする要因にもなっていた(操作の合間に勝手にデモへ遷移してしまうことがある)

### 3. 現状のステータス

th07のタイトルメニューで「Replay」項目にカーソルを合わせることは複数回再現できたが、**決定キーでの確定に至らず、実際のリプレイファイル一覧画面への遷移はまだ確認できていない**。これは実装上の障害であり、東方の描画・fps・録画そのものが機能しない、という話ではない(フェーズ2で示した通り、描画・fps・録画自体は健全)。

## 示唆

- 単発のxdotoolキー送信を都度検証なしに信頼して連続実行するスクリプトは、現状では信頼性が低い。「送信→スクリーンショットで確認→未達なら再送」という**視覚フィードバックループ**を前提にした設計にする必要がある
- より根本的には、xdotoolのプロセス起動オーバーヘッド・X接続の張り直しを避けるため、persistent(常駐)なX接続を1つ保持して`XTestFakeKeyEvent`を送り続ける専用ツール(例: python-xlibベースの小スクリプト)に置き換えた方が信頼性が上がる可能性が高い
- th07.cfgはユーザーの実際の設定ファイルをそのまま使っており、キーバインドがカスタマイズされている可能性も完全には排除できていない(バイナリを軽く確認したが、フォーマットが不明なため断定はできず)
