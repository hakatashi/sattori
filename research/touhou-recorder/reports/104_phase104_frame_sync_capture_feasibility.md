# フェーズ104: フレーム同期キャプチャ(可変速・非リアルタイム録画)の実現可能性の検討

日付: 2026-11-16

## 結論

**実現可能と判断した。** ゲームを実時間で動かして別プロセスで取り込む現行方式をやめ、ゲームの1フレームの描画・取り込みが終わりしだい次のフレームへ進める方式(動画編集ソフトのレンダリングと同じ考え方)は、既存のフックの延長で作れる。最大の作業は音声。本レポートは既存のレポート・コードを読んだうえでの机上検討で、実験はしていない(映像のみのPoCはフェーズ105で行う)。

## 背景

これまでの録画はすべて「ゲームは実時間(またはその定数倍)で動き、x11grabが一定周期で画面を取り込む」前提だった。このため、

- 描画が重い場面でゲームが目標Hzに届かず、進行が遅くなる(理論尺の超過)・取り込みが同じフレームを重複して拾う
- 最も重い場面に合わせて録画速度とインスタンスタイプを決めるので、軽い場面ではCPUが余る
- 3倍速以上ではx11grabそのものが律速になる(reports/89)

という問題が続いていた。ユーザーの提案は、ゲーム側の処理と取り込みを律速にして可変速で動かすこと。軽い場面は速く、重い場面は遅く進み、取り込みはフレーム単位で確実に行う。

## 成立すると考える根拠

| 根拠 | 出典 |
|---|---|
| ゲームの進行は実時間に依存しない。1/3倍速〜4倍速まで時間を偽装してもスコアが一致する | reports/85, 89, 91, 103 |
| 描画が追いつかないとき、ゲームは描画を飛ばさず進行ごと遅くなる(th20は描画とロジック更新が直結。重い場面では理論尺が伸びる)。`Present`を止めればゲームも止まる | reports/46, 47, 67 |
| `Present`フック・タイマー偽装・DirectSound/WASAPIフックが既にある | `mods/common/fps_limiter_hook.cpp`、`speed_hack_hook.cpp`、`dsound_hook.cpp`、`wasapi_hook.cpp` |
| 手法そのものは確立している(デモ録画のkkapture、TAS用のHourglass・libTAS、各種エミュレータのフレームダンプ) | 検討者の記憶に基づく。Wine上での動作は未確認で、これらのツール自体は使わない |

## 構成案

1. **仮想時計**: 現行の`speed_hack_hook`は「実時間×倍率」を返す。これを、実時間と無関係にゲームのメインスレッドの呼び出しに応じて進む時計に替える。QPC・`timeGetTime`・`GetTickCount`は仮想時刻を返し、`Sleep(n)`は仮想時刻をnミリ秒進めて即座に戻る。ゲーム内蔵のウェイト(th15はQPCのポーリング、reports/85)は実時間を消費せずに抜け、ゲームから見た1フレームは常に約1/60秒になる。fps表示は補正なしで60前後になる見込み(チェックリスト項目10が不要になる)。
2. **フレーム同期キャプチャ**: `Present`フック内でバックバッファを読み出し(D3D9は`GetBackBuffer`→`GetRenderTargetData`)、パイプ経由でffmpegの`rawvideo`入力へ書く。パイプが詰まれば書き込みがブロックするので、描画とエンコードの遅いほうが自然に律速になる。x11grabは使わない。
3. **音声**: ゲームが可変速で進むと、PulseAudioで録る現行方式は使えない。
   - **案A(推奨)**: MOD内に仮想の音声デバイスを持つ。DirectSoundを自前実装に差し替え、1フレームごとに735サンプル(44100÷60)だけミックスしてファイルへ書く。効果音はフレーム単位で正確に合い、同期マーカー(reports/88)も不要になる。難所はBGMのストリーミングで、再生位置と通知イベントを仮想時計で進め、補充スレッドが書き終えるまでフレームを待たせる必要がある。th06ncはWASAPIなので別実装。
   - **案B**: 2パス。映像は可変速で録り、音声は描画を無効にした別の実行で既存の方式(倍速可)で録って合わせる。音声の作り込みは不要だが、ロード区間の長さがパス間で違うため区間ごとの位置合わせが必要で、厳密には合わない。

## 課題

| 課題 | 深刻度 | 対処の方向 |
|---|---|---|
| 音声が実時間で流れる | 大 | 上記の案A・案B |
| 実時間で進む区間が残る(ロードスレッド、BGM開始の遅れ。reports/89 §6) | 中 | メインスレッドで同期的に行うロードは動画から消えるだけで無害。ロード中もアニメーションを描くタイトルでは、ロード画面が動画上で何倍にも伸びるので、ロードスレッドの生存中は進行を止めるか等速に落とす |
| MODのメニュー操作が`Sleep`基準(`ScaledSleep`) | 小 | フレーム数基準に書き換える。reports/99 §6のベンチで4倍速時にキーが連打扱いになり空振りしたのと同じ問題 |
| 終了検知・各種タイムアウトが実時間基準 | 小 | パイプを流れるフレーム列に対してフレーム数基準で判定する |
| vpatch・thpracなど外部DLLの時計 | 中 | exeのIATフックでは届かないので、kernel32側のインラインフックが要る |
| 描画API別の読み出し実装(D3D8 / D3D9 / D3D11) | 中 | 3種類を書く。D3D9が最も多い |
| fps暴走検知・処理落ち早期検知 | 小 | この方式では無効にする(FpsMonitorは数百Hzを示すのが正常になる) |

## 効果の見積もり

- **品質**: 判定基準(AGENTS.md)の①落ちフレーム率・②FpsMonitor・③理論尺は構造的に満たされる。統計的な判定の代わりに「`Present`回数=書き出したフレーム数」という厳密な検査になり、処理落ちによるリトライも無くなる。
- **費用**: 最も重い場面ではなく平均で録画時間が決まる。th15 Extraはローカル機(Ryzen 7 5700X、16スレッド)で最低24.6Hzまで落ちるため等倍では録れず1/3倍速相当が必要だが、上限を外したベンチの平均は約100Hz(reports/99 §1、240Hz上限・30fpsのx11grab込み)。単純計算で約5倍の処理量だが、全フレームの読み出しとエンコードを含む実測ではないので目安。
- **運用**: Spotの性能ぶれ・サーマルスロットリング(reports/51)・並列実行は「遅くなるだけ」で品質に響かなくなる。並列2本の上限(AGENTS.md)を外せる可能性がある。
- **CPUの使い切り**: 完全には使い切れない。描画律速のときでも全体の使用率は1600%中1100〜1250%(reports/99 §2)。残りは並列実行で埋める。

## 進め方

1. **映像のみのPoC**(フェーズ105): th15(D3D9・QPCポーリング)で仮想時計とバックバッファ読み出しを実装する。スコア一致、`Present`回数と動画のフレーム数の一致、平均処理速度を測る。速度が出なければここで撤退できる。
2. **音声の事前調査**: DirectSoundの呼び出しを記録するプローブで、各タイトルのBGMストリーミングの方式(通知イベントか再生位置のポーリングか)を確認し、案Aの規模を確定する。
3. 案Aの実装、他タイトルへの展開、クラウド検証。

既存方式とは設定で併存させ、タイトル単位で切り替えられるようにする。
