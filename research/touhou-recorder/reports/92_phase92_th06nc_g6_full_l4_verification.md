日付: 2026-11-05(検証は2026-11-04 14:01〜19:27 UTC)

## 結論

1. **`g6.2xlarge`は`g6f.2xlarge`のフォールバック先として使える。AMI変更は不要。** 本番AMI `<AMI_ID>`と本番イメージ`sattori-worker-gpu:latest`がそのまま動いた(Pass-Through、`Licensed`、Xorg・DXVK・NVENCとも正常)。全15録画が完走し、記録スコアと一致した。
2. **【本検証の最大の発見。g6固有ではない】現行の配信版変換はth06ncの倍速録画を約45fpsへ落とす。** sattoriの`30874c1`(2026-10-04)で等倍化が`-r 60`から`fps=60:start_time=0`へ変わった影響で、ユニークフレームが全区間で約45/秒、落ち約25%になる。**`g6f`の生映像でも同じ**(現行45.08 / `-r 60` 59.9)。パイプラインの重複率は生映像を見るので0.1%のままで、検知されない。`-r 60`に戻すと59/秒以上に戻る。
3. **修正後の品質はg6fと同等**。推奨は下表。3倍速はユーザーの視聴確認で判断する。

## 4. 配信版が45fpsになる問題

### 現象

配信版の`scripts/81`が全倍速条件で実効約45fps、落ち約25%(0.53秒ごとに約8フレーム)。`mpdecimate`後のフレーム間隔は1:2が2:1で並ぶ規則的なパターン(4フレームに1枚が重複)で、ゲーム負荷と無関係に全区間一様。

### 原因

x11grabの120fps取り込みのptsは等間隔ではなく、`16.7, 0.0, 8.3, 8.3ms`の周期で並ぶ(`-vsync 0`のまま記録される)。生映像の中身は120枚/秒すべて別の絵だが、`setpts=2*PTS`の後に`fps`フィルタを掛けると、同じ出力スロットへ複数枚が集まる箇所と空く箇所ができ、前者は捨てられ後者は複製される。出力オプションの`-r 60`はフレームの順序を保って詰めるので起きない。

同じ生映像(スモークのExtra 2倍速、20秒地点から30秒間)の比較:

| 方式 | ユニークフレーム/秒 | 間隔の分布(1枚, 2枚, …) |
|---|---|---|
| 現行 `setpts=2*PTS,fps=60:start_time=0` | 45.10 | 1812, 892 |
| `fps=60:round=down` | 45.11 | 1813, 891 |
| `fps=120`を前置 | 45.11 | 1813, 891 |
| **`setpts=2*PTS` + `-r 60`** | **59.95** | 3594, 2 |
| `-r 60 -vsync cfr` | 59.93 | 3594, 2 |
| g6fの生映像(`sattori-speedup-e2e/raw/th06nc_2x.mp4`)に現行方式 | 45.08 | 1810, 892 |
| 同 `-r 60` | 59.90 | 3588, 7 |

`git log`で確認: `91a7907`以前は`-r 60`、`30874c1`(2026-10-04、配信版カットのIssue #266)で`fps`フィルタへ変更。`30874c1`より前に作られたg6fの配信版(`sattori-speedup-e2e/videos/th06nc_2x.mp4`、`reports/89`の復元)は実効60fps。

### 影響範囲(一部のみ測定)

`/mnt/cache3/sattori-266-verify/`の`30874c1`相当の配信版で測定:

| 動画 | ユニークフレーム/秒 |
|---|---|
| th07 3倍速 | 43.6 |
| th06 4倍速 | 33.9(4倍速のキャプチャ律速を含む可能性あり) |
| **th12 2倍速** | **59.9(低下なし)** |
| th06nc 等倍、th20 等倍 | 60.0(低下なし) |

**タイトル・倍率によって出方が違い、原因の出し分けは未調査。** 本番で2026-10-04以降に作られた倍速の配信版は影響を受けている可能性がある。残りのタイトルは未測定。パイプラインの重複率は生映像を検査するので検出できない。

- **issue #5(最速の速度の表)は、この修正の後で測るか、配信版のユニークフレームで評価すること。** 重複率だけで判断すると45fpsを「実用品質」と誤判定する。
- reports/91の「40Hzの落ち16.6〜18.3%(60fpsキャプチャ)」も`fps`フィルタが関わる可能性がある(未検証)。

### 修正の扱い

**sattori側の変更なので本検証では修正していない(hakatashi/sattori-dev#322)。** `scripts/92_reconvert_r60.py`(`-r 60`へ置換)の結果は、尺・フレーム数・先頭0秒とも現行と一致(92776→92777フレーム、映像・音声とも`start_time=0`)。ファイルサイズは720p 2倍速で+17%、1080p 2倍速で+14%(CQ固定でユニークフレームが増えるため)。

**`-r 60`は`fps=...:start_time=0`のIssue #301対策(先頭を0秒から埋める)を置き換えられるかを網羅的には確認していない。** `th6_20`で先頭0秒は確認したが、mux時に映像を後ろへずらす録画でマーカー検証はしていない(マーカーはカットで配信版から外れる)。修正時は#301の再確認とA/V同期の確認が要る。

- 中央値133秒、最大140秒。本番`g6f`の中央値147秒(起動から録画開始。定義が少し違う)と同程度。**約20分の遅延は5回では再現せず、原因は不明のまま。** 発生時にコンソール出力を取る処理(`scripts/92_boot_timing_cycle.sh`)は使われなかった。

- 終了(`terminate-instances`→`terminated`)は各台約6〜7分。Issueの注記どおり。**終了待ちの間はクォータ(32vCPU)を占有する。**
- `th6_01`・`th6_20`の配信版の尺はframeCount/60より短い(-4〜-42秒)。`th6_33`は長い(+7〜+25秒)。既存の理論尺の傾向に沿うが、録画速度で最大18秒ぶれており、終了検知の待ち(実時間)が倍速では短いためと考えられる(未検証)。

- **配信版末尾の静止区間**: th06ncは終了検知の待ち(実時間16秒)のぶん、配信版の最後に最大約18秒、リプレイ一覧が残る。短いリプレイの実効fps評価を歪めるので、評価時は末尾を除くこと。

## 8.1 3倍速で落ちが激しい区間(`lunatic_720p_3x_delivery_r60.mp4`)
