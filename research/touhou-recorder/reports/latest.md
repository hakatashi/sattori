# 引き継ぎレポート: 東方リプレイ録画PoC 完了 → Webサービス開発への移行

日付: 2026-07-16

## このレポートの位置づけ

本リポジトリ(`touhou-recorder`)での概念実証(PoC)作業はここで一区切りとする。次のフェーズでは、ブラウザから東方のリプレイファイル(`.rpy`)をアップロードすると自動でキューイングされ録画される**Webサービス**の計画・実装に移る。ウェブサービス基盤(フロントエンド・API・キュー等)は未定だが、**録画バックエンドにはAWSを使う方針**が決まっている。

本レポートは、Webサービス開発を担当する次のエージェント(または人間)が読むべき**要点のみ**をまとめたものである。個別の検証経緯・実測データ・失敗した試行錯誤は各フェーズレポート(`reports/00〜19_*.md`)に記録されているので、実装時に疑問が生じたら該当レポートを参照すること。`AGENTS.md`の「常に注意すべきこと」も合わせて必読(Xvfb/Wine環境固有の複数の落とし穴が書かれている)。

## PoCで実証できたこと(結論)

**東方リプレイ→動画の自動生成パイプラインは、ローカル環境・AWS(EC2 Spot)環境の両方で実機動作を確認済み**であり、Webサービスの録画バックエンドとしてそのまま利用できる状態にある。

1. **録画エンジン**: Wine + Xvfb(ヘッドレス仮想ディスプレイ) + ffmpeg(x11grab)によるCPUのみ(GPU不要)の録画で、640x480/60fps安定動作を確認(th07・th08で実証、他タイトルは未検証)
2. **リプレイ自動再生**: DLLインジェクションMOD(DirectInputのvtableフック)によるメニュー自動操作で、`.rpy`ファイルを人手を介さず選択・再生開始できる(th07・th08向けに実装済み。技術詳細は`docs/touhou_menu_automation.md`)
3. **終了自動検知**: 画面の静止判定(直前フレームとのMAD)によりリプレイ終了を検知し、録画を自動停止(誤検知は解消済み、フェイルセーフのタイムアウトも設定済み)
4. **音声同期録画**: PulseAudioの`auto_null.monitor`をffmpegに渡すだけで映像と同期した音声キャプチャができる
5. **AWSへのデプロイ**: EC2 Spotインスタンス(コンテナ経由)でth07リプレイ全編(約14分)の録画→S3アップロード→CloudFront配信までEnd-to-Endで実機確認済み
6. **ウォーターマーク合成**: ffmpegの`overlay`フィルタで録画時にブランディング用ウォーターマークを合成する機能を実装・AWS実機でも品質劣化なしを確認済み

一方で、**Webサービス化に向けて未着手・要検討の項目も多い**(後述)。特に「他タイトルへの対応」「ジョブキューイングの実装」「本番運用時のインフラ自動化」はまだ手つかずである。

## 録画バックエンド: 現状の実装

### パイプライン本体

- `scripts/11_record_th07_replay_e2e.py` — 録画パイプラインの本体。単体実行可能なPythonスクリプトで、以下を一気通貫で行う:
  1. WINEPREFIX起動 → MODインジェクション → タイトル画面到達待ち(`WaitForStableWindow: stable`をMODログから検出)
  2. メニュー自動操作でリプレイファイル選択・再生開始
  3. `xwininfo`でウィンドウの実クライアント領域座標を取得しffmpeg録画開始(x11grab + pulse音声 + 任意でウォーターマーク合成)
  4. 静止画面検知(MAD閾値2.0、8回=16秒連続で終了判定、40分タイムアウトのフェイルセーフ)でffmpegを停止
  5. `--watermark <webmファイルパス>` / `--watermark-width <px>` でウォーターマーク合成を有効化(未指定なら無効、後方互換)
- `mods/th07_replay_autoplay/`, `mods/th08_replay_autoplay/`, `mods/common/` — DLLインジェクションMODのソース(Windows上でビルドが必要、`build.bat`参照)
- `assets/watermark/watermark-60fps.webm` — ウォーターマーク素材(VP9アルファ付き、デコードには`-c:v libvpx-vp9`の明示指定が必須。ffmpegデフォルトのVP9デコーダはアルファを無視する既知の罠)

### 対応タイトル(現状これだけ)

**th07(妖々夢)・th08(永夜抄)の2タイトルのみ**、リプレイ自動再生からE2E録画まで実証済み。他タイトルへの展開は**まだ何もできていない**。着手する場合の前提知識:

- th06はwined3dで原因不明のハングがあり検証未完(D3D8だがth07と挙動が異なる)
- th13以降はSteam DRM(`steamclient.dll`欠落)で即終了する問題があり、追加のファイル配置調査が必要
- th11・th14・th15・th20は起動検証すら未着手
- MOD移植先タイトルは事前に`.cfg`がウィンドウモード(フルスクリーンでない)であることを確認する必要がある(AGENTS.md参照)
- MODは「1件目のリプレイファイルを固定選択」する実装のため、**現状は録画対象のリプレイファイル1つだけをinstanceディレクトリに配置してから実行する運用**になっている。Webサービスではユーザーがアップロードした任意のファイル名のリプレイを再生する必要があり、この固定選択ロジックの改修(ファイル名指定 or リスト内の該当ファイルへのカーソル移動)が必須になる

### AWSインフラ

- `cloud/docker/aws/Dockerfile`, `cloud/docker/aws/entrypoint.py` — 録画ワーカーのコンテナイメージ(Amazon Linux系ではなくUbuntuベース、wine 9.0 + Xvfb + openbox + ffmpeg + pulseaudio + MS Gothicフォント + python3)。PulseAudio起動→録画スクリプト実行→S3アップロードの流れ
- `cloud/terraform/aws/main.tf` — S3出力バケット(7日ライフサイクル)・CloudFront(Origin Access Control経由の非公開配信)・IAMロール/インスタンスプロファイル・セキュリティグループを定義。**EC2インスタンス自体のリソース定義はあるが、terraform経由では作成しない運用にしている**(後述の既知の問題のため)
- 推奨インスタンスタイプ: **`c7i.xlarge`(4vCPU)**。同価格帯の`c6i.xlarge`より重複フレーム率(処理落ち指標)が低く価格も安い「フリーランチ」。品質最優先なら`c6i.2xlarge`(8vCPU、価格約2倍、重複フレーム率さらに改善)。`z1d.xlarge`(高クロック特化)は逆に悪化するので避ける
- **4 vCPUが実用上の下限**(2vCPUだと重複フレーム率が数十%に悪化し録画品質が崩れる)
- **既知の問題: `terraform apply`でSpot EC2インスタンス(IAMインスタンスプロファイル併用)を作成しようとすると、AWS側のSpotキャパシティ不足と組み合わさった際に`terraform-provider-aws`が無限にハングすることがある**(フェーズ16で発見、原因未特定)。回避策として**EC2インスタンス自体は`aws ec2 run-instances`をAWS CLI/SDKから直接呼ぶ**運用にしている。本番のジョブキューイング実装でも、インスタンス起動はterraformではなくAWS SDK(boto3等)から行うことを推奨する
- **複数AZにまたがるSpot Fleet(`request-spot-fleet`、`AllocationStrategy: lowestPrice`)で最安AZの自動選択・起動を実機確認済み**。単一AZでのキャパシティ不足・価格高騰リスクを避けるため、本番では単一`run-instances`ではなくSpot Fleet(またはEC2 Fleet API)の採用を推奨
- コスト目安(録画1回30分相当、保存7日、egressが無料枠超過した場合): 約$0.17〜0.20。**CloudFrontの永年無料枠(1TB/月)を使えばegressを実質ゼロにできる**(実機確認済み。動画1本約1.3GB想定で月700本超まで無料)。Webサービスの配信もS3直リンクではなく必ずCloudFront経由にすること
- インスタンス起動〜録画開始までのオーバーヘッドは約70〜100秒程度(EC2起動・Dockerイメージpull・PulseAudio初期化込み)

### 現在AWS上に残っているリソース(要確認・要整理)

フェーズ19終了時点で、ユーザーの「引き続き検証作業を行う可能性があるため」という指示により、以下のAWSリソースが**削除されずに残置**されている(2026-07-16時点でEC2インスタンス自体は稼働していないことを確認済み):

- S3バケット(`touhou-recorder-output-<AWS_ACCOUNT_ID>`)
- CloudFrontディストリビューション + Origin Access Control
- IAMロール・インスタンスプロファイル・インラインポリシー
- セキュリティグループ
- ECRリポジトリ(`touhou-recorder`、イメージ入り)

Webサービス開発に着手する際は、これらを**本番用に作り直すか、そのまま流用するか**をユーザーと確認すること。検証用の暫定構成(IAMポリシーが緩め、命名が検証時のまま等)のまま本番に転用するのはセキュリティ上望ましくない可能性が高い。

## Webサービス化に向けて未着手・要検討の項目

1. **ジョブキューイングの実装が完全に未着手**。これまでは`gcloud run jobs execute`やAWS CLIでの手動実行のみで、SQS/Cloud Tasks等によるキュー・ワーカー起動の自動化はゼロから設計する必要がある
2. **リプレイファイルのアップロード〜検証〜キューイングのAPI設計が未着手**。ユーザーがアップロードした`.rpy`から「どのタイトル・どのキャラ・バージョンか」を判定するパーサーも現状存在しない(MODは1件目固定選択なので、そもそも複数タイトル・複数リプレイの判別も必要になる)
3. **`.rpy`ファイルのバリデーション**が未実装。不正なファイル・デシンクするリプレイ・非対応タイトルのファイルがアップロードされた場合のハンドリングを考慮する必要がある(なお、フェーズ3で計画していた「デシンクの有無判定」自体、MOD方式に切り替えて以降は実施していない。録画された動画がリプレイと完全に一致している保証は目視確認止まりであり、自動デシンク検知の仕組みは無い)
4. **同時実行数のスケーリング設計が未検証**。ローカルでは2インスタンスが安定上限という制約があったが(AGENTS.md参照)、これはWine/Xの共有リソース制約に起因する可能性が高く、**AWS上で1インスタンス=1コンテナ=1録画ジョブに分離していれば問題にならないと推測されるが、実際に複数EC2インスタンスを同時起動して負荷検証したことは無い**
5. **Spotインスタンスの中断(スポット価格高騰による回収)時のリトライ・レジューム機構が未実装**。ユーザーがアップロードしたリプレイの録画がSpot中断で失敗した場合の再試行設計が必要
6. **ユーザー向けの進捗通知・完了通知の仕組みが無い**(ポーリングかWebhook/WebSocket通知か等はWebサービス側の設計次第)
7. **対応タイトルの拡大**(th07・th08以外)は上述の通りほぼ手つかず
8. **リプレイファイルの任意選択**(MODの「1件目固定」ロジックの改修)が必須
9. **コスト管理**: 想定利用規模(想定ユーザー数・月間録画本数)によって「Spot Fleet + CloudFront」構成のコスト試算(1本あたり$0.05〜0.20程度)がどこまで許容できるかを事前に見積もっておくとよい
