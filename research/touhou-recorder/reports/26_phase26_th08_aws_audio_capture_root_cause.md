# フェーズ26: th08のAWS重複フレーム90%問題の真因特定と修正(音声同時キャプチャ)

日付: 2026-07-22

**訂正(フェーズ27)**: 本レポート「全編録画によるA/V同期(音ズレ)の確認」で「両ストリームとも開始0秒・13分で尺差わずか8ms、音ズレは実用上発生しない」と結論づけたが、これは**尺(duration)の一致=ドリフト(蓄積誤差)が無いことの確認**であり、**2つのffmpegプロセスの録画開始タイミング自体が揃っているか(絶対的な同期オフセット)は検証していなかった**。フェーズ27でAWS `c7i.xlarge`にて別途行ったth08フル尺録画をユーザーが実際に視聴したところ、**音声が映像より約700ms先行する明確な音ズレが確認された**。映像・音声を別プロセスで起動する現行方式(`scripts/23`・`scripts/25`)は、両ffmpegプロセスの起動シーケンス自体はほぼ同時だが、x11grabとpulseそれぞれの実際のキャプチャ開始までの内部レイテンシが異なりうるにもかかわらず、mux時(`-c copy -shortest`)にオフセット補正を行っていないため、これが未補正のまま焼き付いている可能性がある。詳細・今後の調査方針は`reports/27_phase27_th08_alternative_instance_type_verification.md`の追補3を参照。

## 目的

フェーズ24で「AWS EC2上でth08(ver1.00d)の重複フレーム率が90%超になる」問題を発見し、当初「AWS仮想化環境そのものが原因」と結論づけたが、フェーズ25で同一環境・同一パイプラインでth07は正常(0.8%)と判明し、その結論は誤りで「th08固有の何か」に起因することまで切り分けられていた。本フェーズではこの残された真因を特定し、正常に録画できるよう修正した。あわせて、フェーズ24/25の検証が「15分フル録画×3」で高コストだった反省から、検証を大幅に高速化した。

## 検証の高速化(前提整備)

重複フレーム90%はフェーズ24の観測どおり録画開始直後から一様に現れる現象なので、15分フル録画は不要で、**リプレイ再生開始後90秒だけ連続録画してその区間の重複フレーム率を測れば判定できる**。`scripts/25_record_replay_e2e_multigame.py`に以下を追加した:

- `--record-seconds N`: N秒だけ録画して重複フレーム率を計測・報告して終了(画面静止検知・stutter probe・grab_frameポーリングは連続録画の計測を攪乱するので本モードでは行わない)
- `--no-audio`: pulse依存を排し映像のみ録画(切り分け用)
- `--muxed-audio`: 後述の音声分離を無効化し旧来の単一ffmpeg方式に戻す

これにより1試行が約15分→**約1.5〜3分**に短縮され、費用・時間ともに大幅に削減できた。

## 真因特定: 切り分け実験

AWS EC2 `c7i.xlarge`(4vCPU、us-east-1)上で、Dockerデフォルト設定(seccomp/cgroup有効)・uid 1000固定で条件を1つずつ変えて比較した(th08、`th8_01.rpy`、録画開始15秒以降の90秒区間で計測)。

| 条件 | 重複フレーム率 |
|---|---|
| barehost(Docker無し)・音声無し | **2.8%** |
| Docker・音声無し | **1.3%** |
| Docker・muxed音声(x11grab+pulseを単一ffmpegで同時取り込み=旧パイプライン) | **85.8%** |
| Docker・映像のみffmpeg + 独立した別プロセスの音声ffmpegを同時実行 | **2.0%** |

この4条件から真因が一意に確定した:

1. **barehost・音声無し=2.8% / Docker・音声無し=1.3%** → Docker層(namespace/seccomp/cgroup)は無実。フェーズ24が疑った「AWS仮想化環境そのもの」も、音声を外せば正常なので直接の原因ではない。
2. **Docker・muxed音声=85.8%** → フェーズ24の90%問題を同一インスタンスで再現(対照実験)。
3. **Docker・映像ffmpeg + 独立音声ffmpeg=2.0%** → 音声を「別プロセス」でキャプチャすれば同時に録っても映像は正常。

したがって真因は「**x11grab(映像)とpulse(音声)を1つのffmpegプロセスで同時に取り込んでいること**」に確定した。単一ffmpeg内部のA/V同期(音声クロックへの映像キャプチャの結合)がth08の描画・キャプチャタイミングを律速し、実効的な画面更新レートを大幅に落としていた。th07が影響を受けないのは、th07の方が描画パイプラインに余裕があり同一のA/V同期でもタイミングを崩さないため(フェーズ24でth08のみX11ソケットを高頻度にビジーポーリングしていた所見と整合)。ローカルマシンで問題が出なかったのも、ローカルはCPU/スケジューリングに余裕がありA/V同期の結合が顕在化しないため。

## 修正: 映像と音声を別プロセスで録画して後でmux

`scripts/23_record_th08_ver100d_replay_e2e.py`(本番th08)と`scripts/25`(th07/th08共通)の両方を、**既定で映像と音声を別々のffmpegプロセスで録画し、停止後に`ffmpeg -c copy -shortest`で結合する**方式に変更した。旧来の単一プロセス同時取り込みは`--muxed-audio`で明示的に選択できる(非推奨)。cloud entrypoint(`entrypoint_multigame.py`/`entrypoint_th08.py`)はフラグ無しでスクリプトを呼ぶため、**再ビルド・引数変更なしで自動的に修正が適用される**。

- 映像ffmpeg: `x11grab`のみ(ウォーターマーク合成・720pアップスケールのフィルタもこちらに適用)→ `<output>.video.mp4`
- 音声ffmpeg: `-f pulse -i auto_null.monitor`のみ → `<output>.audio.m4a`
- 両者を同時に起動し、停止時に両方へSIGINT、その後`ffmpeg -i video -i audio -c copy -shortest <output>`で結合

### 修正の検証

同一AWS `c7i.xlarge`で、修正後(既定=音声分離)を複数回検証した:

| 検証 | 重複フレーム率 |
|---|---|
| scripts/25・音声分離(修正)・15..91s区間 ×3回 | **1.9% / 3.1% / 1.8%** |
| scripts/23(本番)・音声分離(修正)・アクティブ区間 | **5.9〜7.4%** |

- muxファイルはいずれもh264映像 + aac音声2ch(尺一致)の正常なファイルであることをffprobeで確認。
- 本番`scripts/23`はリプレイ(`th8_02.rpy`、約42秒で終了)の終了を画面静止検知で正しく捕捉して停止し、**試行1で「正常な録画」と判定**(重複フレーム率が30%閾値を大きく下回るためリトライ不要)。なお`th8_02.rpy`はもともと短いリプレイで、42秒以降の静止画面区間まで含めて測ると38.7%になるが、これはリプレイ終了後の静止フレームによるもので、アクティブなゲームプレイ区間(15〜42秒、MAD 27〜156の正常な動き)は5.9〜7.4%と良好。
- ローカル(ユーザーのマシン)でも`scripts/23`が既定=音声分離で正常動作(重複率1.0%、映像+音声2chの正常muxファイル)することを確認済み。

### 全編録画によるA/V同期(音ズレ)の確認

映像・音声を別プロセスで録画して後muxする方式では、2つのffmpegの起動タイミングのズレやクロックドリフトが全編で音ズレにならないかが懸念点となる。これを検証するため、ローカルで`scripts/23`(既定=音声分離)により`th8_01.rpy`を全編録画(総録画793.8秒≈13.2分、`runs/local_full_sepaudio/video.mp4`、624MB)した。

| 項目 | 結果 |
|---|---|
| 映像 start_time / duration | 0.000000 / 793.033s(60fps, 47582フレーム) |
| 音声 start_time / duration | 0.000000 / 793.025s(48000Hz, 2ch) |
| 映像・音声の尺の差 | **8ミリ秒**(13分通しで0.001%、知覚不能・ドリフト無し) |
| 音声レベル | mean −10.7 dB / max 0.0 dB(実際のBGM/SFXが入っている) |
| 重複フレーム率(序盤/中盤/終盤) | 0.8% / 1.7% / 0.0%(全編で一貫して良好) |

**両ストリームとも開始0秒・13分で尺差わずか8msであり、音ズレは実用上発生しない**ことを確認した(音ズレが知覚され始めるのは一般に±40〜80ms以上)。ユーザーによる実際の目視・試聴でも音ズレなし・良好と確認された。

### mux構成による処理時間への影響

音声分離+後muxにより処理時間がどう変わるかを計測した。

- **録画フェーズ**: 追加した音声用ffmpeg(pulse→aac、ステレオ1本)は負荷がごくわずかで、録画はリアルタイム(尺=リプレイ長で律速)のまま変わらない。むしろAWSではこの分離がth08の処理落ちを解消している。
- **追加された後処理(mux)**: `ffmpeg -c copy -shortest`(再エンコード無しのストリームコピー)。上記624MB・13.2分ファイルで実測**0.59秒**(最大RSS 62MB)。I/Oバウンドでファイルサイズにほぼ比例するため、AWSの4vCPU+gp3でも数秒以内。
- **差し引き**: 全体で増えるのはmuxの約0.6秒のみ(13分録画の0.1%未満)で体感差はほぼ無い。旧muxed方式もwall-timeは同じだったが中身が重複フレーム90%の使い物にならない動画だったため、**同じ処理時間で「使える動画」が得られるようになった**のが本質的な差。

## フェーズ24/25の結論の最終訂正

- フェーズ24「AWS EC2の仮想化環境そのものが原因」→ **誤り**(音声を外せばAWSでも正常)。ただしフェーズ24のライブデバッグで得た「th08はスケジューリング/システムコールレイテンシに敏感で余裕が少ない」という所見自体は正しく、それが単一ffmpegのA/V同期という外乱に対してth07より脆弱だった、という形で真因と整合する。
- フェーズ25「問題はth08固有の何か」→ **正しい**。その「何か」が本フェーズで「音声同時キャプチャ時のA/V同期に対するth08描画パイプラインの脆弱性」と具体化された。

## 今後の課題・補足

- 本番の監視ロジック(`scripts/23`の`probe_stutter`/`grab_frame`ポーリング)は録画中に都度新規ffmpegを起動するため、原理上は録画への軽微な外乱になりうる。今回のアクティブ区間5.9〜7.4%は`scripts/25`の`--record-seconds`(ポーリング無し)の1.8〜3.1%よりやや高めで、この差の一部はポーリング外乱の可能性がある。実用上は30%閾値を大きく下回り問題ないが、さらに品質を詰めるなら録画中ポーリングの頻度・方式を見直す余地がある。
- 音声分離方式は`.video.mp4`/`.audio.m4a`の中間ファイルを生成する(cloud entrypointがアップロードするのは最終`video.mp4`のみなので実害なし)。ディスク逼迫が問題になる運用ではmux後に中間ファイルを削除してもよい。
- 同種の修正は`scripts/11`(th07)・`scripts/22`(旧th08 ver1.00a)には未反映。th07はそもそも音声同時取り込みでも正常(4.7%)なため優先度は低いが、安全側に倒すなら同様に音声分離化してもよい。

## 使用・削除したAWSリソース

- 検証用EC2はスポット`c7i.xlarge`(us-east-1)を使用。途中でスポット中断(容量不足)に遭い、かつus-east-1全AZで`c7i.xlarge`スポット容量が枯渇していたため、最後の本番`scripts/23`確認1回のみ同型のオンデマンド`c7i.xlarge`を短時間(約20分、~$0.06)使用した。
- 検証完了後、EC2インスタンス・キーペア・セキュリティグループを全て削除済み。孤立EBSボリューム・スポットリクエストが無いことも確認済み。

## 調査の完了

真因の特定・修正・修正の有効性(AWS実機での重複フレーム率、ローカル全編でのA/V同期・処理時間)の確認まで完了した。ユーザー判断により、**AWS環境を使った追加調査(カクカク版と修正版の比較ペアの録り直し等)は問題なしとして実施せず、本フェーズをもって今回の調査を終了とする**。今後th08のAWS本番録画は、既定(音声分離)の`scripts/23`+`cloud/docker/aws/`のイメージ/entrypointをそのまま使えばよい(追加のフラグ設定は不要)。
