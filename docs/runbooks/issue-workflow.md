# Issue・PR の運用ルール

Issue の作り方・GitHub Projects のカラム運用・PR の作法。Issue を新規に立てるとき、
実装に着手するとき、PR を作るときに読む。`AGENTS.md` §7 から分離した（Issue #114）。

初回リリースに向けた実装フェーズを終え、継続改善フェーズに移行するにあたっての方針である。

## 0. 作成先リポジトリ

**Issue・PR は必ずプライベートリポジトリ `hakatashi/sattori-dev` に作成する**。
`hakatashi/sattori`（パブリック）はミラー的な位置づけで、開発の実体（Issue 管理・PR）は
`sattori-dev` 側にある。`gh` コマンドで Issue・PR を作成する際は `--repo hakatashi/sattori-dev`
を明示するか、作業ディレクトリの `origin` が `sattori-dev` を指していることを確認すること。

## 1. ラベル

**`phase-1` / `phase-2` / `phase-3` ラベルによる Issue 管理は廃止**。フェーズ分けは
初回リリースまでの管理手法であり、継続改善フェーズでは使わない。新規 Issue にこれらの
ラベルを付けないこと。

## 2. GitHub Projects

進捗管理は [GitHub Projects](https://github.com/users/hakatashi/projects/3) の
`Backlog` / `Todo` / `In Progress` / `Done` カラムで行う。

- Issue の実装に着手したら、**手動で `In Progress` へ移動**すること
  （自動遷移は設定していない）。
- `Backlog` は将来的に着手するタスク、`Todo` は比較的すぐ着手したいタスクを置く。
  この2カラム間の仕分けはユーザーのディレクション判断が絡むことが多いため、エージェントが
  新規 Issue を作る場合はどちらに置くべきかユーザーに一任してよい（迷ったら `Backlog` に
  置き、ユーザーに確認する）。

## 3. Issue の作成

- **実装の過程で今後確実に対応が必要な積み残し課題が見つかった場合、ユーザーの許可を
  求めずに Issue を作成してよい**（例: 実装中に見つかった別の不具合、実機検証で判明した
  既知の制約、今回のスコープ外にした TODO）。ただし方向性の判断が必要な提案・アイデア
  段階のものは、Issue 化する前にユーザーに確認すること。
- Issue の **Relationships 機能**（`blocked by` / `blocks`）を積極的に使い、Issue 間の
  依存関係が一覧から分かるようにする。特に新規 Issue 作成時、既存の未完了 Issue に依存する
  （またはブロックする）関係にあるなら明示すること。

## 4. PR

- PR をマージする際は **merge commit 方式**を用いる（squash・rebase は使わない）。
- Issue に対応する PR を作成する際は、**本文に `Closes #xxx` 形式のコメントを書く**。
  マージ時に Issue が自動クローズされるようにするため。
- **Issue を解決する修正は直接 main にコミットせず、必ず PR を作成する**（上記の
  `Closes #xxx` 運用と、Issue ベースの変更履歴を残すため）。
- Issue に紐づかない小規模な修正（typo・ドキュメント微修正など）は main へ直接
  コミットしてよい。ただし**リモートへの push（コミット後の反映）はユーザーの判断による**
  ため、エージェントが直接コミットした場合も push の可否は必ずユーザーに確認すること。
- **PR を作成したら、必ず今回の変更を changelog に追加すべきか検討すること**。対象は
  `apps/web` の UI 変更に限らない —— 録画ワーカー（`worker/`・`home-worker/`）の機能改善、
  リプレイパーサー（`packages/replay-parser`）の仕様変更など、**ユーザーが気づきうる変更は
  すべて対象**とする。内部的なリファクタリング・ドキュメント更新などユーザーから見える
  変化が無いものだけが対象外。
- 追加すると判断したら `apps/web/src/data/changelog.ts` に日英エントリを追記し
  （更新履歴ページ `/changelog`）、**その場で追加コミットとして同じ PR へ push する**
  （PR 作成後の別作業に紛れて忘れないよう、判断と追記・push を1セットで行う）。
- changelog の文面では「自宅サーバー」のような内部実装の詳細を出さず、**「追加ワーカー」
  という表現を使う**（`home-worker/README.md`。ユーザーにとって録画基盤の内部構成がどこで
  動いているかは関知すべき情報ではないため）。
