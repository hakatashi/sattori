# 自宅サーバーでの並列録画の実機検証（CPU温度・処理落ち）

- **検証日**: 2026-08-09
- **対象**: 自宅ワーカー（`home-worker`）でのフル尺録画、1並列 / 2並列（th07・th08）
- **環境**: 開発マシン AMD Ryzen 7 5700X（8コア16スレッド / 94GiB）。タイトル資産の取得・
  リプレイ取得・出力アップロードは本番と同じ eu-south-2 の S3 バケットを使用
- **結論**: 破綻の条件は「2並列であること」ではなく
  **「サーマル上限に張り付いた状態へ、さらに外部負荷が乗ること」**

自宅サーバーでフル尺のリプレイを録画し、並列数と録画品質の関係を実測した。2並列自体は
再現性のある劣化を起こさないが、CPU は常時サーマル上限（91℃前後）に張り付いており、
そこへホストの他負荷が乗ると全編に処理落ちが散発する。`HOME_WORKER_MAX_CONCURRENCY` の
既定を2に留めているのはこの結果による。

## 目的

`HOME_WORKER_MAX_CONCURRENCY` を何に置くべきかを決めるため、自宅マシンで何並列まで
録画品質を保てるかを実測する。

## 方法

コンテナの起動はデーモンの `buildDockerCommand()` / `ContainerRun`（検証当時は Python
実装の `runner.py`。TypeScript 移植後の `src/runner.ts` と同じ `docker run` を組み立てる）
を実際に使った。`JOBS_TABLE` は未指定（本番の JobsTable を汚さないため）、`TASK_TOKEN` は
ダミー（Step Functions の実行が無いため）。

**処理落ちの指標には ffmpeg 自身の `dup` / `drop` カウンタ**
（`worker/runs/{jobId}/ffmpeg_video.log`）を使う。これは「入力フレームが間に合わず
複製した／捨てた」枚数そのもので、60で割れば失われた秒数になる。

CPU 温度は録画中の Tctl / Tccd、CPU 競合は PSI の `cpu some` stall、ホスト負荷は sysstat の
履歴（ldavg・`%nice`・`%user`）で見た。

## 結果

3回のランを比較した。

| ラン | フレーム数 | dup | drop | 録画時間 | 重複フレーム率(15〜45秒) |
| --- | --- | --- | --- | --- | --- |
| 1並列 th07 | 124982 | 2 | 0 | 2084.8秒 | 0.4% |
| 2並列 th07 | 124954 | 3 | 0 | 2086.2秒 | 7.2% |
| 2並列 th08 | 117175 | 3 | 0 | 1955.1秒 | 0.2% |
| **劣化した回** 2並列 th07 | 133631 | **318** | **315** | 2229.0秒 | 6.9% |
| **劣化した回** 2並列 th08 | 125724 | **495** | **491** | 2097.5秒 | 20.6% |

「劣化した回」では目視で1〜2秒の処理落ちが複数回確認でき、`dup` の増分を1分刻みで見ると
全編に散発していた（両ジョブで**同時刻に**スパイクする＝ホスト側の要因）。同じ2並列でも
後日の再現実行では `dup=3` / `drop=0` と、1並列（`dup=2`）とほぼ同一だった。

### 何が効いていたか

**(a) CPU温度**。録画中のCPU温度は 1並列で Tctl 中央 80.8℃ / 最大 88.1℃、2並列で
**中央 91.0℃ / 最大 93.8℃**（Tccd は最大 99.2℃）。5700X の最大動作温度は 90℃なので、
**2並列の録画中は常時サーマル上限に張り付いている**。CPU競合の指標（PSI の `cpu some`
stall）も 21.8 → 79.8 ms/s（p95 126.2 ms/s）と3倍以上になる。

**(b) ホストの他負荷**。劣化した回だけ、sysstat の履歴で ldavg 11〜27・`%nice` 4.7〜6.8%
（nice 値付きの別プロセスが約1コア分）・`%user` 38〜54% を記録していた。再現実行時は
ldavg 6〜14・`%nice` 0.03%・`%user` 31〜35% で、同じ2並列でも破綻しなかった。

つまり**破綻の条件は「2並列であること」ではなく「サーマル上限に張り付いた状態へ、さらに
外部負荷が乗ること」**である。再現する2並列固有の影響は、録画開始15〜45秒の重複フレーム率が
0.4% → 7.2% に上がる程度（録画の総時間は変わらない）に留まる。

### 確認できた機能面

2並列・1並列いずれも `exit_code=0` で完走し、元解像度版・720p版とも正常に生成・
アップロードされた。ジョブごとの PulseAudio sink 分離（Issue #48）は両コンテナで機能し、
`task_heartbeat.py` は送信失敗（ダミートークンによる `InvalidToken`）を握りつぶして録画を
継続した。

## 考察・既知の限界

- **「何並列まで大丈夫か」は固定の数字では決まらない**。冷却状態と、そのときホストで他に
  何が動いているかで変わる。`HOME_WORKER_MAX_CONCURRENCY` の既定を2に留めているのは
  このため。上げる前に必ずこの節の手順で実測すること。
- `HOME_WORKER_LOAD_THRESHOLD`（既定 0.7）は**新規 claim を止めるだけで、走り出した録画の
  劣化は防げない**。劣化した回の ldavg 11〜27 は 16スレッド換算で 0.69〜1.7 なので、
  デーモン経由であれば新規 claim は止まっていた可能性が高い。
- **重複フレーム率の欄は録画開始15〜45秒の30秒スポットしか見ていない**
  （`recording_common.measure_duplicate_rate`、Issue #93）ため、**録画途中の劣化を
  検知できない**。劣化した回も 6.9% で閾値 30% を通過した。表の値を全編の代表値として
  読まないこと（`docs/known-limitations.md` §3）。
- 冷却の改善が最も効果の大きい対策になる見込み。
- サンプルは 1並列1回・2並列2回（うち劣化1回）のみ。3並列以上は測っていない。
