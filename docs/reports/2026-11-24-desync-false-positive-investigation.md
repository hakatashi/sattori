# リプレイずれ検知(`desyncDetected`)の誤検知の原因調査と改善案

- **検証日**: 2026-11-24
- **対象**: 本番で `desyncDetected=true` になったジョブのリプレイ41本(10タイトル)のうち、開発者の目視で
  「ずれていない」(偽陽性)と判定された24本。真のずれ(真陽性)17本は、改善案で見逃さないことの確認に使った
- **環境**: 自宅ワーカー機(HakataMatrix、Ryzen 7 5700X)。本番ワーカーイメージ `sattori-worker:latest`、
  `CAPTURE_MODE=frame_sync`、タイトル資産は S3 の最新版(2026-11-22)
- **結論**: 偽陽性24本のうち22本の原因を特定した。原因はタイトルごとに異なる。th08 は MOD が表示用の追っかけ値を
  読んでいた。th20 は記録者が thprac の「PIVオーバーフロー抑制」を使っていた(修正を当てた再生で記録スコアに完全一致)。
  th07/th11/th13 は、最終ステージだけ再生のスコアが記録にわずかに届かないゲーム側の性質だった。改善案を既存のログに当てると、
  偽陽性は 17/24 → 2/24(加えて検証不能3本)に減り、真陽性17本はすべて検知されたままになる

ゲームのメモリを `/proc/<pid>/mem` から約0.5ms間隔で直接読み、MOD の ScoreMonitor(20ms間隔)では
見えない値の動きと、記録スコアがメモリ上のどこにあるかを確かめた。th20 は、ゲームのコードを
thprac と同じ修正で書き換えて再生し直す実験で確定させた。判定ロジックを変えるときは §5 の改善案と §6 の限界を読むこと。

## 1. 目的

`worker/recording/modlog.py` の `check_replay_desync()` は「MOD の ScoreMonitor のサンプルの中に、
リプレイの記録スコア(`replayInfo.score`)とちょうど一致する値が無ければ true」と判定する。
本番で true になったジョブには、本当にずれたもの(真陽性)とずれていないもの(偽陽性)が混ざっている。
偽陽性の原因をタイトルごとに突き止め、真陽性を見逃さずに偽陽性を減らす方法を探す。

## 2. 方法

### 2.1 対象と正解ラベル

前段の調査(`/mnt/cache3/sattori-desync-verify/`、同ディレクトリの `findings.md`)で、本番 JobsTable の
`desyncDetected=true` 92件から、同一リプレイを畳んで作品ごと最大5本、計41本を選んだ。それを本番イメージの
フレーム同期でローカル再録画し、その動画を開発者が視聴して T(真陽性)/F(偽陽性)を付けた。
th08-e20bccc6 は当初 F だったが、詳しく見直した結果 T(5面まで正常、6面途中からずれ)に訂正された。訂正後の内訳は
**T 17本・F 24本**。ステージ開始時から動きが不自然な「リプレイ異常」(thprac 等の特殊な環境で記録された疑い)も
T として扱う。リプレイは jobId の先頭8桁で呼ぶ(例: th20-16c954e0)。

### 2.2 メモリの直接観測(`memwatch.py`)

Wine のゲームプロセスはホストからも普通の Linux プロセスとして見える。root で `/proc/<pid>/mem` を開けば、
ゲームの仮想アドレスをそのまま読める。MOD が読んでいる状態構造体の全フィールドを約0.5ms間隔で読み、
値が変わるたびに記録した。さらに、MOD の最終値になった瞬間に、書き込み可能な全メモリから
記録スコアの値を探した。スクリプトは
[`research/archive/desync-false-positive-probes/`](../../research/archive/desync-false-positive-probes/README.md)。

| タイトル | 読んだ範囲 | 根拠 |
| --- | --- | --- |
| th07 | `*(0x626278)` から 0xa0 バイト(MODと同じ GAME_MANAGER→globals) | thprac `thprac_th07.h` の `Globals` |
| th08 | `*(0x160f510)` から 0x40 バイト | thprac `thprac_th08.cpp`(score1=+0x08、score2=+0x00) |
| th11 | `0x4a56e0` から 0x78 バイト | thprac `thprac_th11.cpp` の `Globals` |
| th13 | `0x4be7c0` から 0x80 バイト | MOD の設定 |
| th20 | `exe+0x1ba5f0`(`GlobalsSide`)から 0xf0 バイト | thprac `thprac_th20.cpp` の `GlobalsSide` |

### 2.3 th20 のコード書き換え(`th20_pivfix.py`)

th20 の点アイテム得点の計算(RVA `0xC49A7`)を、thprac の `th20_piv_overflow_fix` と同じ64bit計算に
`/proc/<pid>/mem` 経由で書き換え、そのまま録画した(§4.2)。

### 2.4 改善案の評価(`simulate.py`・`corrections.py`)

前段の41本の MOD ログ(20msサンプル)に改善案の判定を当て、開発者の T/F と突き合わせた。
th08 の判定だけは、メモリ観測で得た値を使った(§4.1)。

## 4. タイトル別の原因

### 4.1 th08: MOD が表示用の追っかけ値を読んでいる

MOD(`th08_replay_autoplay`)は `*(0x160f510)+0x00` をスコアとして読む。メモリ観測では、
**+0x08 が真値、+0x00 はそれを数フレームかけて追いかける表示用の値**だった。スペルカード取得の瞬間、
+0x08 は記録スコアちょうどに一度で跳ねる。+0x00 は約7msの観測ごとに約10万点(内部値)ずつ追いかけ、その途中で
リプレイが終わって構造体が解放される(直後にゴミ値になる)。

| リプレイ | 記録(表示値) | +0x08 の到達 | +0x00 の到達(0.5ms観測) | MOD(+0x00、20ms)の最大値(ゴミ値除外) |
| --- | ---: | --- | --- | ---: |
| 01d5db9c | 40,028,690 | 到達 | 到達したが、その8ms後に解放 | 36,954,080 |
| 33851689 | 424,510 | 到達 | 到達せず | 424,310 |
| ab900a45 | 90,998,850 | 到達 | 到達せず | 61,488,950 |
| e646fd8a | 15,377,600 | 到達 | 到達せず | 10,821,170 |

前段の調査で「MOD スコアが一律 444,994,480 の定数」とされた値は、解放後のゴミ値だった。グレイズも
同時に壊れるため、本番の `read_verified_scores()` ではグレイズの上限フィルタで除外される。前段の集計スクリプトは
このフィルタを掛けていなかった。スペルプラクティスは終了が速く、通常プレイよりこの影響が表に出やすい。
**th08 の全面プレイでも、最終ボーナスの直後にリプレイが終われば同じ取りこぼしは起こりうる。**
なお th07 の MOD は最初から `true_score`(+0x04、表示は +0x00)を読んでいるので、この問題は無い。

### 4.2 th20: 記録者が thprac の「PIVオーバーフロー抑制」を使っていた

**ゲーム側のバグ**: th20 の点アイテムの得点は `piv_base × piv / piv_divisor + piv_base/2` で、
実測で `piv_base=10000`・`piv_divisor=5000` だった(`GlobalsSide` +0x40/+0x44/+0x48)。乗算が
**32bit の `imul`**(RVA `0xC49A7`)なので、`piv`(異変値×5000)が 214,748 を超える
(異変値 42.95 以上)と溢れる。攻略wikiの[不具合ページ](https://wikiwiki.jp/thk/bug/%E9%8C%A6)にも、異変値 42.9 前後を境に
点アイテムの得点が10点に固定されると書かれている。thprac には、これを64bit乗算に直す
`th20_piv_overflow_fix`(「PIVオーバーフロー抑制」、既定は無効のオプトイン)がある。

**記録時と再生時で計算が違う**: 記録者がこの修正を有効にしていると、記録時は正しい得点、
素のゲームでの再生はオーバーフローした得点(10点など)になる。プレイ内容は同じなので、画面上は
ずれて見えない。

**ステージ開始時の上書き**: リプレイの再生では、**スコアが各ステージの開始から約2秒後に、記録時のステージ開始
スコアで上書きされる**(MOD ログで観測)。thprac が PIV 修正と同時に有効にする `th20_score_uncap_stage_tr` は、
ステージ遷移時にステージデータ(0x8a dword)を `rep movsd` でコピーする箇所(RVA `0x10910F`)から先頭8バイト
(スコア)を外す hook で、この上書きに当たると見られる(コピー先の特定まではしていない)。差として
最後まで残るのは最終ステージの分だけである。上書きされた量(=直前のステージで生じた差)は、
異変値が 42.95 を跨いだステージの直後にだけ現れた。

| リプレイ | 判定 | 各ステージ開始時の異変値(1〜6面) | 開始時の上書き量(≠0のもの) | 最終値−記録 |
| --- | --- | --- | --- | ---: |
| 16c954e0 | F | 0.00 / 33.11 / 38.97 / 64.94 / 80.30 / 118.94 | 4面 +69,229,930、5面 +457,696,040、6面 +511,825,300 | −913,593,820 |
| abdad590 | F | 0.00 / 25.72 / 32.40 / 51.96 / 70.86 / 101.21 | 4面 +23,310,000、5面 +436,271,270、6面 +492,983,030 | −878,429,270 |
| 57d81918 | F | 0.00 / 4.25 / 7.05 / 24.22 / 31.73 / 49.11 | 6面 +19,836,800 | −901,177,340 |
| 97b20dec | F | 0.00 / 25.99 / 34.87 / 43.47 / 57.48 / 77.60 | なし | +10,200 |
| cf96dc25 | T | 0.00 / 7.86 / 17.45 / 65.95 / 88.63 / 125.60 | なし | +1,171,360 |

前段の調査では「3面から差が広がる」ように見えていたが、ステージ開始時の上書きが2秒遅れて入るためで、
実際の差は面ごとに独立している。97b20dec と cf96dc25 も閾値を跨いでいるが、上書き量はすべて0だった。
記録者が素のゲームで遊んでいたので、記録時と再生時で同じようにオーバーフローしていたことになる。

**確認実験**: 16c954e0 を、§2.3 の書き換えを当てて再生した。上書き量は全ステージで0になり、
**最終スコアが記録スコア 2,622,647,520 に完全一致**した(`desyncDetected=false`、理論尺比 +0.13%)。
書き換えはリプレイ開始の数十秒後になったが、異変値が閾値未満のうちは両方の計算結果が同じなので影響しない。
装備・難易度の違う 57d81918(Easy、Red/Red/Blue/Green)も、再生開始前に書き換えて録画すると
**記録スコア 1,950,482,540 に完全一致**した(理論尺比 −0.08%)。

#### 4.2.1 対照: 素のゲームで記録されたリプレイに書き換えを当てる

素のゲームで記録された 97b20dec(上書き量がすべて0)に、同じ書き換えを再生開始前に当てて録画した。
異変値が閾値を跨ぐ3面の直後から、**再生が記録を上回る向きの上書き**が入った(4面 −23,290,350、
5面 −328,944,070、6面 −524,832,530)。最終値は記録より +870,314,460 高く、`desyncDetected=true` になった
(理論尺比 −0.04%)。修正を常に当てることはできない。一方で上書き量の**符号**を見れば、記録者が修正を
使っていたか(正)、修正なしの記録に修正を当てたか(負)を区別できる。

### 4.3 th07・th11・th13: 最終ステージだけ再生が記録にわずかに届かない

3タイトルとも、再生の最終値は記録より少しだけ低い。th07・th11・th13 を1本ずつ同じ条件で2回再生したところ、
**最終値は1回目と同じ値**になった(フレーム同期では決定的)。メモリ観測でも、真値のフィールドは最後の加点の後
数秒〜7秒そのまま動かずに、記録値に届かないまま終わった。全メモリを探すと、記録スコアの値は
ヒープ上の1か所(リプレイのヘッダを読み込んだ領域と見られる。th11・th13 はブロック先頭+0x34)にしか無かった。
MOD のサンプリング間隔や読む場所の問題ではない。

| リプレイ | 記録(表示値) | 再生の最終値 | 差 | 記録比 | 2回目 |
| --- | ---: | ---: | ---: | ---: | --- |
| th07 12e70625 | 219,169,040 | 219,109,600 | −59,440 | −0.027% | 同値 |
| th07 1d710c21 | 279,960,530 | 279,353,540 | −606,990 | −0.217% | (未実施) |
| th07 4d15a112 | 1,608,253,750 | 1,607,660,680 | −593,070 | −0.037% | (未実施) |
| th11 57f6211c | 223,845,030 | 223,841,940 | −3,090 | −0.0014% | (未実施) |
| th11 8ba51a31 | 738,375,070 | 738,374,820 | −250 | −0.00003% | 同値 |
| th11 b760aac0 | 672,737,520 | 672,735,730 | −1,790 | −0.0003% | (未実施) |
| th13 28759316 | 260,429,020 | 260,112,700 | −316,320 | −0.121% | 同値 |

- **th11**: th20 と同じく、ステージ開始時にリプレイのスコアで上書きされる。その上書き量が
  **ずれていない3本でも普段から +20〜+480 点ある**(例: 8ba51a31 は3面 +420、4面 +150)。
  ステージ内の得点が再生で数十〜数百点再現されず、次のステージの開始で記録の値に戻される。
  最終ステージにはその「次」が無いので、差がそのまま残る。最終の差(−250〜−3,090)は、境界での上書き量と同じ規模である。
- **th13**: 境界での上書き量は0だった。最終の差 31,632(内部値)は、終盤に拾っていた点アイテム
  7,908点のちょうど4個分。記録時はボス撃破後にもう4個回収されていたことになる。
- **th07**: ステージ開始時の上書きは無い(または MOD の読む値に反映されない)。ステージ別の記録値には
  1・2面は一致し、3面以降は0.5ms観測でも一度も一致しなかった。差は 3面終了時 11,913 → 最終 5,944(内部値)
  と単調ではない。ステージ別記録の取得タイミングを含め、機構は特定できていない。
  [`2026-11-21-mod-core-refactor-verification.md`](2026-11-21-mod-core-refactor-verification.md) の
  「th07 の既知の個体差」(実時間で数十点足りない)も同じ型と見られる。

いずれも開発者の目視では、ずれは無かった。これは仮説1(ゲーム自体の記録・再生の差)に当たる。
仮説2(サンプリング間隔)・仮説3(追っかけ値)は、この3タイトルには当てはまらない。th11 の Globals+0x00 と
th13 の +0x50 には追っかけ値があったが、MOD はどちらも真値の側を読んでいた。

### 4.4 th06 3731b273: ヘッダとステージ記録の食い違い

ヘッダのスコアは 45,621,640、最終ステージ(5面)のステージ記録は 45,621,660 で、リプレイ自身の中で20点食い違う。
MOD の最終値は後者と一致し、1〜4面のステージ記録にも各面の終了時に一致した。

### 4.5 未解明の2本

- **th06 de779faf**(Extra): MOD の最終値が記録より +19,302,130 高く、理論尺比 −10.7%。終端で +24,127,660 の
  一括加算がある。記録時との違いは特定できていない。
- **th20 97b20dec**: 全ステージで上書き量が0、最終ステージだけ +10,200(内部値1,020)高い。th20 の点アイテムは
  オーバーフロー域では1個10点(内部値)なので、102個ぶんに当たる。§4.3 と同じ型の差が、逆向きに出た可能性がある。

## 5. 改善案

前段の41本の MOD ログに当てた結果(`simulate.py`、§2.4)。

| | 偽陽性24本のうち true | 偽陽性のうち検証不能(None) | 真陽性17本のうち true |
| --- | ---: | ---: | ---: |
| 現行(完全一致のみ) | 17 | 0 | 17 |
| 改善案 P1〜P4 | **2**(th06 de779faf、th20 97b20dec) | 3(th20) | **17** |

### P1. th08 の MOD のスコア欄を +0x08(真値)へ変える【MODの変更】

`th08_replay_autoplay/dllmain.cpp` の `sm.scoreOffset = 0x00` を `0x08` へ。スペルプラクティス4本の偽陽性が消える。
MOD の変更なので、全面プレイ・スペルプラクティスの実機検証が要る(`AGENTS.md` §3)。

### P2. 最終ステージの記録スコアも一致として認める【ワーカーの判定】

ステージ記録がステージ終了時のスコアを持つタイトル(th06 系・th07・th08)では、ヘッダのスコアに加えて
最後のステージ記録のスコアとの一致も認める。th06 3731b273 が解消する。

### P3. 最終値が記録をわずかに下回るだけなら一致とみなす【ワーカーの判定】

`0 < 記録 − 最大値 ≤ 記録 × 0.3%` なら、ずれ無しとする。th07×3・th11×3・th13×1 が解消する。

- **下回る側だけを許す**。上回る側は真陽性の th20 cf96dc25(+0.26%)と偽陽性の 97b20dec(+0.002%)の
  両方があり、許容を設けると cf96dc25 を見逃しうる。
- 真陽性のうち最も差が小さいのは th08 e20bccc6 の −20.8% で、0.3% から十分遠い。0.3% は、偽陽性の最大
  (th07 1d710c21 の −0.217%)に余裕を持たせた値で、7本からの当てはめにすぎない(§6)。
- 最終ステージのごく終盤で起きたずれ(得点への影響が0.3%未満)は見逃すが、動画への影響も小さい。
- ステージ開始時の上書きがあるタイトル(th10〜th20 系)では、途中ステージの開始スコアとの完全一致
  (各ステージの最初の数サンプル以内)を併せて要求すると、より安全になる。

### P4. th20 の「PIV修正つき記録」を扱う【MODかワーカー】

- **案A(推奨、MODの変更)**: MOD でステージ開始時の上書き量を見張る。上書きが正の値で、直前のステージの
  異変値が閾値(214,748)を超えていたら、それ以降の点アイテム得点を64bit計算へ切り替える(§2.3 と同じ書き換えを
  MOD の中で行う)。ステージ開始で記録のスコアに戻るので、次のステージからは記録と完全に一致した検証ができる。
  さらに、**動画に映るスコア表示も記録者が見ていた値になる**(現状は修正つき記録の再生で、終盤のスコア表示が
  記録より数億点低い)。最終ステージで初めて閾値を跨いだ場合は切り替えの機会が無いので、P4案Bに落とす。
- **案B(ワーカーの判定だけ)**: MOD ログから各ステージ開始時の上書き量を求め、正の上書きが異変値の閾値越えと
  重なっていたら `None`(検証不能)とする。上の表の 3本が None になる。上書き量が0の cf96dc25(真陽性)は
  従来どおり true のまま。
- **修正を常に当てるのは不可**: 素のゲームで記録されたリプレイ(97b20dec 等)が逆に一致しなくなる(§4.2.1)。
