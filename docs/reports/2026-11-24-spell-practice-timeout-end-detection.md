# スペルプラクティスを耐久で終えたリプレイ(th13・th14・th20)の終了検知

- **検証日**: 2026-11-24
- **対象**: th13・th14・th20 のスペルプラクティスのリプレイ9本(`packages/replay-parser/test-fixtures/` の
  th13_07・08、th14_03〜05、th20_09〜12)。本番でタイムアウトしたジョブ `2ecbdbb7…`(th13 Extra のスペルプラクティス)
- **環境**: 自宅ワーカー機(HakataMatrix、Ryzen 7 5700X)の Docker。本番ワーカーイメージ
  `sattori-worker:latest`、フレーム同期(`CAPTURE_MODE=frame_sync`)、`--cpus 4`。タイトル資産は S3 の現行版
- **結論**: 耐久で時間切れになったリプレイは**再生後にリプレイ一覧画面へ戻る**。一覧画面は背景が全面で
  動き続けるので画面静止検知は永久に成立しないが、**一覧画面のテンプレート照合**なら、通常のプレイ
  (全編録画で計約6.5時間分)と大差で分離でき、3本とも動画の約3.5秒以内に終了と判定できる

本番ジョブは推定84秒のリプレイが、実時間の上限120分のあいだ一覧画面を録り続け、約5時間(18,040秒)・配信版を含め約10 GBの動画として
配信された。ローカルでも耐久の3本(th13_07・th14_03・th20_11)だけが同じく止まらず、残りの6本は従来どおり画面静止で
終了した。対策として、画面静止検知はそのまま残し、**リプレイ一覧画面のテンプレート照合を2本目の終了条件として足す**
ことを提案する(§5)。あわせて、未知の画面に対する保険として理論尺による上限も検討に値する。

## 1. 目的

ユーザーの調査で、th13・th14・th20 のスペルプラクティスで「通常スペカを耐久して時間切れ(未取得)」で終わった
リプレイは、再生終了画面に遷移せずリプレイ一覧画面に戻ることが分かっている(耐久スペカでは起きない)。
これをローカルで再現し、こうしたリプレイの再生終了を正しく検知する方法があるかを確かめる。

## 2. 方法

### 2.1 録画

[`verify-recording-locally`](../../.claude/skills/verify-recording-locally/SKILL.md) skill の手順で、S3 のタイトル資産を
`/mnt/cache3/sattori-spellprac-timeout-verify/` へ展開(root 所有)し、本番ワーカーイメージで `record_thNN.py` を
直接呼んだ(`--max-attempts 1`、フレーム同期)。終了しないリプレイは外側の `timeout`(th13_07 は300秒、th14_03 は200秒、
th20_11 は420秒)で打ち切った。スクリプトは
[`research/archive/spell-practice-list-template-probes/`](../../research/archive/spell-practice-list-template-probes/README.md) の `run.sh`。

`--expected-duration-seconds` は全本ダミーの60を渡したので、ログの「理論尺との比較」の警告は無意味である(§3.1 の表で
正しいフレーム数と比べ直した)。3タイトルを並列で走らせたため th14・th20 は動画の0.4〜0.5倍速で進んだが、フレーム同期なので
映像には影響しない。

### 2.2 テンプレート照合の評価

終了検知が実際に見ているのは、MOD が書くサブ出力(`output/repro.pollstream.raw`、160x120 グレー、8fps)である。
打ち切った3本はこれが残るので、その一覧画面の部分からテンプレートを作り、マスク付き MAD
(`recording/vision.py` の `mad_masked()`、閾値の比較と同じ量)を全フレームについて出した。

- **マスク**: th13・th14 は全画面から一覧の先頭行(プレイヤー名・日付などリプレイごとに変わる行。160x120 で th13 は
  19〜24行目、th14 は18〜24行目)を除いた。th20 は背景の動きが大きく先頭行の差が埋もれるので全画面とした。
  th10 の前例(touhou-recorder reports/56)に倣った「見出し"Replay"だけ」の案も th20 で比べた。
- **テンプレート**: (a) 一覧画面の区間の中央値、(b) 1枚のフレーム(一覧区間から等間隔に約12枚選んで最悪値を取った)、
  (c) th13 のみ本番ジョブの動画(640x480、別リプレイ・EC2 `c7a.2xlarge`)から切り出した1枚。
  (b)(c) は PNG に保存し、本番の `load_end_template()` と同じく PIL で160x120へ縮小して使った。
- **誤検知の走査**: 過去の検証で残っている通常リプレイの全編録画を、ffmpeg で 8fps・160x120 グレーに落として
  全フレームを照合した(`scan.py`)。リプレイ再生開始前にも一覧画面が映る(動画の11〜14秒)ので、**最初の25秒を除いた
  最小値**を「再生中の最小値」とした。本番の監視はリプレイ再生開始からさらに15秒の猶予のあとに始まるので、この除外は
  本番の挙動と同じ側にある。
- **判定タイミング**: `framesync._monitor_until_end()` と同じく、動画の2秒間隔・猶予15秒・2回連続で一致したら終了、を
  サブ出力に当てた(`simulate.py`)。

### 3.2 一覧画面で画面静止が成立しない理由

一覧画面は背景が全面でアニメーションする(th13 は花びらが舞う、th14 は背景の明滅、th20 は模様が流れる)。
画面静止の判定(2秒おきの MAD が `STILL_MAD_THRESHOLD`=2.0 未満を8回連続)に対し、一覧画面での実測は次のとおりで、
2.0 を下回るのは周期の中の1サンプルだけだった。除外矩形(`still_detect_exclude_rect`)で逃がせる範囲ではない。

| タイトル | 一覧画面での静止判定 MAD(2秒おき) | 周期 |
| --- | --- | --- |
| th13 | 1.6〜6.0 | 約10秒 |
| th14 | 1.8〜9.0 | 約10秒 |
| th20 | 6.3〜29.7 | 不規則 |

### 3.5 判定タイミング

`simulate.py` で、本番の監視ループと同じ間隔・猶予・連続回数を当てた結果(th13・th14 は閾値15、th20 は閾値35)。
理論終端は「上限を解除したフレーム + リプレイの frameCount」を60で割った値(再生確定から上限解除までの約1秒のずれを含む)。

| リプレイ | テンプレート | 判定(動画の秒) | 終端(`content_end_sec`) | 理論終端 | 差 |
| --- | --- | ---: | ---: | ---: | ---: |
| th13_07 | (c) 本番動画の1枚 | 68.6 | 66.6 | 63.5 | +3.1秒 |
| th14_03 | (b) 1枚 | 47.9 | 45.9 | 44.9 | +1.0秒 |
| th20_11 | (b) 1枚・(a) 中央値とも | 68.5 | 66.5 | 65.3 | +1.2秒 |

切り出される動画の末尾は「Bonus Failed」とロード画面を含み、一覧画面の最初の1〜2秒で終わる。正常終了のリプレイでも
画面静止の始まりを終端にしているので、見た目は同程度になる。

## 4. 考察・既知の限界

### 4.1 検討した方法

| 方法 | 評価 |
| --- | --- |
| 画面静止の除外矩形を広げる・閾値を緩める | 不可。一覧画面は全面が動き(§3.2)、th20 は MAD が30近くまで上がる。緩めればプレイ中の静かな場面で誤検知する |
| **リプレイ一覧画面のテンプレート照合を足す** | **有効**。プレイ中との差が大きく(th13 33以上・th14 41以上・th20 50以上 対 一覧画面 最大9〜29)、既存の `end_template` の仕組み(th06〜th10 で運用中)の延長で書ける |
| 理論尺(frameCount)による上限 | 保険として有効。通常の6本は再生区間が frameCount より1.7〜3.7秒長いだけで、全編録画の理論尺比も既存レポートでは th06 の1本(-14%)を除き±数%以内。ただし終了の検知そのものではなく、どこで切るかは粗い |
| MOD でゲームのシーン遷移を読む | 今回は調べていない。一覧へ戻ってもスコア監視の値(stage 等)は変わらなかったので、タイトルごとに新しい RVA を探す必要がある |

### 4.2 この検証から言えないこと

- **閾値の余裕**: th13・th14 は既存の `END_TEMPLATE_MAD_THRESHOLD`(15)で足りる(一覧画面の最大12.2、プレイ中の最小33.5)。
  th20 は15では一覧画面を取りこぼす。35前後が中間だが、1枚テンプレートの一覧画面側の最悪値(29.3)との差は6しかない。
  中央値テンプレートなら最大20.0まで下がるので、th20 は中央値で作った方がよい。いずれも一覧画面のサンプルは
  1本(th20 は約100秒、th14 は約45秒)からしか取っていない。
- **再生前の一覧画面との競合**: 照合はリプレイ再生開始の15秒後から始まり、再生前の一覧画面は動画の14.4秒までで消えている
  (全12本)。ただしメニュー操作に失敗して一覧画面のまま再生が始まらない場合は、猶予明けに「終了」と判定される。
  現状はこの場合も時間切れまで止まらないので悪化ではなく、スコアが0のままなら `is_score_zero()` でリトライされる。
- **実時間の経路(GPU の段)**: th13・th20 は GPU 倍速の段も持つが、今回はフレーム同期だけを検証した。
  `pipeline._monitor_until_end()` も同じ静止検知なので同じ問題があるはずで、同じ照合を足すなら別途検証が要る。
- **他のタイトル**: 他の録画対応タイトルで同じ挙動がないことはユーザーの調査による(この検証では録画していない)。
- **耐久リプレイのスコア照合**: th13_07 等は終了しないので確かめられていない。
- **時間切れした録画の扱い**: 本番ジョブは上限で打ち切られたのに `done` で配信された(`timedOut=true`)。止まらないことの
  被害を大きくしているが、この検証の範囲外とした。

## 5. 実装するなら

1. **テンプレート照合を2本目の終了条件として足す**: `GameConfig` にリプレイ一覧画面のテンプレート(パス・マスク・閾値)を足し、
   `still_detect_exclude_rect` で静止検知しているタイトル(th13・th14・th20)では、静止判定に加えて毎サンプル照合する。
   2回連続で一致したら `detected_by="replay_list"` 等で終了し、`content_end_sec` は一致の始まりにする。今の `end_template` は
   「テンプレートがあれば静止検知を使わない」排他の作りなので、そのまま th13 用の PNG を置くと正常終了(終了メニューの静止)を
   取りこぼす。そこは流用せず別の項目にすること。
2. **テンプレート画像**: サブ出力と同じ160x120グレー(または同じ縮小を通る画像)にする。マスクは th13・th14 は先頭行
   (160x120 で18〜24行目)を除いた全画面、th20 は全画面。th20 は複数フレームの中央値で作る。候補画像は自宅ワーカー機の
   `/mnt/cache3/sattori-spellprac-timeout-verify/templates/` にある(`thNN_replay_list_median160.png` 等)。
   `worker/assets/` はリポジトリに入れない扱いなので、Dockerfile の COPY と S3/イメージへの反映を忘れないこと。
3. **保険**: 動画の時間(フレーム同期ならサブ出力の枚数)で「理論尺の1.5倍＋数分」を超えたら打ち切る上限は、今回のような
   未知の画面への備えとして安く入れられる。打ち切ったものをどう扱う(警告付きで配信するか)かは別に決める必要がある。
4. 録画パイプラインの変更なので、**クラウドでの実機検証を経ること**(`AGENTS.md` §3)。耐久の3本で終了すること、
   撃破・耐久スペカの6本と通常の全編録画で退行しないことを確かめる。

## 6. データの場所

自宅ワーカー機の `/mnt/cache3/sattori-spellprac-timeout-verify/`:

- `thNN/run-<リプレイ>/`: 各録画の `run.log`・`output/`(打ち切った3本は `repro.pollstream.raw` が残る。mp4 は未完成)
- `th20/run-th20_11-short/`: th20_11 の最初の試行(200秒で打ち切り、並列実行)
- `th13/run-th13_08-score/`: `--expected-score` 付きの再実行
- `prod-2ecbdbb7/`: 本番ジョブの動画から切り出したフレーム
- `templates/`: 候補テンプレート画像
