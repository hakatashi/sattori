# 倍速録画（Issue #288）の本番E2E検証とNVENC品質値の決定

- **検証日**: 2026-10-02
- **対象**: PR #291（録画ワーカー・MOD）と PR #292（shared・API・infra）を本番へデプロイし、
  `options.recordingSpeed` をAPIで直接指定して全12タイトルを録画（フロントエンドは`main`の
  ビルドのまま、`verify-recording-in-production` skill）
- **環境**: 本番（eu-south-2）。GPUジョブは全件 `g6f.2xlarge`（Spot、全件 eu-south-2b）、
  等倍のCPUジョブは自宅ワーカー（th20）と `c7i-flex.xlarge`（th10）
- **結論**: **全17ジョブが完走**し、映像で確認した限り本当のデシンクは無かった。同期マーカーの
  mux後の残差は全件±1ms以内。倍速を等倍へ戻した動画のゲーム本編は等倍録画と一定のオフセットで
  揃っており、速度のずれは見られなかった。ただし**#291に倍速時だけ起きる不具合が2件**
  （th09の起動待ちタイムアウト短縮、スコア監視の取りこぼしによるデシンク誤判定）と、
  **th12の倍速時に画面上のfps表示が120fpsになる**問題を見つけた。NVENCの配信用品質値は
  **CQ25**に決めた（暫定値27から変更）。

## デプロイ

- MODを全タイトル分クリーンビルドした。タイトル資産は、ローカルの`games/`・`prefixes/`がローカル
  検証で変わっている可能性を避けるため、**S3上の現行アーカイブを取得し`mods/*/build/`だけを
  差し替えて**再パックした（全12本でファイル一覧が不変であることを確認）。
- ワーカーイメージ（CPU用・GPU用）をpush → タイトル資産をアップロード → #292のworktreeから
  CDKデプロイ（`apps/web/dist`は`main`のビルドに差し替え）。公開サイトの配信JSに
  `recordingSpeed`が含まれないことを確認した。
- `cdk diff`の差分は、Lambda群・GPU Launch Templateの`g6f.2xlarge`化・CPU用AMIの定期更新
  （ECS最適化AL2023の 20260922 → 20260929）だけだった。

## 見つかった問題

### 1. 倍速時にスコア監視が最終スコアを取りこぼし、デシンクと誤判定する（#291で修正）

th07（3倍速）とth08（2倍速）で`desyncDetected=true`になった。しかし動画の最終フレームのスコアは
どちらも記録スコアと一致していた（th07: 3581800、th08: 59889420）。ScoreMonitorは**実時間1秒**ごとに
サンプリングするため、倍速時はゲーム内の間隔がN倍に広がる。どちらも未クリアのリプレイで、最終スコアへの
到達からメニュー復帰までが短く、最後のスコア上昇を取りこぼしていた。th07はローカルの等倍でも同じく
取りこぼしていた（2026-09-30のMOD統合テストのログで最終サンプルが357380）ので、元々際どい
リプレイである。

→ `StartScoreMonitorThread()`で、`SPEED_HACK_MULTIPLIER`が1より大きいときに間隔を1/Nにする
（ゲーム内時間での間隔を等倍と揃える）。等倍の動作は変わらない。

### 2. th09の倍速時に起動待ちのタイムアウトが縮み、1回目の試行が失敗した（#291で修正）

th09のMODは、ウィンドウ待ちとフック待ちのタイムアウトを`30000 × (60 / FPS_LIMIT_TARGET_HZ)`で
計算していた（低速録画で延長するための式）。倍速では**2倍速で15秒・3倍速で10秒に縮み**、ゲームの
起動（Direct3D初期化に約15秒）を待ちきれず`WaitForStableWindow: TIMEOUT`になった。2回目の試行で
成功した。ワーカー側の`scaled_timeout_sec()`と同様、延長方向にだけ効かせるよう修正した。
他タイトルのMODに同じパターンは無い。

### 3. th12の倍速時に画面上のfps表示が120fpsになる（未修正）

上記のとおり。th12の公開はPR 5/5なので、それまでに直す。

### 4. GPUインスタンスで`docker run`の失敗がStep Functionsへ通知されない（既存の問題）

th11の初回インスタンスは、イメージのpullとログストリームの作成までは進んだものの、イベントが0件のまま
インスタンス内部からシャットダウンした。UserDataの`notify_bootstrap_failure`はECRログインと
pullの失敗しか通知しないため、ハートビートタイムアウト（15分）を待ってからリトライされた。
原因（GPUランタイムの初期化失敗など）は、コンソール出力が残っておらず特定できなかった。

### 5. g6f.2xlargeのSpot単価が上がり続けている

今回のGPUジョブは全件 eu-south-2b・$0.1401/時（2aは`InsufficientInstanceCapacity`）。Spot価格の
履歴では、2bが9/19の$0.070から毎日上がり続けて10/2に$0.140、2aも$0.063→$0.124、2cは$0.39。
`packages/shared/src/cost.ts`の予備単価と、Issue #288のコスト見積もり（$0.08〜0.10/時で月$4.0〜4.9）の
前提より高い。この単価のままだと、同じ見積もりは月$6〜7程度になる。

## NVENCの配信用品質値（`NVENC_DELIVERY_CQ`）

8タイトルの生データ（チェックポイントが変換後に削除される前に別キーへ退避したもの）を、
使い捨てのg6f.2xlargeで本番と同じ`convert_for_delivery()`のまま**CQ23〜29**で変換した。
本番CPUイメージでのlibx264 crf18と比べた結果は次のとおり。画質は、同じフィルタチェーンの
ロスレス変換（libx264 `-qp 0`）を基準にした全フレーム平均のSSIM/PSNR。

| タイトル（解像度） | libx264 crf18 | NVENC CQ25 | NVENC CQ26 | NVENC CQ27（暫定値） |
| --- | --- | --- | --- | --- |
| th06（640x480→960x720） | 75.3MB / 0.9855 / 41.81 | 84.2MB / 0.9850 / 42.83 | 75.6MB / 0.9830 / 42.14 | 67.5MB / 0.9808 / 41.43 |
| th06c（同上） | 80.7MB / 0.9852 / 42.09 | 90.3MB / 0.9837 / 42.71 | 81.0MB / 0.9818 / 42.07 | 72.4MB / 0.9797 / 41.44 |

| th20（1280x960） | 211.4MB / 0.9818 / 40.54 | 212.2MB / 0.9806 / 41.14 | 189.1MB / 0.9774 / 40.30 | 167.2MB / 0.9731 / 39.35 |

（各セルは サイズ / SSIM / PSNR[dB]）

- 同じサイズで比べると、NVENC（`-preset p4`）はlibx264（`-preset veryfast`）よりSSIMがわずかに
  低い。CQ27では全タイトルでlibx264より画質が下がっていた。
- **CQ25に決めた**。8タイトル合計のサイズがlibx264とほぼ揃い（+2%）、SSIMもほぼ同等になる。
  タイトル別のサイズ比は0.87〜1.28と幅があり、640x480を拡大するタイトルは+4〜12%、
  th06nc（720p）は+28%、th128は−13%。最初に公開するth15はサイズ−2%で画質同等。
- CQの値は出力に対して決定的だった（本番のCQ27の出力とスイープのCQ27の出力が1バイトも違わない）。
- 変換時間はCQに依らず、尺の約13%（GPU）だった。

## 所要時間の推定（`packages/shared/src/recordingSpeed.ts`）

`launchedAt`→`doneAt`の実測と、`estimateRecordingCompletionSeconds()`（GPU: 固定180秒＋
録画`尺×1.05/N`＋変換`尺×0.08`）を比べた。起動失敗を含むth11とリトライを含むth09を除くと、
推定/実測は**0.92〜1.13（13件、平均1.01）**で、**係数は変えない**。内訳は、録画以外の固定分が
約140秒、変換が推定尺の約16%（出力尺の約13%）で、変換係数の過小分を固定分の過大分が
打ち消している。CPU側の等倍は2件とも過大見積もり（自宅1.25、c7i-flex 1.40）だったが、
件数が少なく今回の範囲外。
