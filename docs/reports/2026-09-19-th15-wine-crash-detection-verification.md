# GPUワーカーのWineクラッシュ検知手段を実機再現実験で比較

- **検証日**: 2026-09-19
- **対象**: 本番GPU(g6f)ワーカーで発生したWineクラッシュ3件の原因調査と、その検知手段の比較(Issue #267)
- **環境**: 調査はAWS本番(eu-south-2、`g6f.2xlarge`)のDynamoDB・CloudWatch Logs・S3。再現実験はHakataMatrix(自宅ワーカー機)のDocker上で`sattori-worker:latest`(CPU系イメージ)を使い、th15を`gpu_display=False`(Xvfb+wined3d+llvmpipe)で録画
- **結論**: 3件はいずれも「Wine上でゲーム本体がクラッシュし、フリーズした画面を静止検知が誤って"リプレイ終了"と判定したもの」。**`wine.log`に現れる`Unhandled`だけが2つのクラッシュ形態の両方を検知でき、かつ正常時・デシンク時に誤検知しない**。プロセス生存監視・プロセスstate監視・`winedbg`出現監視はいずれか一方しか検知できない

th15 PR(#264)の本番E2E検証中、GPUワーカーで3件立て続けにWineがクラッシュし、録画が途中で切れたまま`done`として配信された。本番ログとDynamoDBの横断調査でAZ(`eu-south-2a`)への強い偏りを特定し、さらにローカルで意図的にアクセス違反を起こす再現実験を3通り行って、どの検知手段なら実装に足るかを実測で決めた。

## 目的

1. 3件のクラッシュの原因を特定し、th15 PR(#264)の変更が原因かどうかを判定する。
2. この異常を録画中に検知する手段を決める。**理論尺比(録画時間/リプレイ推定時間)による検知はデシンクと縮退するため使えない** —— デシンクは本質的に回復不能(リトライで解決しない)な東方シリーズ共通の問題で、ユーザーも織り込み済みであり、途中までの動画にも価値がある。理論尺比で失敗判定するとデシンクに対して不要なリトライを消費し、かつ録画データがユーザーに届かなくなる。

## 方法

### 本番ログの横断調査

対象ジョブ(`3182b7c9-0678-4994-8a85-02951946a402`・`a37acd43-c469-405e-9052-fdc56565371c`(th06nc、同一リプレイ)・`d18b4eb3-2984-47e3-a91a-0f6b8a08ae32`(th15))について、DynamoDB `JobsTable`のレコード、CloudWatch Logs `/sattori/worker`のワーカーログ、S3の`progress/<jobId>/`配下の進捗プレビュー画像を突き合わせた。あわせてGPU(`g6f`)ジョブ全22件をAZ別に層別し、Fisher正確検定(片側)でクラッシュ率の差を検定した。また保持期間(14日)内の全録画について`総録画時間`ログと`estimatedDurationSeconds`の比を算出し、途中終了したジョブを網羅的に洗い出した。

### ローカル再現実験

`verify-recording-locally` skillの手順に従い、th15の資産をS3から取得してDockerで録画した。**このマシンにはNVIDIA GPUが無い**ため、`record_th15.py`の`gpu_display=True`を`False`にしたコピーをコンテナへマウントして差し替えた(リポジトリの`worker/`は変更していない。`crtc_mode`は`gpu_display.py`でしか参照されないためCPU描画では無害に無視される)。録画中のth15.exeに対して3通りの方法でクラッシュを試み、0.5秒間隔で次を記録した:

1. `/proc/<pid>/stat`のstate
2. `winedbg`/`werfault`等クラッシュハンドラプロセスの出現
3. `wine.log`の新規出力
4. MODの`ScoreMonitor`ログが止まるか
5. Xのトップレベルウィンドウ構成

| 実験 | 方法 |
| --- | --- |
| 1 | 外部から`SIGSEGV`を送信 |
| 2 | `th15.exe`のコード領域(`0x401000-0x4be000`)全体を`mov eax, ds:[0]`(`A1 00 00 00 00`)で埋め、ゲーム自身の実行でアクセス違反を起こす |
| 3 | 同じ書き込みを64KBに限定 |

`/proc/<pid>/mem`への書き込みはコンテナのデフォルト権限(`CAP_SYS_PTRACE`なし)では`Permission denied`になるため、実験2はホストのrootから、実験3は`--cap-add=SYS_PTRACE`を付けたコンテナ内から行った。

## 結果

### 本番3件の共通点

| 項目 | 3182b7c9 | a37acd43 | d18b4eb3 |
| --- | --- | --- | --- |
| タイトル | th06nc | th06nc | th15 |
| インスタンス | g6f.2xlarge | g6f.2xlarge | g6f.2xlarge |
| AZ | eu-south-2a | eu-south-2a | eu-south-2a |
| 理論尺 / 実録画 | 849s / 623.8s (73%) | 849s / 226.5s (27%) | 260s / 289.3s (111%) |
| 最終観測スコア | 123746410 | 69668330 | 25269670 |
| 判定 | `done`(desyncDetected=true) | `done`(desyncDetected=true) | `done`(desyncDetected=true) |

**3182b7c9とa37acd43は同一リプレイなのにクラッシュ地点が595秒と202秒で異なる**(スコアも異なる)。デシンクは決定論的に同じ場所で崩れるため、これは環境側の非決定的なクラッシュである。進捗プレビュー画像では、d18b4eb3にWineのクラッシュダイアログ(「プログラム th15.exe で重大な問題が発生したため、終了する必要があります。」)が、3182b7c9には真っ黒な画面(ウィンドウごと消滅)が写っていた。

### AZ別のクラッシュ率(GPUジョブ、`status=done`のもの)

| AZ | done | Wineクラッシュ |
| --- | --- | --- |
| eu-south-2a | 6 | **4** |
| eu-south-2b | 16 | **0** |

Fisher正確検定(片側)で **p = 0.0021**。Spot価格を追うと`eu-south-2a`は一貫して`eu-south-2b`より約20%安く(0.061〜0.065 vs 0.071〜0.078)、`price-capacity-optimized`が9/18を境に2aを選び続けるようになったことが「立て続けに起きた」直接の引き金だった。9/12〜9/17のGPUジョブはほぼ全て2bだったのに対し、9/18は5件全てが2aである。

**th15 PR(#264)の変更は原因ではない。** Launch Templateのバージョン履歴から各ジョブが使ったAMI・UserDataを逆引きしたところ、AMI切り替え(`SourceVersion: $Default→$Latest`、`decisions/0051`)は9/17 04:31から、32bit NVIDIAライブラリのマウント追加は9/18 17:49から有効だったが、**9/13の`91815815-9fc2-48b8-b197-2f436428b405`が旧AMI・32bitマウント無しの状態で全く同じ現象(理論尺比25%)を起こしている**。

### 途中終了ジョブの網羅調査(ログ保持期間内の全録画)

理論尺比85%未満は8件あり、うちGPUジョブは上記4件。残る4件(`51b7ae1b`・`18a776c8`・`b42355c9`・`e20bccc6`、いずれもc7i系)の最終プレビューを確認したところ、`f33af7f9`(th09)は対戦決着画面で正常終了、`b42355c9`(th06)はクラッシュダイアログなしのデシンクだった。**Wineクラッシュを伴う途中終了はGPUジョブでしか観測されていない。**

### 再現実験の結果

| 観測項目 | 実験1 (SIGSEGV) | 実験2 (全面破壊 757KB) | 実験3 (限定破壊 64KB) |
| --- | --- | --- | --- |
| `wine.log` | `err:seh:segv_handler Got unexpected trap 0` | `err:seh:NtRaiseException **Unhandled** exception code c0000005 flags 0 addr 0x49e93e` | `wine: **Unhandled** page fault on write access to 00000000 at address 004077C0 (thread 00d4), starting debugger...` |
| ゲームの継続 | **継続した**(score_samples 28→34と増加) | 停止 | 停止 |
| プロセス生存 | 生存 | `Z`→約1秒後に消滅 | **`alive=True`のまま**(クラッシュ50秒後も) |
| プロセスstate | `S` | `Z` | **`S`**(通常のsleepingのまま) |
| `winedbg`/`werfault` | なし | **出現せず** | `winedbg --auto 208 236` |
| ScoreMonitor | 継続 | 137サンプルで停止 | 35サンプルで停止 |
| 画面 | 変化なし | **真っ黒**(3182b7c9と一致) | **クラッシュダイアログ**(d18b4eb3と一致) |

実験2は本番の3182b7c9型を、実験3は本番のd18b4eb3型を、それぞれ画面の見た目まで含めて再現できた。実験2で`winedbg`が起動しなかったのは、コード領域を全面破壊したせいで例外処理中に`virtual_setup_exception stack overflow`が起き、ダイアログを出す前に二重障害で即死したためと見られる(`AeDebug`は`"Auto"="1"`, `"Debugger"="winedbg --auto %ld %ld"`と正しく設定されていた)。

### 検知手段の弁別性

`Unhandled`という単一パターンで3実験の`wine.log`出力を判定させた結果:

| 手段 | 実験2(消滅型) | 実験3(ダイアログ型) | 実験1(ゲーム継続) |
| --- | --- | --- | --- |
| プロセス死亡監視 | 検知 | **検知できない** | — |
| プロセスstate監視 | 検知(`Z`) | **検知できない**(`S`) | — |
| `winedbg`出現検知 | **検知できない** | 検知 | — |
| **`wine.log`の`Unhandled`** | **検知** | **検知** | **非検知(正しい)** |
| ScoreMonitor停止 | 検知 | 検知 | 非検知 |

`Unhandled`は2つのクラッシュ形態の両方に含まれ、かつゲームが生きているケース(`segv_handler Got unexpected trap 0`)には含まれない。

### 検知漏れの実害

両実験とも、録画パイプラインはクラッシュの**18〜20秒後**に画面静止検知で停止した。実験2では総録画時間170.1秒(理論尺260秒の65%)で**「試行1で正常な録画を確認しました」と成功扱い**になり、重複フレーム率は0.x%で素通りした。本番3件と同じ挙動である。

## 考察・既知の限界

- **ScoreMonitorはそのままではハートビートに使えない。** `worker/mods/common/score_monitor.cpp`は値が変化したときだけログを出すため、正常にリプレイ選択画面へ戻った場合も出力が止まり、クラッシュと区別できない。使うならMOD側に無条件ハートビートを追加する改修(全12タイトルのDLL再ビルドと資産再アップロード)が前提になる。この実験ではクラッシュ時に停止することだけを確認した。
- **`winedbg`出現検知は当てにならない。** ダイアログが出ない形態(実験2・本番3182b7c9)では起動しない。
- **AZ差の原因は未特定。** `eu-south-2a`で有意にクラッシュしやすいことは統計的に示せたが(p=0.0021)、ハードウェア個体差・vGPUスライスの状態など環境要因の可能性が高いというだけで、機序は分かっていない。本レポートの再現実験はクラッシュそのものの再現であって、AZ差の再現ではない。暫定対応としてGPUジョブのFleet Overridesから`eu-south-2a`を除外したが、原因が特定でき次第この除外は撤回すべき。
- **GPU描画経路そのものは未検証。** 再現実験はこのマシンにNVIDIA GPUが無いためCPU描画(Xvfb+llvmpipe)で行った。本番はXorg+NVIDIA GRIDドライバであり、**Wineの例外処理経路・`wine.log`の出力自体はGPUの有無に依存しない**が、GPU固有のクラッシュ形態が他にある可能性は否定できない。
- **クラッシュは人工的に起こしたもの。** 本番で実際にゲームを落とした原因(GPU側の異常なのか、ゲーム内部の状態なのか)は再現していない。あくまで「クラッシュが起きたときにどの手段で検知できるか」の比較である。外部からの`SIGSEGV`ではWineのシグナルハンドラに吸収されて再現できず、ゲーム自身の実行によるアクセス違反が必要だった点は、同種の実験を行う際の注意点として記録しておく。
- **サンプル数の制約。** AZ別の比較はGPUジョブ22件(2a:6件、2b:16件)に基づく。`eu-south-2b`で新環境(32bitマウント有効、v148以降)の長時間GPUジョブを流したデータは無く、PR #264の変更の寄与を完全にゼロと断定はできない。
- 副次的に、`nvidia-smi`失敗時のログが常に空になっていたことが判明した。NVMLの初期化失敗(`Failed to initialize NVML: Unknown Error`)は**stdout**に出るが、`worker/recording/pipeline.py`は`stderr`しか記録していなかったため、本番調査時にこの行が手がかりにならなかった。
