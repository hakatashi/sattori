# ワーカーのフレーム同期録画経路(Issue #389、親 #399)の全13タイトル・フル尺の実機検証

- **検証日**: 2026-11-22
- **対象**: Issue #389(`CAPTURE_MODE=frame_sync` の録画経路、`worker/recording/framesync.py`)。**本番のジョブのリプレイを全13タイトル各1本、フル尺で**録画した。補助として th06・th07 の追加リプレイ5本、実時間の経路(`CAPTURE_MODE` 無し)の退行確認2本
- **環境**: HakataMatrix(自宅ワーカー機、16 スレッド、GPU 無し)。`sattori-home-worker` は検証開始時に停止済みだった(こちらからは止めていない)。**ワーカーイメージは `worker/Dockerfile` を本ブランチからビルド**(`sattori-worker:verify-389-local`)し、`docker run --cpuset-cpus`(物理4コア+SMT = 8スレッド、`c7i.2xlarge` 相当)で2本ずつ並列に実行した
- **結論**: **全13タイトルが試行1回で完走**し、三者照合(MODの書き出し = 動画 = 音声)・スコア(th09 を除く)・視聴(代表フレーム・音量)を満たした。理論尺は th06 の1本だけが -14.0% で、同じリプレイを実時間の経路で録っても同じ長さ(753.8秒)になる**パーサー側の過大見積もり**と分かったため、許容を「短い側 -30%・長い側 +10%」にした。実時間の経路は th06(フル尺)・th15(低速録画)とも退行が無い

PR #409(MOD の移植)の検証([`2026-11-21-mod-frame-sync-port-verification.md`](2026-11-21-mod-frame-sync-port-verification.md))は
MOD の統合テスト用の短いリプレイだった。ここでは、**ワーカーの経路(FIFO のハンドシェイク・ffmpeg・終了検知・
mux・配信用変換まで)を、本番で実際に流れたフル尺のリプレイで**確かめた。設計判断は
[`0077`](../decisions/0077-worker-frame-sync-recording-path.md)。

## 目的

1. `framesync.py` が全13タイトルでフル尺を完走し、合否の判定(三者照合・理論尺・スコア)が正しく働くこと。
2. 終了検知・進捗・カット位置(動画の時間)が、実時間の経路と同じ品質で成り立つこと。
3. 音声が全タイトルで正しく出ていること(TR で視聴確認済みは th15・th12 だけだった)。
4. `CAPTURE_MODE` 無しの実時間の経路が壊れていないこと。

## 方法

- **ワーカーイメージ**: `docker build -t sattori-worker:verify-389-local worker`(`recording/` はディレクトリごと COPY されるので、
  `Dockerfile`・`Dockerfile.gpu` の COPY に新モジュールを足す必要は無い。両方が `COPY recording/ /app/recording/` を持つことは
  `worker/tests/test_dockerfiles.py` が確かめる)。MOD(`*_hook.dll`)は PR #409 の HEAD でビルドしたもの。
- **タイトル資産**: `worker/games/<title>`・`worker/prefixes/<title>-wined3d-gl`・上記 MOD・`injector*.exe` から、
  本番のアーカイブと同じ構成・除外(`score.dat`・`log.txt`・`replay/*` 等)で作り、`root:root` にして `/mnt/<title>-assets` へマウント
  (th06c・th06nc は Steamworks スタブで `steam_api64.dll` を上書き)。
- **リプレイ**: **本番の完了済みジョブから、推定尺が約13分(th06c だけ約10分)のものを各タイトル1本**選び、S3 のアップロード用
  バケットからダウンロードした(下表。**スコアの無い th09 以外はスコア照合ができる**ものに限った)。
- **実行**(`verify-recording-locally` skill の手順に準じる。`entrypoint.py` を経由せず `record_<title>.py` を直接):
  ```bash
  docker run --rm --cpuset-cpus 0-3,8-11 \
    -v $A/<title>:/mnt/<title>-assets -v $D/replay.rpy:/mnt/replay.rpy:ro -v $D/output:/mnt/output \
    -e CAPTURE_MODE=frame_sync -e WINEPREFIX=... -e SATTORI_GAME_DIR=... -e SATTORI_MOD_DIR=... \
    --entrypoint bash sattori-worker:verify-389-local -c 'pulseaudio -D ...; timeout --kill-after=30s 7800s \
      python3 record_<title>.py --replay-path /mnt/replay.rpy --output /mnt/output/video.mp4 \
      --expected-duration-seconds <推定尺> --expected-score <スコア> --desync-result-path ... --cut-result-path ...'
  ```
  録画のあと、`entrypoint.convert_and_upload()` と同じ引数(カット範囲・ウォーターマーク・`needs_separate_raw_output()`)で
  `convert.convert_for_delivery()` を実行して配信用の動画を作った。
- **並列度**: 2本ずつ(`0-3,8-11` と `4-7,12-15` の2レーン)。速度は並列の負荷込みの値(単独では速い)。

### A/V の同期

- **構造的な保証**: 全タイトルで「映像のフレーム数 × 2940バイト == PCM の大きさ」が端数0バイトで成り立ち、音声は映像の1フレームにつき735サンプルずつ書かれる
  (MODの仮想ミキサ)。mux は位置合わせ(`-itsoffset`)をしない。つまり音声の n 番目のフレームは映像の n 番目のフレームと同じゲーム時刻。
- **外部との照合は決め手に欠けた**: th06 の同じリプレイの実時間の経路の録画との相互相関(映像の動き量 vs 音声の高域エンベロープ、±30秒)では、
  映像のラグが +3.82秒、音声のラグが +3.89秒で**差は73ms**だった。ただし実時間側のタイムスタンプに数%の重複・不規則があり、60秒窓ごとの
  ラグが一定せず、実時間側の誤差と分離できなかった。**厳密な同期の確認は TR の決定性検証(reports/109: 基準動画との `drift=[0,0,0]`・A/V差 0.0ms)に依拠する**。

### 進捗・カット・チェックポイント

- **進捗**はサブ出力の枚数から「リプレイ再生開始からの尺」を報告する(`framesync.progress_seconds()`、ユニットテストで確認)。実機では
  `progress/state.json` に値が出ていることだけ確認した(アップロードは `entrypoint.py` の `ProgressReporter` で、ここでは通していない)。
- **カット**は全タイトルで、配信版の先頭がリプレイ選択画面(再生確定の1秒前)、末尾が終了検知の位置になっている(上のコンタクトシート)。
  th06nc・th20 は先頭の1秒がタイトル/メニューの画面になる(最後のStepが速いため。実時間の経路と同じ「再生確定のキーの1秒前から残す」規則)。
- **チェックポイント**のメタデータ `sattori-time-scale` は 1.0(`recording_time_scale()` が `CAPTURE_MODE=frame_sync` で常に 1.0)。
  `convert.needs_separate_raw_output()` は time_scale が 1.0 なので、640x480 のタイトル(960x720へ引き上げ)と th15・th20(1440x1080)は
  元解像度版を別に出し(2本)、th06nc(1280x720)は1本になる。**今の等倍のCPUと同じ挙動**で、上の表の配信版はこの結果。

### ディスク

生動画は 1280x960 で約 **2.0MB/秒(7.3GB/時)**、640x480 で約 0.7〜1.1MB/秒、PCM は **635MB/時**(1秒あたり 176.4KB)。1時間の th20(1280x960)では、
mux 前(中間の映像 7.3GB + PCM 0.64GB)→ mux 後(7.3GB)→ 変換(7.3 + 配信版 7.9 + 元解像度版 6.5 = 約21.7GB)がピークで、**実時間の経路と同じ最大使用量**
(増えるのは mux 時の PCM 0.64GB/時だけ)。最長の th20 Lunatic(41.6分)なら約15GB。Launch Template のボリュームサイズはコード上に明示が無く
(AMI の既定)、Docker のイメージ(3.3GB)とタイトル資産(約1.1GB)を足しても既存の運用と同じ余裕。ただし**EC2 での実測は #390 で行う**。

## 考察・既知の限界

- **th06 の理論尺 -14.0%**: リプレイパーサーの th06 の `frameCount` は「各ステージの入力変化ログの最後の `frameNum`」で(`packages/replay-parser/src/games/th06.ts`)、
  リプレイによってゲームの実際の再生フレーム数とずれる。この862秒の1本は実際の再生が約742秒で、**実時間の経路でも同じ長さ(753.8秒)**に
  なり、スコアも最終まで一致した。つまり**録画の異常ではなくパーサーの見積もりの誤差**。当初の ±10% では正しい録画を破棄したので、短い側を -30% にした
  (`framesync.DURATION_TOLERANCE_SHORTER_RATIO`)。**th06 のパーサーの誤差の原因は未解明**(他の th06 の4本は +0.6〜-5.65%)。リプレイが再生されなかった/
  途中で止まった録画(-100%〜大幅な短縮)を弾く目的には足りる。
- **ここで検証していないこと**: (1) AWS の EC2(c7i.2xlarge/4xlarge)での実行(速度は**この機械の4コア+SMT・2本並列**の値で、`c7i.2xlarge` の
  実測とは違う。TR reports/112 §5.2 の推定速度と同じ傾向)。(2) GPU インスタンス(g6f)でのフレーム同期(計画に無い)。(3) `FRAME_SYNC_SKIP_PRESENT=1`(既定では使わない)。
  (4) 41.6分のような最長のリプレイ(ここでは約10〜15分)。120分の上限は固定値と単体テストのみ。(5) th06nc の 1080p(保留中)。(6) 起動側の配線(#390)。
- **FIFO のバッファ**: 並列に走らせた2本目以降で、`F_SETPIPE_SZ` が EPERM になる場面があった(`pipe-user-pages-soft`、
  コンテナは `CAP_SYS_RESOURCE` を持たず、同じ root のパイプの総量が上限を超えるため)。1MiB を得られたのは th08(1回目)・th15・th128、
  512KiB が th08(最終)、128KiB が th06nc、**8KiB(2ページ)が th06・th06c・th07・th09・th10・th11・th12・th13・th20 の9本**だった。**録画自体はすべて成功**し、1280x960(th15 は 1MiB で 0.59x、th20 は 8KiB で 0.63x)
  では差が見えなかったが、640x480 の速度(th08 は 1MiB で 3.53x、512KiB で 3.22x)への影響は切り分けていない。バッファを小さくして試す
  フォールバックと警告ログを入れた(`framesync._grow_pipe_buffer()`)。**自宅ワーカーで並列実行するなら `docker run` の追加引数に `--cap-add=SYS_RESOURCE` を
  足すと上限を受けない**(要検討、起動側の設定のため #390 の運用で)。
- **最初の実行の失敗**: 並列の1本目(th15)が 1MiB を確保したあと、2本目(th20)・以降の同じレーンの6本が `F_SETPIPE_SZ` の EPERM で例外終了した(未対応の例外)。上のフォールバックを足して全部やり直した(この記録の表はやり直しのあとの結果)。
