# 自宅ワーカーの配信用動画アップロード速度を本番ログから実測

- **検証日**: 2026-09-05
- **対象**: 自宅ワーカー(Issue #49)から出力バケット(`eu-south-2`)への配信版動画アップロードの
  実効スループット。アップロード中の進捗バー・残り時間推定(Issue #202フォローアップ、
  `apps/web/src/hooks/jobProgressBudget.ts`)の初期値・悲観バジェットの根拠にする。
- **環境**: 本番の自宅ワーカー(HakataMatrix、Issue #49)、CloudWatch Logs `/sattori/worker`
  (ログストリーム名=jobId)とDynamoDB `JobsTable`(`workerKind=home`・`status=done`)を突き合わせ。
- **結論**: 大きめのファイル(100MB超)では概ね10〜12MB/s(80〜99Mbps)に収束する、非常に安定した
  実測値が得られた。悲観バジェットの初期値には並行トラフィック等での劣化を見込みマージンを取る。

`worker/entrypoint.py`が本番で書き出す標準出力(CloudWatch Logsへ転送)には、アップロード開始時の
`動画をアップロード: s3://...`ログとジョブ完了時の`[status] {jobId} -> done`ログが両方含まれる。
このPRで`status="uploading"`への遷移ログ自体は本番未投入(このブランチでの新規追加のため)だが、
アップロード開始ログは元から存在するため、これと完了ログの時刻差で実質的なアップロード所要時間を
逆算できる。

## 目的

アップロード中の進捗バー・残り時間推定を実装するにあたり、悲観バジェット
(`MIN_UPLOAD_BYTES_PER_SECOND`)とライブ推定の初期値(`DEFAULT_UPLOAD_RATE_BYTES_PER_SECOND`)に
使う自宅ワーカーの実効アップロード帯域を、当てずっぽうではなく本番実績から決める。

## 方法

1. DynamoDB `JobsTable`を`workerKind=home AND status=done`でスキャンし、`outputBytes720p`
   (無ければ`outputBytes`、th20・低速録画等の1本集約ケース)を配信版動画の実サイズとして取得。
2. 各ジョブのCloudWatch Logsストリーム(=jobId)から以下2つのログの発生時刻を取得:
   - 開始点: `動画をアップロード: s3://.../videos/{jobId}_720p.mp4 (X バイト)`
     (`upload_video()`がアップロード呼び出し直前に出すログ)
   - 終了点: `[status] {jobId} -> done`(`update_status()`がDynamoDB更新成功後に出すログ)
3. `所要時間 = 終了時刻 - 開始時刻`、`実効速度 = 配信版動画サイズ / 所要時間` を算出。
4. 両方のログが取れた41件(48件中、複数試行が同一ログストリームに混在する等で7件除外)を対象に
   分布を集計。

## 結果

| 指標 | 値 |
| --- | --- |
| サンプル数 | 41件(全48件中) |
| ファイルサイズ範囲 | 約31MB 〜 約5.7GB |
| 中央値 | 11.24 MB/s(約89.9 Mbps) |
| 平均値 | 10.53 MB/s(約84.2 Mbps) |
| 25パーセンタイル | 10.57 MB/s |
| 75パーセンタイル | 11.67 MB/s |
| 10パーセンタイル | 9.83 MB/s |
| 最小値 | 3.25 MB/s(ファイルサイズ36MBの小規模ジョブ) |

ファイルサイズが100MBを超えるジョブ(41件中37件)に限ると9.8〜12.4 MB/sの狭い帯に収まり、
非常に安定している。50MB未満の4件だけが3.25〜5.75 MB/sと明確に低く、固定オーバーヘッド
(posterフレーム抽出のffmpegシーク・TCPスロースタート等)がファイルサイズに対して無視できない
比率を占めるための見かけ上の低速化と考えられる。

## 考察・既知の限界

- 「終了点」の`-> done`ログは、配信版動画アップロード完了後の**poster画像抽出・アップロード**
  (Issue #171、小さいJPEG)や、1本集約ケースでの生データ削除も含んだ後に出る。そのため
  この方法で求めた所要時間は実際のアップロード時間よりわずかに長く、実効速度はわずかに
  **過小評価(悲観的)側**に倒れている——進捗推定の初期値として使う分には安全な方向のずれ。
- 自宅ワーカーは物理的に1台(HakataMatrix)のみで運用されている前提の数値であり、
  他の物理環境への一般化はできない。将来ワーカーを追加・移設した場合はこの値を再測定すること。
- 除外した7件は、Step Functionsのリトライで同一ログストリームに複数試行のログが混在し
  マーカーの対応付けが一意にできなかったケース。速度分布への系統的な偏りがあるとは考えにくいが、
  未検証。
- この測定は自宅回線が他のトラフィックと競合していない状態での実測値であり、実使用時に
  他の通信(録画中の音声ストリーミング等は無関係だが、家庭内の他機器の利用など)と競合すると
  実効速度は下がりうる。`apps/web/src/hooks/jobProgressBudget.ts`の悲観バジェットには
  この10パーセンタイル(9.83 MB/s)よりさらに下のマージンを持たせた値を採用する。
