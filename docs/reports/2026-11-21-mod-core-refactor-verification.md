- 「重複率」は録画開始15〜45秒の自動チェックの値(低速録画では高くなるのが正常)。「A/V残差」は同期マーカーによる
  mux後の検証の残差。「尺÷(推定尺×倍率)」の録画尺はメニュー操作と終了後の数秒を含む生の録画の長さ。
- 新旧で比べた6タイトルは、尺の比が±0.4%以内、A/V残差は±1ms以内で一致した。th12 の重複率(5.1%/2.8%)の差は、
  並行していた録画(新は th13、旧は th11)とのCPUの取り合いの範囲で、閾値30%からは遠い。
- **th07 の不一致は退行ではない**: 変更前のMODでも不一致になった。最終観測値は 168164940 / 168165040
  (変更前)で、記録スコア 168165080 の直前まで進んでからゲームオーバーの演出に入っており、統合テストの README に
  ある「1秒間隔のポーリングが最終スコアを取りこぼす」既知の個体差と同じ形だった(本番の GPU 3倍速の録画では一致)。
- 低速録画(今回は th06nc・th15・th20)では `time_scale::StartupTimeout()` で起動待ちの上限が伸びる(0076 の決定4)が、
  どの録画も元の上限(30〜120秒)より前に起動を終えたので、伸ばしたことの影響は出ていない。

## 3. EC2 での録画(実験ジョブ、`docs/runbooks/experiment-workflow.md`)

本番の MOD はタイトル資産(S3)から取るので、本番のタイトル資産を変えずに試すため、このブランチのワーカーイメージに
このブランチの MOD を焼き込み、`SATTORI_MOD_DIR` でそちらを使う検証用イメージ(`exp-modcore393-1`、検証用ECR)を
作った(このイメージ専用の作りで、リポジトリには入れていない)。

| タイトル | 段 | 結果 | 試行 | 重複率% | A/V残差 | スコア |
|---|---|---|---|---|---|---|
| th15 | `c7i.4xlarge` CPU 1/3倍速(本番の CPU の段の Extra) | done | 1 | 80.3 | +0.2ms | 一致 |
| th06nc | `c7i.2xlarge` CPU 1/2倍速(本番の CPU の段) | done | 1 | 59.3 | +1.0ms | 一致 |
| th12 | `c7i.2xlarge` CPU 等倍(本番の CPU の段) | done | 1 | 0.3 | +0.4ms | 一致 |

- 3本とも `timedOut=false`。th06nc の MOD ログで `RuntimeConfig: FPS_LIMIT_TARGET_HZ=30.00 ... MENU_WAIT_EXTRA_SCALE=1.00`
  を確認した(`TH06NC_TIME_SCALE` を渡さなくても、メニュー待ちが1/2倍速に合わせて伸びて操作が完走した)。
- **GPU の段(th12・th06nc の2倍速)は未検証**: 同じイメージで `g6f.2xlarge` の実験ジョブを投げたが、eu-south-2 の
  Spot 在庫切れで `capacity_exhausted` になった。検証用イメージは一次リージョンでしか使えないので、フォールバック先
  (eu-north-1)でも試せない。倍速録画で変わるのは Present の上限(バス経由になった)・QPC偽装・メニュー待ちの値の
  出所で、どれも単体テストとローカルの低速録画で同じ経路を通っているが、GPU の実機では確かめていない。
