# CPUクーラー換装(簡易水冷→空冷)後の自宅ワーカー健全性確認(Issue #162)

- **検証日**: 2026-08-26
- **対象**: 自宅ワーカー(`HakataMatrix`)のCPUクーラー換装後、新たにジョブを受け付けられる状態か。
  th20の低速録画・等倍録画・低速録画2並列を実施
- **環境**: HakataMatrix(AMD Ryzen 7 5700X、8コア16スレッド/94GiB)。CPUクーラーを経年劣化した
  簡易水冷から新品の空冷ファンへ換装済み(`~/docs/hardware-fancontrol.md`)。録画は`worker/`を
  ネットワーク不要のローカル実行(`worker/README.md` §11)で直接実行、Docker/AWSは未使用
- **結論**: **サーマルスロットリングは解消した**(録画中もTctl最大61℃、旧障害時の90℃台後半から
  劇的に改善)。ただし**th20の低速録画2並列で、温度と無関係の新規バグ**(難易度確認画面から
  ステージ開始への遷移でジョブの一方が高確率で完全にフリーズする)を発見した

touhou-recorder reports/51(`sattori-dev#162`)でCPU冷却系のハードウェア障害によるサーマル
スロットリングが特定され、ユーザーがCPUクーラーを空冷へ換装した。換装後、自宅ワーカーが
安全に稼働を再開できるか、th20(低速録画対応の唯一のタイトル、`worker/README.md` §7)で
温度・録画品質の両面を実機確認した。

## 目的

1. CPUクーラー換装により、touhou-recorder reports/51で確認された高温状態(無負荷でも
   Tctl 82〜88℃、高負荷で95℃前後に張り付く)が解消しているか。
2. 低速録画1並列・等倍録画1並列・低速録画2並列のいずれも、録画品質(重複フレーム率・
   リトライ回数)に問題が無いか。

## 方法

`worker/record_th20.py`をローカル実行し、10秒間隔で`sensors`(`k10temp`のTctl/Tccd1)を
CSVへ記録するシェルスクリプトを並行して回した。

```bash
FPS_LIMIT_TARGET_HZ=30 python3 record_th20.py --replay-path games/th20/replay/th20_01.rpy \
  --output runs/162_thermal_verify/slowmo_single/video.mp4 --progress-dir .../progress
# 等倍は FPS_LIMIT_TARGET_HZ を付けない
# 2並列は2本目に SATTORI_DISPLAY=:195 / SATTORI_INSTANCE_DIR / WINEPREFIX(複製したprefix)を
# 個別に指定し、同一ホストでのXvfb・wineserverの衝突を避けた(本番はコンテナ分離で自動的に
# 避けられるが、ローカル直接実行では手動で分離する必要がある)
```

以下の5回を実施(2並列は再現性確認のため2回実施):

| フェーズ | リプレイ | 難易度 |
| --- | --- | --- |
| 低速録画・単独 | `th20_01.rpy`(Stage All Clear) | Hard |
| 等倍録画・単独(1回目) | `th20_02.rpy` | Easy(描画負荷が低く参考限定、後述) |
| 低速録画・2並列(1回目) | `th20_01.rpy` + `th20_03.rpy` | Hard / Lunatic |
| 等倍録画・単独(2回目、やり直し) | `th20_04.rpy`(未クリア) | Lunatic |
| 低速録画・2並列(2回目、再現確認) | `th20_01.rpy` + `th20_03.rpy` | Hard / Lunatic |

等倍録画1回目に使った`th20_02.rpy`はEasy難易度で描画負荷が低く、サーマル検証としての
参考度が低かったため、描画負荷の高いLunaticリプレイ(`th20_04.rpy`)で2回目を実施した。

## 結果

### 温度(Tctl、10秒間隔サンプルの区間内最大値/平均値)

| フェーズ | サンプル数 | 最大 | 平均 |
| --- | --- | --- | --- |
| 低速録画・単独(th20_01) | 336(56分) | 61.0℃ | 52.9℃ |
| 等倍録画・単独(th20_02, Easy) | 174(29分) | 60.9℃ | 57.0℃ |
| 低速録画・2並列(1回目) | 27(4.5分、早期終了のため短い) | 59.0℃ | 50.7℃ |
| 等倍録画・単独(th20_04, Lunatic) | 185(31分) | 60.6℃ | 57.4℃ |
| 低速録画・2並列(2回目) | 28(4.7分、早期終了のため短い) | 57.9℃ | 50.2℃ |

検証開始前のアイドル温度は37〜40℃(`sensors`実測)。全フェーズを通じてTctlは**最大でも
61℃**に収まり、touhou-recorder reports/51が報告した障害時の値(無負荷でも82〜88℃、
高負荷で95℃前後に張り付き、負荷除去後も長時間下がらない)とは比較にならないほど改善して
いる。**サーマルスロットリングは解消したと判断できる。**

### 録画品質(重複フレーム率・リトライ回数)

| ジョブ | 試行回数 | 結果 | 重複フレーム率(録画開始15秒以降) | 録画時間 |
| --- | --- | --- | --- | --- |
| 低速単独(th20_01) | 1/3で成功 | 正常 | 50.0%(閾値65.0%、等倍換算25.0%/30.0%) | 3340.0秒 |
| 等倍単独(th20_02) | 1/3で成功 | 正常 | 1.6%(閾値30.0%) | 1707.9秒 |
| 等倍単独(th20_04, Lunatic) | 1/3で成功 | 正常 | 1.6%(閾値30.0%) | 1791.4秒 |
| 2並列1回目・A(th20_01) | 3/3失敗 | **異常** | ― | 各試行62〜75秒で処理落ち早期検知 |
| 2並列1回目・B(th20_03) | 3/3目で成功 | 正常(尺は後述) | 50.0%(閾値65.0%) | 100.3秒 |
| 2並列2回目・A(th20_01) | 3/3目で成功 | 正常(尺は後述) | 49.8%(閾値65.0%) | 100.2秒 |
| 2並列2回目・B(th20_03) | 3/3失敗 | **異常** | ― | 各試行62〜75秒で処理落ち早期検知 |

単独録画(低速・等倍とも、Easy/Lunatic問わず)はいずれも**初回試行で正常終了**し、温度・
重複フレーム率のいずれにも異常はなかった。

### 2並列で発見した新規バグ: 難易度確認画面でのフリーズ

2並列は2回とも、**どちらか一方のジョブが高確率(6試行中4試行)で完全にフリーズし**、
「処理落ちの早期検知」(`stutter probe: dup_fraction=1.00`、リプレイ再生開始とみなした
時刻から**常に34.3〜34.9秒後**という酷似したタイミング)でリトライになった。失敗した
フレームを目視確認したところ、フリーズ位置は**難易度確認画面(「HARD」「LUNATIC」の
ロード演出)のままステージ1が開始しない状態**だった(`/tmp/frames_check/a_30s.png`等、
本レポートには添付していない)。この間、ホストCPU使用率はアイドル同然(`top`実測で
90%超idle)で、**スピンではなく完全なハング**に見える。

成功した側のジョブも、記録された尺は**わずか約100秒**(低速録画なので実ゲーム内時間は
約50秒相当)しかなく、フリーズには至らないもののステージ1着手直後で「画面が一定時間
変化しなくなったため」自然終了と誤判定されている(フレーム確認で、スコア表示のある
実際のゲームプレイ画面まで到達していることは確認できた)。

**どちらのジョブ(display :95側かdisplay :195側か)が失敗するかは2回の検証で入れ替わって
おり、特定のdisplay番号やWINEPREFIXコピーに起因する問題ではなさそうである。**

## 考察・既知の限界

- **クーラー換装によるサーマルスロットリングの解消は実測で確認できた。** 旧障害
  (touhou-recorder reports/51)との比較で、アイドル・高負荷とも温度が40℃前後低下している。
- **一方で、th20の低速録画2並列に温度と無関係の新規バグが見つかった。** 難易度確認画面から
  ステージ開始への遷移で、2並列時に高確率(今回のサンプルでは6試行中4試行)で一方のジョブが
  完全にハングする。原因は未特定(GPU/wineserverの共有資源競合、`fps_limiter_hook`の
  `QueryPerformanceCounter`ベースのタイミング計算が2プロセス同時実行下のスケジューリング
  遅延で破綻する、等の仮説はあるが本検証では切り分けていない)。**この不具合は
  `HOME_WORKER_MAX_CONCURRENCY`を2以上に保ったまま自宅ワーカーを復帰させた場合、th20が
  2並列で同時に走った際に高確率で失敗(自動リトライの3回を使い切る)し得ることを意味する。**
  別Issue(#179)として起票し、原因調査は今後の課題とする。
- サンプル数は各条件1〜2回のみで、統計的な確度は低い。特に2並列の「6試行中4試行で失敗」は
  試行回数が少なく、真の失敗率の推定には使えない。
- 本検証はローカル直接実行(Docker非経由)。本番のコンテナ分離環境(home-worker経由)で同じ
  頻度で再現するかは未確認(ただしWINEPREFIX・display・pulse-sinkは分離済みで実行したため、
  ローカル特有の共有状態が原因である可能性は低いと考えている)。
- th20以外のタイトルでの2並列動作は本検証の対象外(温度面は
  [`2026-08-09-home-worker-parallel-recording.md`](2026-08-09-home-worker-parallel-recording.md)
  でth07/th08の組み合わせを別途検証済み)。
- 重複フレーム率は録画開始15〜45秒の30秒スポットのみの値であり、全編の代表値ではない
  (Issue #93、`docs/known-limitations.md` §3)。
