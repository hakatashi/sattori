# ドキュメント運用ガイドライン

このリポジトリで「どこに何を書くか」を決めるための判断基準。ドキュメントを性質で
4分類し、**書き換えるファイル（参照仕様・手順書）には追記せず、追記型の情報
（決定と根拠・検証記録）は1件1ファイルで増やす**という原則で肥大化を構造的に止める。
新しく何かを書く前に §3「追記先の判断フロー」を見ること。

## 1. なぜこの規約があるか

このプロジェクトのドキュメントは一度肥大化と分割を経験している。当初はすべてを
`AGENTS.md` に書いていたが重くなりすぎたため、「常に必要な情報だけを残して各パッケージの
`README.md` へ分割する」という再編を行った。しかしその後も仕様や知見が溜まるたびに
各 README へ追記し続けた結果、今度は各 README が肥大化した（Issue #112）。

**前回の分割の軸は「どのパッケージの話か」という場所だけで、「情報の性質」になって
いなかった**ことが原因である。1つの README の中に、上書きされて増えない情報
（構成表・環境変数・API 契約）と、本質的に消せず増え続ける情報（なぜこうしたかの根拠・
実機検証の記録）が同居していた。後者は同じファイルに書き続ける限り必ず膨らむ。

したがって本ガイドラインは「短く書け」という規律ではなく、**追記型の情報が既存ファイルを
太らせない置き場所を用意する**ことを目的とする。規律は破れるが、置き場所が分かれていれば
追記しても既存ファイルは太らない。

## 2. ドキュメントの4分類

| | 種類 | 中身の例 | 置き場所 | 更新の仕方 |
| --- | --- | --- | --- | --- |
| ① | 参照仕様（今こうなっている） | 構成表、環境変数、API 契約、ルーティング、状態機械 | 各パッケージの `README.md` | **書き換える**（追記しない） |
| ② | 決定と根拠（なぜこうしたか・踏んだ地雷） | th20 対応の技術的背景、thprac の注意点、`tar -h` 禁止 | `docs/decisions/` | 1決定1ファイルで**新規追加**。既存は原則不変 |
| ③ | 手順書 | 資産の S3 アップロード、WINEPREFIX 作成、MOD ビルド、デプロイ | `docs/runbooks/` または Skill | 書き換える |
| ④ | 検証記録 | 実機録画の重複フレーム率、CPU 温度実測、コスト調査 | `docs/reports/` | 1検証1ファイルで**新規追加**。不変 |

分類の判断がつかないときは「**この記述は将来書き換えられるか、それとも積み上がるか**」で
考える。書き換えられる（古くなったら消える）なら ①③、積み上がる（古くなっても価値が
残る）なら ②④ である。

②と④の違いは「決めたこと」か「測ったこと」か。実機検証をして、その結果として何かを
決めた場合は**両方書く** —— 測定の詳細は `docs/reports/` に、そこから何を決めたかは
`docs/decisions/` に置き、決定記録から検証記録へリンクする。

## 3. 追記先の判断フロー

新しく書きたいことが出てきたら、上から順に当てはめる。

1. **現在の仕様が変わった**（実装を変えた、環境変数が増えた、API が変わった）
   → 該当パッケージの `README.md` を**書き換える**。古い記述の隣に新しい記述を足さない。
2. **なぜそうしたのかの根拠・踏んだ地雷・やってはいけないこと**
   → `docs/decisions/` に**新規ファイル**を作る。既存の決定記録は編集しない
   （覆す場合は §5.2 の「置き換え」）。
3. **実機検証・実測・調査をした**
   → `docs/reports/` に**新規ファイル**を作る。一度書いたら不変。
4. **手順が増えた・変わった**
   → `docs/runbooks/` か Skill（§5.4 で使い分け）。
5. **上のどれでもないが、作業前に必ず知っておく必要がある**
   → `AGENTS.md`。ただし §7 の制約を必ず読むこと。ここに書くのは最後の手段であり、
   「知らずに作業すると誤った変更をしてしまうか」を基準に厳しく選別する。

よくある誤りは、②を①のファイルに書いてしまうことである。「この設定はこうなっている
（① 仕様）」の直後に「なぜならこういう不具合があって……（② 根拠）」と続けたくなるが、
根拠の部分は別ファイルへ出してリンクで繋ぐ（§5.5）。仕様は数行で変わるが、根拠は
永久に積み上がるためである。

## 4. ディレクトリ構成

```
AGENTS.md                       # ① 全体の地図。常時ロード対象（§7）
CLAUDE.md                       # @AGENTS.md の参照のみ
README.md                       # サービスの紹介（外部向け）
docs/
  documentation-guidelines.md   # 本ファイル
  known-limitations.md          # 既知の制約・未実装事項の索引
  decisions/                    # ② 軽量 ADR。1決定1ファイル・連番・原則不変
    README.md                   #    一覧表（番号 / 日付 / 対象 / 状態）
    TEMPLATE.md                 #    コピーして書き始める雛形
    NNNN-kebab-case-title.md
  reports/                      # ④ 検証記録。1検証1ファイル・不変
    README.md / TEMPLATE.md
    YYYY-MM-DD-kebab-case-title.md
  runbooks/                     # ③ 手順書
  research/                     # ④ のうち長大な調査レポート
    README.md
    aws-region-cost-analysis.md
<package>/
  README.md                     # ① そのパッケージの参照仕様
  docs/                         # ② のうち、パッケージ内で軸を切った方が自然なもの
    titles/th20.md              #    例: worker のタイトル別背景
```

`docs/decisions/` と `docs/reports/` は横断的な受け皿である。一方、**同じ軸で確実に
増えていくことが分かっている情報は、パッケージ配下に専用ディレクトリを切ってよい**
（`worker/docs/titles/` が典型で、対応タイトルが増えるたびに1ファイル増える）。
判断基準は「その軸で今後も件数が増え続けるか」であり、増えるなら README の表に
1行足すだけで済む構造にする。

`touhou-recorder`（PoC リポジトリ）の `reports/NN` は**別リポジトリのもので、
こちらへは移設しない**。混同を避けるため、あちらは連番、こちらの `docs/reports/` は
日付ベースの命名とする。このリポジトリの文書から参照する場合は
「touhou-recorder reports/50」のようにリポジトリ名を添えること。

## 5. 書式規約

### 5.1 全ファイル共通

- **ファイル冒頭に3行程度のサマリを置く**。見出しの直後、目次より前。エージェントが
  全文を読む前に当たりを付けられ、人間も同じ恩恵を受ける。「何が書いてあるか」だけでなく
  「どういうときに読むべきか」を含めると効果が高い。
- **150行を超えるファイルには目次を置く**。GitHub の自動目次は折りたたまれており、
  ファイルを読み込むエージェントには見えないため、本文に明示的に書く。
- 見出しには番号を振る（`## 3. 追記先の判断フロー`）。他ファイルから
  「§3」で参照できるようにするため。**節番号を変える編集をしたら、その節を参照している
  箇所を `grep -rn "§"` で洗って追随させること**。
- 1行はおおむね90文字以内で折り返す（既存ファイルの慣習に合わせる）。

### 5.2 決定記録（`docs/decisions/`）

ファイル名は `NNNN-kebab-case-title.md`（4桁の連番）。番号は既存の最大値+1を採る。
日付順ではなく作成順なので、番号が飛んでいても詰めない。雛形は
[`decisions/TEMPLATE.md`](decisions/TEMPLATE.md)（下記と同内容）。

```markdown
# NNNN. <決定の内容を一文で>

- **状態**: 有効 ／ `NNNN` によって置き換え済み
- **決定日**: YYYY-MM-DD
- **対象**: worker / apps/api / infra など影響するパッケージ
- **関連**: Issue #NN、PR #NN、touhou-recorder reports/NN

<3行程度のサマリ。何を決めたか、それを知らないと何を壊すか>

## 背景

何が問題だったか。どういう制約下での判断か。

## 決定

何を決めたか。実装上どう表れているか（ファイル名・関数名を挙げる）。

## 根拠

なぜそう決めたか。**実機検証やレポートへの参照を必ず添える**
（`docs/reports/YYYY-MM-DD-....md`、touhou-recorder reports/NN など）。

## 採らなかった選択肢

検討したが選ばなかった案と、その理由。「昔なぜそうしなかったか」は
再検討時に最も価値が高い情報なので省略しないこと。

## 影響範囲

この決定に依存しているコード・ドキュメント。ここを変えるときに何を確認すべきか。
```

**決定が覆された場合も、元のファイルは削除・書き換えしない**。`状態` を
「`NNNN` によって置き換え済み」に変え、新しい番号で新規ファイルを作る。覆された決定と
その理由が残っていること自体が、同じ検討を繰り返さないための情報である。

`docs/decisions/README.md` に一覧表（番号 / 日付 / 対象 / 状態 / 一行要約）を置く。
**エージェントはまずこの一覧だけを読み、関係する1件だけを開く**運用を前提とするため、
新規追加時は必ず一覧にも1行足すこと。

### 5.3 検証記録（`docs/reports/`）

ファイル名は `YYYY-MM-DD-kebab-case-title.md`（検証を実施した日付）。雛形は
[`reports/TEMPLATE.md`](reports/TEMPLATE.md)（下記と同内容）。

```markdown
# <検証の対象を一文で>

- **検証日**: YYYY-MM-DD
- **対象**: 何を検証したか（タイトル・インスタンスタイプ・構成）
- **環境**: 実行環境（リージョン・インスタンスタイプ・自宅マシンのスペックなど）
- **結論**: 一行

<3行程度のサマリ>

## 目的

## 方法

再現に必要な手順・コマンド・パラメータ。

## 結果

数値は表で。**測定条件（何秒間の測定か、何回の平均か）を必ず併記する**。

## 考察・既知の限界

この測定から言えないこと。サンプル数や測定範囲の制約。
```

**検証記録は一度書いたら不変**。後から分かったことは新しいファイルを足し、必要なら
古い記録の冒頭に「この結果は `YYYY-MM-DD-...` で更新された」の1行だけを追記する。

長大な調査レポート（数百行規模で、単一の調査として完結しているもの）は
`docs/research/` に置く。`docs/reports/` との違いは規模と粒度だけなので、迷ったら
`docs/reports/` でよい。

### 5.4 手順書（`docs/runbooks/` と Skill）

同じ ③ でも置き場所が2つある。使い分けは次の通り。

- **Skill**（`.claude/skills/` 等）: エージェントに実行させる定型作業。Claude Code の
  Skill は frontmatter の `description` 1行だけが常時ロードされ、本文は必要になった
  時にのみ読まれるため、デプロイ手順のように「そのときにしか要らないが手順は長い」
  ものに最も適合する。
- **`docs/runbooks/`**: 人間が読んで判断しながら進める手順、障害対応、Skill にするほど
  定型化していないもの。

**どちらへ書く場合も、手順だけを写して理由を落とさないこと**。「A の前に B をやる」と
書かれた手順は、理由が書かれていないと必ず逆順で実行される。順序を守らないと事故になる
記述（例: ワーカーイメージの `docker push` を `cdk deploy` より先に行う理由）は、
手順の直前に理由ごと置く。

### 5.5 相互参照

README（①）と決定記録（②）・検証記録（④）は必ず双方向にリンクする。

- **README → decisions**: 仕様の記述の直後に1行で添える。
  例: `> なぜこの構成なのかは [docs/decisions/0018-thprac-post-attach.md](...) 参照。`
- **decisions → README**: 「影響範囲」節に、その決定に依存しているファイル・
  ドキュメントを列挙する。
- **decisions → reports**: 「根拠」節から参照する。

**リンクが無いと、エージェントは決定記録の存在に気づけないまま README の仕様だけを読み、
推測で変更してしまう**。これは `AGENTS.md`「3. 常に踏まえておくべき設計判断」が
最も警戒している事態そのものであり、分割そのものよりリンクを張ることの方が重要である。
リンクを張らずに情報を別ファイルへ移すのは、削除と大差ない。

## 6. サイズ上限

### 6.1 上限値

| 対象 | 上限 | 根拠 |
| --- | ---: | --- |
| `AGENTS.md` | 150行 / 12 KB | 毎セッション無条件にロードされる（§7） |
| 各パッケージの `README.md` | 300行 | 「そのパッケージを触る」だけで開くファイル |
| `packages/replay-parser/README.md` | 500行 | npm 公開パッケージで、利用者向け API リファレンスを兼ねる。外部リンクで分割できないため別枠 |
| `docs/` 配下 | 500行 | 必要なときに1件だけ開く前提 |
| `docs/reports/` 配下 | 上限なし | 1件が長いこと自体は問題ない。不変で、必要な人が1件だけ開く |
| `docs/research/` 配下 | 上限なし | 同上 |

上限の **80% を超えたら警告**を出す（CI での機械チェックは Issue #118）。上限に達して
から慌てて分割するより、余裕のあるうちに気づける方が望ましい。

検査対象外: `node_modules` / `dist` / `cdk.out` / `.pytest_cache` などの生成物。

### 6.2 超過したときの分割の軸

上限を超えたら、**まず §2 の分類で仕分ける**。多くの場合、超過分は ② と ④ であり、
これらを `docs/decisions/` と `docs/reports/` へ出すだけで収まる。

それでも ① だけで超過する場合は、次の順で軸を探す。

1. **件数に比例して増える軸があるか**（タイトル別・エンドポイント別・画面別）。
   あるならその軸で1件1ファイルに切り出し、README には表の1行だけを残す。
   将来同じ軸で増え続ける分がまとめて隔離できるので、最も効果が高い。
2. **読者が違うか**（利用者向け / 実装者向け / 運用者向け）。違うなら読者で分ける。
3. どちらでもないなら、単純に大きい節を `<package>/docs/` へ切り出す。

**分割の際は §5.5 のリンクを必ず張る**。また、内容そのものの書き直しや情報の削除は
分割と同時にやらないこと（何が失われたか追えなくなる）。

## 7. 常時ロードされるファイルの特別扱い

`AGENTS.md` は `CLAUDE.md`（`@AGENTS.md`）経由で**毎セッション無条件にコンテキストへ
載る**。ここに書かれた内容は、その情報が不要な作業をしているときも常にコストを払う。

したがって `AGENTS.md` には次の制約を課す。

- **追記型の情報（② 決定と根拠 / ④ 検証記録 / 既知の制約の列挙）を置いてはならない**。
  これらは放っておくと単調増加するため、常時ロードされるファイルとは相性が最悪である。
- 書いてよいのは、**パッケージを問わず常に踏まえておくべき情報**だけ。すなわち
  全体アーキテクチャの地図、確定済みの全体方針、各詳細ドキュメントへの導線。
- 個別の事実を書くかどうかは「**知らずに作業すると誤った変更をしてしまうか**」で判断する。
  「知っていると便利」程度なら詳細ドキュメント側に置き、`AGENTS.md` からはリンクだけ張る。
- 上限は 150行 / 12 KB（§6.1）。

同じことが `CLAUDE.local.md`（gitignore 済みだが同様に常時ロードされる）にも当てはまる。
こちらはほぼ全体が ③ の手順書だったため、`.claude/skills/` の Skill 3本へ移設済み
（§5.4、Issue #114）。

---

本ガイドライン自体は ③（手順書・運用ルール）に分類され、**書き換えて更新する**。
運用してみて機能しなかった規約は、追記して例外を積むのではなく本文を書き換えること。
