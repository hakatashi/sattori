# 0082. フレーム同期の理論尺ずれは、再生区間がほぼ無い場合だけ失敗にし、それ以外はデシンク警告として配信する

- **状態**: 有効
- **決定日**: 2026-11-23
- **対象**: worker / docs
- **関連**: [`0077`](0077-worker-frame-sync-recording-path.md)(一部を置き換え)、Issue #103・#324、
  `docs/known-limitations.md` §「デシンクの自動検知は録画後のスコア突き合わせのみ」

フレーム同期の録画で理論尺とのずれが許容(短い側-30%・長い側+10%)を超えても、**再生区間が3秒以上あれば録画は
成功扱いで配信**し、短い側なら`desyncDetected`を立ててユーザーへ注意書きを出す。**これを知らずに「尺ずれ=失敗」へ
戻すと、デシンクで早期終了したリプレイが3回リトライされて`recording_failed`になり、途中までの動画が届かなくなる。**

## 背景

0077は理論尺の許容を超えた録画を一律に破棄(`exit 1`)にしていた。しかしデシンク(リプレイずれ)は決定的で
回復不能な東方共通の問題であり、従来方針(Issue #103)は「自動リトライ・失敗扱いはせず、`desyncDetected`で警告して
録画は配信する」だった。本番のth10ジョブ(2026-11-23)がリプレイずれで早期終了し、`duration_mismatch`で
3回(各約1分)破棄されて失敗した。実時間の経路には尺ずれによる破棄は無く、フレーム同期で入った退行だった。

## 決定

`framesync.record_frame_sync()`で、尺が許容を超えたとき次のとおりにする。

- 再生区間が`DURATION_TOLERANCE_MIN_SEC`(3秒)未満: リプレイが再生されなかったとみなして破棄(`duration_mismatch`)。
- それ以外: `WARNING`を出して成功扱い。**短い側**のずれなら`desyncDetected=True`を書く(スコア照合の結果より優先して
  Trueにする)。長い側のずれはフラグを立てず警告のみ。

## 根拠

- デシンクを失敗扱いにしない既存方針(`known-limitations.md`)との整合。途中までの動画には価値がある。
- 再生されなかった録画は、スコア監視のないタイトル(th09等)では`score_zero`で弾けないため、再生区間の下限で残す。

## 採らなかった選択肢

- **閾値を維持し、再生区間が理論尺の5〜10%以上なら警告配信**: 閾値の根拠が乏しく、今回のように早い段階で
  デシンクした録画が再び失敗しうる。
- **尺ずれの破棄を完全に無くす**: 再生されなかった録画を配信してしまう。

## 影響範囲

`worker/recording/framesync.py`、`worker/tests/test_recording_framesync.py`。0077の「理論尺との比較」の
記述と`known-limitations.md`の該当節はこの決定が優先する。
