# 0035. 録画処理のハング対策は「コード側の後片付け頑健化」+「ベアメタル実行時は外側timeoutラッパー」の二段構えにする

- **状態**: 有効
- **決定日**: 2026-08-27
- **対象**: worker
- **関連**: Issue #186、Issue #179、`docs/reports/2026-08-27-wine-cleanup-hang-incident.md`

録画処理がハングした場合の後片付けは `worker/recording_common.py` 自身で頑健化するが、
それでも防ぎきれない「Pythonプロセス自体が固まる」経路への保険は、コードに組み込まず
**ベアメタル直接実行時に利用者が外側からOSレベルの強制終了ラッパー(`timeout`)を併用する**
運用に留める。Wine自体のsystem D-Bus接続無効化は影響範囲が広いため、この決定では採らず
選択肢として記録するだけにする。

## 背景

2026-08-27、自宅ワーカーのホスト(HakataMatrix)でsystemdがハングし手動電源断からの復旧を
要するインシデントが起きた。原因の一端は、`worker/recording_common.py` の
`kill_wine_and_wait()` がD state(カーネルレベルで割り込み不可能)に陥ったゲームプロセスを
相手にした `wineserver -w` のタイムアウトを捕捉しておらず、例外がリトライループごと
伝播してスクリプトをクラッシュさせ、放置されたWineプロセスがsystem D-Busのメッセージ
キューを枯渇させたことだった(詳細は
[`reports/2026-08-27-wine-cleanup-hang-incident.md`](../reports/2026-08-27-wine-cleanup-hang-incident.md))。

実害を受けたのは本番のDocker経路ではなく、`worker/README.md` §11 のベアメタル直接実行
(手動検証)だけである。Docker経路はジョブ完了後にコンテナごと破棄されるため、ホストへの
プロセスリークが構造的に起こらない。

## 決定

1. **コード側の後片付け(`kill_wine_and_wait()`・`_record_with_retry()`)を頑健化する
   (Issue #186、必須)。** タイムアウト・想定外の例外を捕捉し、最終的に必ず
   WINEPREFIX配下のプロセスをSIGKILLしてから抜ける。これは全実行経路(Docker・
   ベアメタルの両方)に効く。
2. **ベアメタル直接実行時は、利用者が `timeout --kill-after=` 等のOSレベルの強制終了
   ラッパーを併用する運用にする(`worker/README.md` §11に追記)。** コード側の頑健化は
   「録画スクリプト自身がハングを検知できる」経路にしか効かず、Pythonプロセス自体が
   何らかの理由で応答しなくなる経路までは保証できないため、その保険は運用(手動での
   ラッパー併用)に置く。

## 根拠

- 実害があるのはベアメタル直接実行だけであり、そこは開発者本人が手動で叩く経路なので、
  運用上の注意書きで足りる。無条件にコード側へ外側タイムアウトの仕組みを足すと、本番
  Docker経路にも影響する変更になり、正常に長時間かかる録画(低速録画や重い変換)を
  誤って打ち切るリスクを持ち込む。
- コード側の後片付け頑健化(1点目)は「ハングを検知できた場合に後始末を確実にする」
  ものであり、根本的にハング自体を防ぐものではない。両者は独立した保険であり、
  どちらか一方で十分とはみなさない。

## 採らなかった選択肢

- **WineのsystemD-Bus接続そのものを無効化する設定を追加する。** `winedevice.exe`が
  system D-Busへ接続しシグナル購読を持つこと自体が今回のキュー枯渇の引き金になった
  ため、根本的な解決策になり得る。ただし、この設定はDocker本番経路・ベアメタル直接
  実行経路の両方に影響する変更であり、Wine内部のどのコンポーネントがD-Bus経由の
  機能(デバイス変更通知等)に依存しているか未調査のため、この場では決定しない。
  採用するかどうかは改めてユーザーの判断を仰ぐ。
- **録画スクリプト自身にウォッチドッグタイマー(別プロセスからのSIGKILL)を組み込む。**
  効果は外側`timeout`ラッパーとほぼ同じだが、実装・保守のコストが増える上、
  「本番Docker経路では不要」という条件分岐をコードに持ち込むことになり、
  `AGENTS.md` §3の「ワーカーの中に環境差分の分岐を作らない」方針(Issue #49・#68の
  決定と同種)に反する。運用側の対応で足りる限りはそちらを優先する。

## 影響範囲

- `worker/README.md` §11(ベアメタル直接実行の手順)。
- `worker/recording_common.py` の `kill_wine_and_wait()` / `_record_with_retry()`
  (Issue #186)。
- 将来Wineのsystem D-Bus接続無効化を検討する場合は、この決定の「採らなかった選択肢」を
  必ず読んでから着手すること。
