# 0065. 倍速録画の配信版は`fps`フィルタではなく`-r 60 -fps_mode cfr`で60fpsへ揃える

- **状態**: 有効
- **決定日**: 2026-11-07
- **対象**: worker
- **関連**: Issue #322、#301、#266、#316、[`0058`](0058-speedup-recording-on-gpu-instances.md)・
  [`0059`](0059-cut-range-decided-by-recorder.md)・[`0064`](0064-cpu-slow-motion-and-g6-fallback-on-gpu-shortage.md)、
  [`reports/2026-11-07`](../reports/2026-11-07-speedup-delivery-frame-rate.md)、touhou-recorder reports/92

倍速録画(`time_scale<1`)だけ、`convert.build_convert_cmd()`の`fps`フィルタを外し、出力オプションで
60fpsへ揃える。**倍速録画の生映像のptsは信用できない**ので、時刻で枠へ割り当てる方式へ戻さないこと。
等倍・低速録画は`fps=60:start_time=0`のまま。

## 背景

`30874c1`(Issue #266)で等倍化を`-r 60`から`fps=60:start_time=0`へ変えたところ、多くの倍速録画で
配信版のユニークフレームが約45/秒へ落ちた。生映像を見る重複率の検査には出ない。

## 決定

- `time_scale<1`: フィルタでは`setpts`までにとどめ、出力に`-r 60 -fps_mode cfr`を付ける。
- それ以外: 従来どおり`fps=60:start_time=0`。

## 根拠

落ちる原因は生映像のptsにある。**タイトルではなく録画ごとの条件で決まる**(Issue #322の「タイトルや倍率で
出方が違う」の答え)。x11grabの`tbr`の検出結果がエンコーダのtime_baseになるため、録画ごとに次のどれかになる。

| 検出されたtbr | 生映像のpts | fpsフィルタ |
| --- | --- | --- |
| キャプチャfpsと一致(th12 2倍速の例) | 等間隔 | 落ちない |
| `1000k`(1µs) | NVENCのBフレームで`Invalid DTS`になり、muxで書き換わって4枚に1枚が隣と同じ時刻になる | 落ちる |
| キャプチャfpsより低い(180fps録画で120など) | time_baseへの丸めで衝突する | 落ちる |

`-r 60`はフレームの順序を保って枠へ詰めるので、ptsの乱れで絵を捨てない。配信版のユニークフレームは生映像と
ほぼ同数になった(レポート)。ユーザーも検証動画で修正の効果を確認済み(Issue #322のコメント)。

`-fps_mode cfr`を明示するのは、mp4の既定の同期方式に頼らず、CFRと先頭の埋め(#301)を保証するため。カットなしの
録画でも映像・音声とも0秒始まりで、空編集が無いことを確認した。

等倍・低速を変えないのは次の理由から。

- 等倍は`fps`でも落ちない(60枠で等間隔)。
- 低速は`fps`が重複を時刻どおりに間引ける。CFRでは定常的に約+30msずれ、先頭で余分なフレームが出た(th15 1/2・1/3倍速)。

## 採らなかった選択肢

- **`-r 60`のみ(`-fps_mode`なし)**: 検証では結果が同じだが、同期方式がffmpegの既定とmuxerに依存する。
- **`fps=120,setpts,fps=60`や`round=down`**: 効かない(Issue #322の切り分けで約45)。
- **`setpts`で等間隔に振り直す(`N/(60*TB)`など)**: キャプチャの遅れや停止があると音声との同期がずれていく。
- **録画側でptsを直す**: 根本には近いが、既存のチェックポイントを救えず、NVENCの実機検証が要る。`-r 60`は生のptsに
  依存しないので、配信版の修正としてはこれで足りる。

## 影響範囲

- 映像の時刻が後ろへ動く(録画により+8〜+33ms。th06 4倍速は中央値+2.6ms→+33.5ms、p99は+47.7ms)。時間とともに広がることはない。
  音声のフィルタは変えていない。基準はマーカー同期後の生映像のptsで、配信版の映像と音声を直接照合した値ではない(レポート)。
- 配信版のサイズが増える。ユニークフレームが増えるため。libx264で0〜+22%、NVENCで+14〜17%(touhou-recorder reports/92)。
  CloudFrontの無料枠(1TB/月)の見積もりに効く。
- `time_scale<1`の分岐を変えるときは、配信版のユニークフレームを生映像と比べて確認すること。
