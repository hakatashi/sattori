# 0054. Wineクラッシュの検知は理論尺比ではなく`wine.log`の未処理例外で行う

- **状態**: 有効
- **決定日**: 2026-09-19
- **対象**: worker
- **関連**: Issue #267、`docs/reports/2026-09-19-th15-wine-crash-detection-verification.md`

録画中にゲーム本体がWine上でクラッシュしたことを、`wine.log`に現れる`Unhandled`
（`WINE_UNHANDLED_EXCEPTION_MARKER`、`worker/recording/pipeline.py`）で検知し、
`classification="crashed"`として**破棄・リトライする**。**理論尺比（録画時間÷リプレイ
推定時間）による異常検知を使ってはならない** —— デシンクと縮退して、回復不能な現象に
対して無駄なリトライを消費し、価値のある途中までの動画をユーザーへ届けられなくなる。

## 背景

th15 PR(#264)の本番E2E検証中、GPU(g6f)ワーカーで3件立て続けにWineがクラッシュした。
いずれもゲーム画面がフリーズしたまま**画面静止検知が誤って「リプレイ終了」と判定**し、
`classification="good"`・重複フレーム率0.x%で素通りして、途中で切れた動画が`done`として
配信された（`3182b7c9`は理論尺の73%、`a37acd43`は27%）。重複フレーム率チェックも
画面静止検知も、この異常を検知する経路を持っていない。

クラッシュには2つの形態があることが再現実験で判明した。

- **プロセス消滅型**: ゲームプロセスが`Z`を経て消滅し、ウィンドウごと消えて画面が
  真っ黒になる（本番の`3182b7c9`）。
- **ダイアログ残存型**: `AeDebug`設定により`winedbg --auto`が起動してクラッシュ
  ダイアログを表示し、**ゲームプロセスは停止したまま生存し続ける**（本番の`d18b4eb3`）。

## 決定

- `_monitor_until_end()`のポーリングループで`{config.instance_dir}/wine.log`の増分を
  読み、`Unhandled`を含む行が現れたら`crashed=True`として直ちに打ち切る。
  **画面静止・テンプレート照合より先にチェックする** —— クラッシュ後は画面がフリーズ
  するため、後回しにすると静止検知の方が先に成立して`"good"`と誤判定される。
- `attempt_recording()`は`crashed`時に`classification="crashed"`を返す。
- `_record_with_retry()`は`"crashed"`を重複フレーム率チェックより前に判定し、
  **常に破棄してリトライする**。

理論尺比は**リトライの必要条件としては使わない**。クラッシュ検知が成立した後の補助的な
判断材料としてなら使えるが、単独の異常検知には用いない。

## 根拠

実機再現実験（`docs/reports/2026-09-19-th15-wine-crash-detection-verification.md`）で
本番の2形態を両方再現し、検知手段ごとの弁別性を実測した。

| 手段 | 消滅型 | ダイアログ残存型 | ゲーム継続時の誤検知 |
| --- | --- | --- | --- |
| プロセス死亡監視 | 検知 | **検知できない**（`alive=True`） | — |
| プロセスstate監視 | 検知（`Z`） | **検知できない**（`S`のまま） | — |
| `winedbg`出現検知 | **検知できない**（起動しない） | 検知 | — |
| **`wine.log`の`Unhandled`** | **検知** | **検知** | **誤検知しない** |

`Unhandled`は実験2の`err:seh:NtRaiseException Unhandled exception code c0000005`と
実験3の`wine: Unhandled page fault on write access to ...`の両方に含まれ、一方で
ゲームが生存し続けたケース（外部`SIGSEGV`が吸収された`err:seh:segv_handler Got
unexpected trap 0`）には含まれない。

リトライを選ぶ根拠は、クラッシュが**非決定的**であること。本番の`3182b7c9`と
`a37acd43`は同一リプレイなのにクラッシュ地点が595秒と202秒で異なっており、別の
インスタンスで再試行すれば成功しうる（実際ユーザーは手動で再投稿していた）。

## 採らなかった選択肢

- **理論尺比（録画時間÷リプレイ推定時間）による異常検知**: 最初に検討したが不採用。
  **デシンクと原理的に区別できない**。デシンクは東方シリーズ共通の回復不能な現象で、
  リトライしても直らずユーザーも織り込み済みであり、途中までの動画にも価値がある。
  理論尺比で失敗判定すると、デシンクに対して無駄なリトライを消費した挙げ句、録画
  データがユーザーに届かなくなる。実際、保持期間内の理論尺比85%未満8件のうち半数は
  クラッシュではなくデシンク・正常終了だった（同レポート）。
- **プロセス生存監視（`find_live_game_pid()`の流用）**: 既存関数をそのまま使えて実装が
  最も軽いが、ダイアログ残存型では`winedbg`がptraceでアタッチした状態で**プロセスが
  終了せずに残る**ため素通りする。クラッシュ50秒後も`alive=True`だった。
- **プロセスstate監視（`/proc/<pid>/stat`が`t`/`T`になるか）**: 上記の改良案として
  検討したが、実測ではダイアログ残存型でもstateは通常の`S`（sleeping）のままだった。
- **`winedbg`/`werfault`プロセスの出現検知**: ダイアログ残存型には有効だが、消滅型では
  そもそも`winedbg`が起動しない（例外処理中に`stack overflow`が起きてダイアログを出す
  前に二重障害で即死する）。
- **MODの`ScoreMonitor`をハートビートとして使う**: 2形態とも停止するため検知自体は
  可能だが、`worker/mods/common/score_monitor.cpp`は**値が変化したときだけ**ログを
  出すため、正常にリプレイ選択画面へ戻った場合も出力が止まり区別できない。無条件
  ハートビートを足す改修は全12タイトルのDLL再ビルドと資産再アップロードを伴うため、
  `wine.log`監視で足りる現状では見送る。

## 影響範囲

- `worker/recording/pipeline.py`: `WINE_UNHANDLED_EXCEPTION_MARKER`、
  `_monitor_until_end()`（戻り値に`crashed`が増えた）、`attempt_recording()`の
  `classification`、`_record_with_retry()`の破棄条件。
- `classification`の値が`"good"` / `"timeout"` / `"setup_error"`に`"crashed"`を加えた
  4種類になった。この値を見る箇所を増やす場合は`"crashed"`の扱いを明示すること。
- `wine.log`は`_launch_game()`が試行ごとに新規で開くため、増分監視の基準点は
  `_monitor_until_end()`開始時点のファイルサイズとしている。Wineのバージョンが上がって
  未処理例外のメッセージ書式が変わった場合、この検知は静かに効かなくなる（`Unhandled`
  という語自体はWineのソースで長く安定しているが、定期的な確認が要る）。
