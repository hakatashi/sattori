# 0007. IP 単位のレート制限・reCAPTCHA を見送る

- **状態**: 有効
- **決定日**: 2026-07
- **対象**: apps/api / apps/web
- **関連**: Issue #14、Issue #9、Issue #60

濫用対策はメールアドレス単位のレート制限・月間コストガード・キルスイッチで足りており、
**IP 単位のレート制限や reCAPTCHA 等の追加 bot ゲートは意図的に入れていない**。
「bot 対策が無い」のは実装漏れではないので、足す前にこの記録を読むこと。

## 背景

ジョブ1件が EC2 Spot を数十分占有するため、自動化された連投は直接コストになる
（Issue #14）。一方で UI は「動画に詳しくないファンでも迷わず使える」ことを最優先とし、
操作を単純に保つ方針である。

## 決定

濫用対策として実装するのは以下の3つに留め、IP 単位のレート制限・reCAPTCHA・
その他の bot ゲートは**入れない**。

1. **メールアドレス単位のレート制限**（`apps/api/src/rateLimit.ts`、Issue #9）。
   `+` エイリアスを正規化した上で24時間5件まで。
2. **月間コストガード**（`apps/api/src/costGuard.ts`、既定 50 USD）。当月の推定コスト
   合計が閾値に達したら新規受付を止める。
3. **キルスイッチ**（`apps/api/src/settings.ts`、`/admin/settings`）。運用者が手動で
   受付を即座に停止できる。

## 根拠

- **メールアドレスによる認証が既に強力な濫用抑止として機能している**。ジョブを起動する
  には受信できるメールアドレスが要り、jobId はメールにしか現れない
  （[0004](0004-job-id-as-authorization-secret.md)）。使い捨てアドレスで回避しようと
  すれば、その回数ぶんアドレスを用意する手間がかかる。
- **最悪ケースの上限は金額側で閉じている**。コストガードが当月の推定コストで受付を
  止めるので、突破されたとしても被害はその閾値で頭打ちになる。回数ではなく金額で
  判定しているのは、自宅ワーカー（Issue #49）が処理したジョブの EC2 コストが 0 になり
  ジョブ単価が一様でないため。
- reCAPTCHA は**フォームに1ステップ増える**うえ、外部サービスへの依存とプライバシー上の
  説明責任が増える。UI を単純に保つ方針に対して、上記2つを足した先の限界的な効果が
  見合わない。

## 採らなかった選択肢

- **IP 単位のレート制限**。CGNAT や共有回線の巻き添えがある一方、突破は容易
  （IPv6 なら特に）。メール単位の制限に足せるものが小さい。
- **reCAPTCHA / hCaptcha 等**。上記のとおり。
- **AWS WAF**。月1000回規模のトラフィックに対して固定費（WebACL）が割に合わない。

## 影響範囲

- `apps/api/src/rateLimit.ts` / `settings.ts` / `costGuard.ts`
- `docs/known-limitations.md` §6（現状の濫用対策の一覧）
- **この判断は「メールが濫用の律速になる」という前提に立っている**。将来ログイン不要の
  経路を足す・メール認証を省略する変更を入れるなら、この決定ごと再検討すること。
