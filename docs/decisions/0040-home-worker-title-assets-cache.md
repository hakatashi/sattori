# 0040. 自宅ワーカーのタイトル資産はETagキー付き世代ディレクトリでキャッシュする

- **状態**: 有効
- **決定日**: 2026-08-30
- **対象**: worker / home-worker
- **関連**: Issue #104、[`0010`](0010-slow-motion-no-worker-side-branching.md)（ワーカー側の
  分岐を作らない方針）、[`0018`](0018-home-worker-pull-assignment.md)（自宅ワーカーの前提）

自宅ワーカーだけが渡す `TITLE_ASSETS_CACHE_DIR` の有無で、`worker/title_assets.py` が
「ホスト側キャッシュを使う」か「毎回S3から直接ダウンロードする」かを切り替える。キャッシュは
S3オブジェクトのETagをバージョンキーにした世代ディレクトリ(`{cache_dir}/{game}/v-{etag}/`)
とし、世代ディレクトリ自体は内容不変・削除は経過時間だけで判断する保守的な方式にする。

## 背景

自宅ワーカーはAWSリージョン(eu-south-2)から地理的に離れた日本の家庭回線に置かれており、
タイトル資産アーカイブ(ゲーム本体+WINEPREFIX+MOD、数百MB)のダウンロードに毎ジョブ約40秒
かかる(Issue #104の実測)。このデータはタイトルの新規追加・ゲームデータやMODの更新時にしか
変わらないため、自宅マシンのローカルディスクへ永続化して使い回せば、この40秒をほぼゼロに
できる。

一方で制約が2つある。

- **`worker/title_assets.py` に「自宅かEC2か」の分岐を持ち込まない**方針
  ([`0010`](0010-slow-motion-no-worker-side-branching.md)と同じ構造)。EC2はジョブ毎に
  使い捨てのインスタンスなので、キャッシュを持たせても再利用の機会が無く、単にコードパスが
  増えるだけになる。
- 自宅ワーカーは `HOME_WORKER_MAX_CONCURRENCY`(既定2)まで並列で `docker run` するため、
  **同じタイトルの資産取得が同時に2ジョブから走りうる**。さらに `upload-title-assets` skill
  によるタイトル資産の更新は、走っているジョブの有無を待たずに任意のタイミングで実行される
  運用のため、**キャッシュ更新中に別ジョブが古い資産を参照している**状態が起こり得る。

## 決定

- **分岐は環境変数の有無だけで表す**。`docker run` する側(`home-worker/src/runner.ts`)が
  設定時のみホスト側ディレクトリを `-v` でマウントし `TITLE_ASSETS_CACHE_DIR` を渡す
  (`HOME_WORKER_TITLE_ASSETS_CACHE_DIR` 未設定なら何も渡さない)。`title_assets.py` は
  この環境変数の有無だけを見て経路を選ぶ。EC2起動側(`apps/api`)はこの変数を一切扱わない。
- **バージョンキーはS3オブジェクトのETag**。`HeadObject`(本体を転送しない)で取得し、
  ローカルの世代ディレクトリ名 `v-{etag}` と一致すればダウンロードを省略する。アーカイブの
  内容が変われば(通常は非マルチパートアップロードなのでMD5相当が変わる)ETagも変わるため、
  「リモートに変更があれば破棄して更新する」という要件をHEADリクエスト1本で満たせる。
- **世代ディレクトリは内容不変**とし、`.complete` マーカーを展開完了後に書く(展開途中で
  死んだ場合、次回実行時はマーカーが無いため未完了とみなして再ダウンロードから始め直す)。
  ワーカーコンテナは `/app/games/{game}` 等から世代ディレクトリへシンボリックリンクを張る
  だけで、世代ディレクトリ自体を書き換えない。
- **同一タイトルへの同時アクセスは `{game}` 単位のロックファイル(`flock`)で直列化**する。
  ダウンロード・展開が終わるまで後続の同時ジョブは待たされるが、初回だけの一時的なコストで
  あり、2並列という規模では許容できる。
- **古い世代の削除は即時に行わず、`STALE_VERSION_MAX_AGE_SECONDS`(6時間)経過後にのみ**、
  次回のキャッシュ更新のタイミングで掃除する。「参照中かどうか」を追跡しない代わりに、
  自宅ワーカーの最大ジョブ所要時間(低速録画込みで150分、`HOME_WORKER_DRAIN_TIMEOUT_SEC`の
  既定)より十分大きい猶予を置くことで、削除時点でその世代を参照中のジョブが実際に走って
  いる可能性を実務上排除する。
- **`HeadObject` 自体が失敗した場合は、既存の完了済み世代があればそれにフォールバックする**
  (無ければ例外を伝播する)。一時的なネットワーク不調でジョブ全体を失敗させるより、
  やや古い資産でも録画を続行できる方を優先する。

## 根拠

- ETagベースの検証はHeadObjectのみで完結し、本体をダウンロードしない。既存の
  「毎回ダウンロード」からの追加コストがほぼゼロ(ミリ秒オーダーのAPI呼び出し1本)で済む。
- 世代ディレクトリを不変にする設計は、`docker run` する自宅ワーカーの並列実行モデル
  (同時に2コンテナが同じホストディレクトリをマウントしうる)で、書き込み中のディレクトリを
  別ジョブが読みに行く競合を構造的に避けられる。ロック無しで安全にできる範囲を
  「読み取り専用の完成品を指すシンボリックリンクの張り替え」に限定したのが要点。
- 削除を経過時間ベースにしたのは、フルの参照カウント管理(どのジョブがどの世代を使用中かを
  追跡する仕組み)を導入するコストに見合わないと判断したため。タイトル資産の更新頻度は
  低く(新タイトル追加時・MOD更新時のみ)、猶予期間中に一時的に旧世代分のディスク容量を
  余分に使う程度のトレードオフは許容できる。

## 採らなかった選択肢

- **ホスト側ディレクトリを `/app` そのものへマウントする**: ワーカーイメージに焼き込まれた
  録画パイプライン本体(`entrypoint.py` 等)まで隠れてしまい、コンテナが起動不能になる。
  タイトル資産専用のサブパス(`/mnt/sattori-title-assets-cache`)にマウントし、
  `title_assets.py` 側でシンボリックリンクを張る方式にした。
- **キャッシュ更新の度に世代ディレクトリを`rmtree`して同じ場所へ再展開する**(バージョン
  ディレクトリを分けない): 実装は単純になるが、更新中に別ジョブがそのディレクトリを
  参照していた場合、参照先が消えたり不完全な内容になったりする実害がある。競合の回避を
  ロックの保持時間(ジョブ全体の実行時間)に頼る設計も検討したが、`entrypoint.py`の
  制御フローを大きく作り替える必要があり、世代分離の方が変更範囲が小さい。
- **参照カウントで古い世代を安全確実に削除する**: 正確だが、ジョブのクラッシュ・
  `docker kill` による強制終了(`home-worker/README.md` §3)でカウンタが不整合になる
  リスクがあり、キャッシュの複雑さに見合わないと判断した。経過時間ベースの保守的な削除で
  十分と判断した。
