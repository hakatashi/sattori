# 0004. jobId 自体を認可の秘密値として使う

- **状態**: 有効
- **決定日**: 2026-06
- **対象**: apps/api / apps/web
- **関連**: Issue #9、Issue #14

マジックリンクに別途トークンを載せるのではなく、**jobId（UUID）そのものを秘密値として
扱う**。「メールを確認しないと分からない値」であることが、メール認証と bot / 濫用対策を
同時に満たす。**jobId をログ・URL・エラーメッセージへ気軽に晒さないこと**。

## 背景

ユーザーにアカウント登録をさせない方針（「動画に詳しくないファンでも迷わず使える」ことが
最優先）のため、認証はメールアドレスのマジックリンクのみである。一方でジョブ1件が
EC2 Spot を数十分占有するため、bot に叩かれると直接コストになる。

## 決定

- ジョブは `POST /magic-links` の時点で `status: "pending"` として作られ、**jobId は
  メール本文のリンクにしか現れない**。
- `POST /jobs/{jobId}/start`・`GET /jobs/{jobId}` は、**jobId を知っていること自体を
  認可とする**（`apps/api/src/handlers/startJob.ts`）。追加のトークン検証は無い。
- **管理画面（`/admin/*`）の認可はこれとは別系統**である
  （[0005](0005-admin-auth-ssm-shared-token.md)）。

## 根拠

- jobId は UUID であり、総当たりで当てられる空間ではない。
- 別途トークンを発行すると、`jobId` と `token` の対応をどこかに持ち、失効・再発行の
  経路も作ることになる。**得られる強度は「知らないと辿れない URL」から変わらない**のに、
  状態と分岐だけが増える。
- メールが届く先を確認しないと先へ進めないので、**メール認証と濫用対策が同じ1つの仕組みで
  満たせる**。

## 採らなかった選択肢

- **署名付きトークン（JWT 等）を別途発行する**。上記のとおり、この規模では強度が変わらず
  失効管理だけが増える。
- **アカウント登録・ログイン（Cognito 等）**。UI を単純に保つ方針に真っ向から反する。
- **IP 単位のレート制限・reCAPTCHA を追加する**。
  [0007](0007-no-ip-rate-limit-no-recaptcha.md) を参照。

## 影響範囲

- `apps/api/src/handlers/startJob.ts` / `getJob.ts`（jobId のみで認可する経路）
- `apps/api/src/jobs.ts`（`PENDING_JOB_TTL_MS` = 24時間。誰も踏まなかった `pending`
  ジョブを残さない。これも濫用対策の一部）
- `apps/api/src/rateLimit.ts`（メールアドレス単位のレート制限。jobId の秘密性とは
  独立した、同一メールからの連打への対策）
- `apps/web`（ページBの URL に jobId が入る）
- **この設計に依存して jobId の秘匿が前提になっている**ため、jobId をユーザー向け以外の
  経路（ログ・エラー本文・外部サービス）へ出すときは影響を確認すること。
