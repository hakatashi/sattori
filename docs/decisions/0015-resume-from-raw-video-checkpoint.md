# 0015. リトライ時の再開可否は S3 の生動画の実体で判定し、録画時の倍率はそのオブジェクトに添えて運ぶ

- **状態**: 有効
- **決定日**: 2026-08
- **対象**: worker / apps/api
- **関連**: Issue #11、Issue #49、Issue #68、
  [`0010`](0010-slow-motion-no-worker-side-branching.md)、
  [`0014`](0014-slow-motion-scaling-across-pipeline.md)

Spot 中断・タイムアウトで別のワーカーがリトライしたとき、**何を見て「変換から再開できる」と
判断するか**と、**録画時の再生速度をどう次のワーカーへ伝えるか**の決定。どちらも間違えると
完了済みのジョブを `failed` にしたり、半分の速度の動画をそのまま配信したりする。
`entrypoint.py` の再開判定を触る前に読むこと。

## 背景

`entrypoint.py` は起動直後に S3 の生動画チェックポイント(`videos/{jobId}.mp4`)を確認し、
在れば録画をスキップして配信用変換から再開する。ワーカーは EC2 Spot でも自宅サーバーでも
動き、どちらもリトライで入れ替わりうる(Issue #49)。

## 決定

- **再開できるかは S3 オブジェクトの実体で判定する**。ジョブレコードの `outputPath` は
  使わない。
- **起動時点でジョブが既に `done` なら、何もせず成功として通知する**。
- **録画時の実時間スケールは、生データ自身の S3 オブジェクトメタデータ
  (`sattori-time-scale`)として添えて運ぶ**。再開側で `FPS_LIMIT_TARGET_HZ` を読み直さない。
  メタデータが読めない場合は等倍として続行する。

## 根拠

- **`outputPath` を使ってはいけない理由**: 出力が1本のジョブ(`outputPath` が変換結果を
  指し、生データは `done` 確定後に削除される。`worker/README.md` §4)では、完了済みの
  ジョブがリトライされたときに「再開できる」と誤認し、存在しない生データを取りに行って
  失敗する —— **`done` だったジョブが `failed` へ書き換わる**。
- **`done` なら何もしない理由**: コンテナは完走していたのにハートビートが途切れて
  Step Functions がリトライした場合(自宅ワーカーの claim 取り消し周りで起こりうる、
  `home-worker/README.md` §3)、録画をやり直しても同じものが出来るだけで、実時間を数十分
  捨て完了メールを二重に飛ばす分だけ悪い。
- **倍率をデータ側に持たせる理由**: 自宅ワーカーが低速録画した後にリトライが EC2 へ回ると、
  EC2 には `FPS_LIMIT_TARGET_HZ` が渡らない(低速録画は自宅限定なので、渡さないのが正しい。
  [`0010`](0010-slow-motion-no-worker-side-branching.md))。環境変数を読み直す実装では
  **半分の速度の動画をそのまま等倍として配信してしまう**。倍率をデータ側に持たせておけば、
  どのワーカーが再開しても正しく等倍へ戻せる。
- **メタデータが読めないときに例外にしない理由**: このフィールド導入前のジョブや S3 の
  一時障害で、変換から再開できたはずのジョブを録画からやり直させることになるため。

## 採らなかった選択肢

- **ジョブレコードに再開可否のフラグを持つ**。S3 の実体とレコードが食い違う窓ができ、
  結局実体を確認することになる。
- **録画フェーズ自体を途中から再開する**。中断時点までの生データを繋ぐ仕組みが要り、
  リプレイ再生を途中から始める手段も無い。中断時はそのフェーズを最初からやり直す。
- **リトライ時も同じ種別のワーカーへ回す**。自宅ワーカーは claim されるとは限らず
  (Pull 型)、EC2 へのフォールバックを塞ぐことになる。
