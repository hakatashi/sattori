# 東方紅魔郷: Classic / New Classic のリプレイフォーマット解析

調査日: 2026-09-10 / 対象: 2026-09-10 発売の紅魔郷リメイク2作 /
結果を実装した場所: `packages/replay-parser/src/games/th06.ts`

**結論**: 両作とも th06（東方紅魔郷 1.02h）のリプレイ形式の直系の派生で、
マジック `T6RP`・+7 加算鍵による難読化・「固定ヘッダ→7個のステージ別スナップショット→
入力変化イベントの疎ログ」という構造をそのまま受け継いでいた。違いは
**64bit 化に伴うフィールド幅の拡大**（ステージオフセット・スコアが 8 バイト化、
入力レコードが 8→12 バイト化）と、**New Classic のゲームモード追加に伴う 4 バイトの挿入**
だけである。実機で確認した13件のリプレイのメタ情報（プレイヤー名・日付・機体・難易度・
モード・ステージ別スコア）が**全項目一致**したため、確信的な結果として parser に実装した。

## 1. 何を調べたか

2026-09-10 に「東方紅魔郷: New Classic」「東方紅魔郷: Classic」が発売された。前者は
4K 対応・グラフィック/音楽刷新の改良版（チャレンジモードとスペルプラクティスを追加）、
後者は原作をほぼそのまま現代環境へ移植したもの（ゲーム内表記は ver. 1.03）である。
どちらもゲームディレクトリ下の `replay/th6_xx.rpy` にリプレイを保存する。

発売当日のため内部構造の公開情報は存在せず、
`@sattori/touhou-replay-parser` はこれらを既存の th06 デコーダに流し込んでしまい、
**誤った値を「成功」として返す**状態だった（マジックが `T6RP` で一致するため
`unknown_magic` にすらならない）。本調査でフォーマットを確定させ、
別タイトル（`th06c` / `th06nc`）として正しく解析できるようにした。

## 3. 判明した構造

### 3.1 固定ヘッダ

3変種を並べる。オフセットは復号後のもので、
`鍵` の直後から末尾までが +7 加算鍵で難読化されている（`buffer[i] -= key; key += 7`。
th06 と同じ）。

| 内容 | th06 (1.02h) | th06c (1.03) | th06nc |
| --- | --- | --- | --- |
| マジック `"T6RP"` | 0x00 (4) | 0x00 (4) | 0x00 (4) |
| バージョン `u16` | 0x04 = `0x0102` | 0x04 = `0x0103` | 0x04 = `0x010f` |
| ゲームモード `u8` | — | — | 0x06 |
| 機体 `u8`（0=ReimuA, 1=ReimuB, 2=MarisaA, 3=MarisaB） | 0x06 | 0x06 | 0x07 |
| 難易度（0=Easy…4=Extra） | 0x07 `u8` | 0x07 `u8` | 0x08 `u32` |
| チェックサム `u32` | 0x08 | 0x08 | 0x0c |
| 不明 `u16` | 0x0c | 0x0c | 0x10 |
| 加算鍵 `u8` | 0x0e | 0x0e | 0x12 |
| 記録日時 `char[9]`（`MM/DD/YY` + NUL） | 0x10 | 0x10 | 0x14 |
| プレイヤー名 `char[9]` | 0x19 | 0x19 | 0x1d |
| スコア | 0x24 `u32` | 0x24 `u32` | 0x28 `u64` |
| `1.12 + 処理落ち率` `f32` | 0x28 | 0x28 | 0x30 |
| **処理落ち率(%)** `f32` | 0x2c | 0x2c | 0x34 |
| `2.34 + 処理落ち率` `f32` | 0x30 | 0x30 | 0x38 |
| 不明（全件 `0xffffffff`） | — | — | 0x3c |
| ステージオフセット配列 `[7]` | 0x34 `u32` | 0x38 `u64`（0x34 は 8 バイト境界へのパディング） | 0x40 `u64` |
| ステージデータ開始 | 0x50 | 0x70 | 0x78 |

ステージオフセット配列の意味は th06 と同じで、添字 0〜5 が Stage 1〜6、添字 6 が Extra。
使われなかったステージは 0。

New Classic のゲームモード（0x06）は次の値を確認した。

| 値 | モード | リプレイ選択画面の表示 |
| --- | --- | --- |
| 0 | 標準モード | `Standard` |
| 1 | チャレンジモード | `Challenge` |
| 2 | **未観測** | — |
| 3 | スペルプラクティス | `SpellPr` |

スペルプラクティスのとき、0x08 の 4 バイトは難易度ではなく
**スペルカードの 0 始まりの通し番号**になる（`No.108 獄符「千本の針の山」` のリプレイで
`107` = `0x6b`）。この場合、難易度はファイル中のどこにも見当たらない（§6）。

### 3.2 チェックサム

th06 で知られている「`0x3f000318` + 0x0e 以降の全バイトの総和（`u32` で切り捨て）」が
**Classic でもそのまま通る**。New Classic は種と開始位置が変わっており、
`0x2f10a329` + 0x12 以降の総和になる。いずれも13/13件で厳密一致した。

```
th06   / th06c : checksum(0x08) == (0x3f000318 + Σ decoded[0x0e..]) & 0xffffffff
th06nc         : checksum(0x0c) == (0x2f10a329 + Σ decoded[0x12..]) & 0xffffffff
```

New Classic 側の種 `0x2f10a329` はきりの良い値ではなく、実際の計算式は
（開始位置がさらに手前で、途中に固定値が混ざるなど）これとは違う形をしている可能性がある。
7件で定数として成立することのみ確認した経験則である。parser はチェックサムを検証していない。

### 3.3 ステージ別スナップショット

各ステージオフセットの先頭にある固定長ヘッダ。th06 と同じ並びのまま、
64bit 化でスコアが 8 バイトになり後続がずれている。

| 内容 | th06 | th06c | th06nc |
| --- | --- | --- | --- |
| ステージ開始時スコア | +0x00 `u32` | +0x00 `u32` | +0x00 `u64` |
| 不明（スコアと相関して増える累積値） | +0x04 `u32` | +0x04 `u32` | +0x08 `u32` |
| パワー `u8` | +0x08 | +0x08 | +0x0c |
| 残機 `u8` | +0x09 | +0x09 | +0x0d |
| ボム `u8` | +0x0a | +0x0a | +0x0e |
| 内部ランク `u8` | +0x0b | +0x0b | **無し**（+0x0f は全件 0） |
| ヘッダ全体の大きさ | 0x10 | 0x20 | 0x24 |

New Classic ではランクに相当する位置が全ステージ・全ファイルで 0 であり、
+0x10 の 4 バイトは th6_04 の 3・4 面で `0xffff4000` / `0xffff0204` という負値を取るため
未初期化のゴミと判断した。よって `splits[].additional` は `null` にしてある
（th06/th06c は従来どおり `{ rank: N }`）。

### 3.4 入力ログ

ヘッダの直後から、入力の**変化があったときだけ** 1 レコードを書く疎なログが続く。
th06 は `{ frameNum: u32; inputKey: u16; padding: u16 }` の 8 バイトだったが、
リメイク2作は 12 バイトに拡張され、しかも **`frameNum` がレコードの先頭から末尾へ移動している**。

```c
// th06c / th06nc
struct ReplayDataInput {
    uint32_t inputKey;          // このフレームからの入力状態
    uint32_t previousInputKey;  // 直前のレコードの inputKey と一致する
    uint32_t frameNum;          // ステージ開始からのフレーム数
};
```

終端は th06 と同じ番兵レコード（`frameNum == 9999999`）。番兵の後ろには 8 バイトの
ゼロ埋めが入り、次のステージのオフセットへ繋がる。Classic では最終ステージだけ
`(..., N), (0,0,9999999), (0,0,N), (0,0,9999999)` と番兵が二重に書かれる
（これも th06 と同じ挙動）。New Classic では二重化しない。

## 4. どうやって突き止めたか

順序が分かるように記す。前段は Classic、後段は New Classic。

1. **暗号化は変わっていないと仮定して復号を試した**。Classic は th06 と同じ
   「鍵 = `buffer[0x0e]`、0x0f から +7 加算」でそのまま平文になり、
   `09/10/26` と `koyi` が読めた。0x24 の `u32` も真値のスコアと一致した。
2. **ステージオフセット配列だけが読めなかった**。0x34 以降が
   `00000000 70000000 00000000 b42f0000 …` と、**4 バイトおきにゼロが挟まる**
   並びになっていたため、`u64` 化を疑って 0x38 から 8 バイト刻みで読み直したところ、
   Extra リプレイ（th6_04）で添字 6 だけが埋まる・1面で死んだリプレイで添字 0 だけが
   埋まるという th06 と同じ意味論が復活した。先頭値 `0x70` がそのままヘッダ長になる点も
   th06（`0x50`）と同じ形である。
3. **入力ログの刻みは番兵と単調性で決めた**。ステージ境界の手前に `0x0098967f`
   （= 9999999）があることから、そこを終端とみなしてレコード長とヘッダ長の候補を総当りし、
   「レコード内のどれか1つの `u32` が単調非減少になる」組み合わせを探した。
   12 バイト・ヘッダ 0x20 のときだけ全ステージで成立した。
4. **フィールドの意味は不変条件で確定させた**。上で残った 3 つの `u32` のうち、
   2番目が常に「直前のレコードの1番目」と一致することを、1面の全 1005 レコード
   （先頭と番兵を除く 1003 組）で確認し（違反 0 件）、`{ inputKey, previousInputKey, frameNum }` と結論した。
   単なる位相のずれ（ヘッダ長 0x14 でも 12 の倍数条件は満たす）はこの不変条件で棄却できる。
5. **New Classic は鍵の位置探しから始めた**。日付文字列 `09/10/26` が平文に現れるはずなので、
   「復号後の隣接バイトの差 = 暗号文の隣接バイトの差 − 7」という関係から位置を絞り、
   鍵 = `buffer[0x12]`・0x13 から復号、日付 0x14 という **全体が +4 ずれた配置**を得た。
6. **+4 のずれの正体はヘッダ先頭の 2 フィールド**だった。0x06/0x07 に
   `(0,0) (0,0) (3,1) (1,2) (0,3) (0,0) (0,0)`、0x08 の `u32` に
   `2, 4, 107, 2, 2, 3, 0` が入っており、真値の
   「機体」「モード」「難易度」と突き合わせると 0x06=モード・0x07=機体・0x08=難易度
   （スペルプラクティスのみスペル番号）で完全に説明できた。
7. **スコアが `u64` 化していることは 0x28 で確定**。0x26 の `u16` を挟んで
   `60 65 76 05 00 00 00 00` = 91,645,280 が真値の総スコアと一致した。
8. **ステージヘッダ長は 0x18 か 0x24 かで迷った**が、
   0x18 とすると「先頭レコードが `(0,0,K)` になり、次のレコードの `previousInputKey` が
   それと矛盾する」ステージが多数出るのに対し、0x24 なら全ステージ・全ファイルで
   不変条件が成立する（例外は2件のみで、いずれもステージ途中の 1 レコードであり
   ミス被弾時の再同期と思われる）ことから 0x24 に決めた。
9. **処理落ち率の位置は「3つ組の関係」で裏取りした**。0x30/0x34/0x38 の 3 つの `f32` は
   常に `a = 1.12 + s`, `s`, `b = 2.34 + s` の関係にあり、真ん中が真値の処理落ち率と
   一致する。th06/th06c でも同じ関係（オフセットは 0x28/0x2c/0x30）が成り立つため、
   構造対応の裏付けにもなった。

| th06c/th6_02 | ReimuA | Easy | 1,407,360 | 一致 | 4,589 (1m 16s) |
| th06c/th6_03 | ReimuB | Lunatic | 247,920 | 一致 | 1,660 (27s) |

| th06nc/th6_01 | ReimuA | Hard / Standard | 91,645,280 | 6面すべて一致 | 105,355 (29m 15s) |
| th06nc/th6_02 | ReimuA | Extra / Standard | 68,468,720 | 一致 | 45,388 (12m 36s) |

`frameCount` については独立した真値が無いため厳密な検証はできていないが、
以下の 3 点で妥当性を確認した。

- **スペルプラクティス 1 枚が 17.7 秒**。単一のスペルカードとして自然な長さで、
  かつ他のどのリプレイとも桁が違う（誤ったレコード長ならここが破綻する）。
- **3面序盤でのゲームオーバー（th6_05）が 3 面ぶんだけ 30 秒**、
  **3面終盤でのゲームオーバー（th6_06）は 3 面ぶんが 254 秒**と、真値の
  「序盤／終盤」という記述に対応している。
- 6面全クリアが 24〜29 分、Extra 全クリアが 10〜13 分と、原作の実プレイ時間と整合する。

構造の網羅性については、全13ファイル・全32ステージについて
「ステージブロック長 − ヘッダ長 − 8 が 12 の倍数」かつ「番兵が期待位置にちょうど乗る」
ことを機械的に確認した（全件成立）。

## 6. 分かっていないこと・追加で欲しいデータ

以下は今回のデータでは決められなかった。**リプレイを追加でもらえれば確定できる**ものは
その旨を書いた。

1. **クリア判定（`cleared`）**。th06 と同じく、ステージオフセット配列からは
   「6面に到達した」ことしか分からず、全クリアと 6 面でのゲームオーバーを区別できない。
   固定ヘッダ全域をバイト単位で走査して「クリア済み4件 / 未クリア3件」をきれいに
   分ける位置を探したが、スコア上位バイトの偶然の一致以外に候補は無かった。
   → **6面（および Extra）でゲームオーバーになったリプレイ**があれば、
   フラグの位置を特定できる可能性が高い。両作それぞれ1件ずつ欲しい。
2. **New Classic のスペルプラクティスの難易度**。0x08 がスペル番号に潰されるため
   ファイルから読めず、`difficulty: null` としている。ただし
   **スペル番号自体が難易度込みで採番されている**可能性がある
   （原作のスペルカード数は 64 枚で、`No.108` はそれを超えている）。
   → **同じスペルを異なる難易度でプレイしたスペルプラクティスのリプレイ**が
   2〜3件あれば、番号が難易度ごとに割り振られているのか、別に難易度が保存されて
   いるのかを判別できる。
3. **New Classic のゲームモード値 2**。未観測。ステージプラクティスだと推測されるが
   確証が無いため、parser は未知のモードを `stage: "Mode 2"` として素通しする。
   → **ステージプラクティスのリプレイ**（存在するなら）が1件欲しい。
4. **スペルプラクティスのステージ添字**。唯一のサンプル（`No.108`）は
   ステージオフセット配列の添字 5（= 6面）に書かれていた。これが
   「そのスペルが属する面」を意味するのか、スペルプラクティスは常に特定の添字を使うのかは
   1件では判別できない。parser は前者と解釈して `splits[0].stage = 6` を返す。
   → **異なる面のスペルのプラクティスリプレイ**が1件あれば判別できる。
5. **チャレンジモードの被弾回数**。モード自体は 0x06 から判別できるが、
   ゲーム内で記録されるはずの被弾回数に対応するフィールドは見つからなかった。
   ステージヘッダの残機欄は 2 のまま固定で動かない。
6. **処理落ち率を公開していない**。`ParsedReplay` に該当フィールドが無いため、
   オフセットは判明しているが parser は読んでいない（3変種すべてで同様）。
7. **New Classic のチェックサム種の意味**（§3.2）。経験則としては 7/7 件で成立する。
8. **入力キーのビット割り当て**。`0x001` が射撃、`0x100` が常時立っていること以外は
   詰めていない。`frameCount` の算出には不要なため深追いしなかった。

## 7. Sattori 側への影響

- **録画は未対応**。`SUPPORTED_GAME_IDS`（`packages/shared/src/games.ts`）には
  入れていないので、アップロードすると「対応していないタイトル」として弾かれる。
  これは意図した挙動である。**両作を th06 として受け付けてしまうと、
  ver 1.02h のタイトル資産では Classic のリプレイが読み込めない
  （旧バージョンは 1.03 のリプレイをファイルとして認識しない）ため、
  録画が必ず失敗する。**
- リプレイの保存先がゲームディレクトリ下の `replay/` であり、`/replay-help` の
  2グループ（インストール先直下 / `%APPDATA%`）のどちらの説明にも当てはまらないため、
  ヘルプページの一覧からは明示的に除外している（`REMAKE_GAME_IDS`）。
  録画対応時には専用の案内とアイコン（`apps/web/public/icons/th06c.png` など）が要る。
