# th20（東方錦上京）リプレイの本体構造解析

調査日: 2026-09-02 / 対象: Issue #176 / 結果を実装した場所: `packages/replay-parser/src/games/th20.ts`
/ English version: [`th20-replay-format.en.md`](th20-replay-format.en.md)

## 1. 何を調べたか

`@sattori/touhou-replay-parser` は th20 だけ **`splits`（ステージ別内訳）と
`frameCount`（総再生フレーム数）を取得できていなかった**。これは先行プロジェクトも同様で、

- raviddog/threplay（本パッケージの移植元）は th18 まで
- n-rook/thscoreboard（Silent Selene のバックエンド）は
  `replays/kaitai_parsers/th20.py` に `Header` しか定義しておらず、`Stage` を持たない
- 実際 Silent Selene の th20 リプレイ詳細ページは、上位スコアも含めて全件
  "Stage split information is unavailable for this replay." と表示する

という状態で、**th20 の本体（XOR+LZSS 展開後のバイト列）の構造を確定させた公開情報は
見当たらなかった**。本調査でこれをリバースエンジニアリングした。

`frameCount` が取れるようになると `ReplayInfo.estimatedDurationSeconds`
（`packages/shared/src/replay.ts`）が埋まり、録画中の進捗率表示の分母が入る。
th20 は録画対応済みタイトルなので、これは利用者から見える改善でもある。

## 2. 調査に使ったデータ

| 出所 | 件数 | 用途 |
| --- | --- | --- |
| Silent Selene（`.agents/skills/silent-selene/`。全難易度＋Extra から無作為抽出） | 63 | 構造の汎化検証 |
| Sattori 本番の完了済み th20 ジョブ（S3 のアップロード済み `.rpy`） | 25 | 同上＋録画動画との突き合わせ |
| リポジトリ同梱フィクスチャ `test-fixtures/th20/` | 7 | 同上 |

取得したのは 95 ファイルだが、Silent Selene に上がっているものと同じリプレイが本番ジョブにも
投入されていた等の重複があり、**内容が異なるのは 88 ファイル / 420 ステージレコード**。
以下の検証結果はこの重複除去後の数で述べる。

うち **本番ジョブ5件は録画動画が S3 に残っており**、動画のフレーム数・HUD 表示を「真値」として
使えた（残り20件は動画が消えていた）。ジョブ `c5b06095`（Lunatic 全クリア）と
`a1ef72c0`（Lunatic 全クリア。Silent Selene の th20 Lunatic 1位記録と同一ファイル）については、
利用者が動画を再生して各ステージの開始時刻とクリア時スコアを読み取った実測値があり、
これが解析の出発点になった。

同梱フィクスチャは全クリア（Hard / Easy / Lunatic）・ゲームオーバー（5面まで）に加えて、
**Extra ステージ・スペルプラクティス・ステージプラクティス**の3種類を後から足してある。
プレイ内容が根本的に違うこの3つでも同じ走査がそのまま通ることが、構造の裏付けになっている。

## 3. 判明した構造

XOR+LZSS 展開後の本体は次の形をしている（`decodeModernBody(..., 48)` の戻り値）。

```
[0x100 バイトのヘッダ][ステージレコード][入力ログ][ステージレコード][入力ログ]...
```

**ステージレコードは 0x2a0（672）バイト固定**で、その直後に可変長の入力ログが続く。
入力ログの長さはレコード内の `INPUT_SIZE` に入っているので、これを足しながら辿ると
次のレコードの先頭に着く。ステージ数はヘッダの 0xd4 に入っている。

### 3.1 本体ヘッダ（0x00〜0xff）

| オフセット | 型 | 内容 |
| --- | --- | --- |
| 0x00 | 16 バイト | プレイヤー名（SJIS、NUL 埋め。末尾に未初期化のゴミが残ることがある） |
| 0x10 | u64 | 記録時刻（Unix epoch 秒、UTC）。th10-th18 の `timestamp` と同じ性格の値 |
| 0x18 | u64 | 最終スコア ÷ 10 |
| 0xd0 | f32 | 処理落ち率（%）。Silent Selene の "Slowdown" 表示と一致 |
| 0xd4 | u32 | ステージレコード数 |
| 0xd8 | u32 | 自機（0=霊夢 / 1=魔理沙）。既存実装が使用済み |
| 0xdc | u32 | 石（`STONE_NAMES` のインデックス）。既存実装が使用済み |
| 0xfc | u32 | **スペルプラクティスのスペルカード番号（0始まり）**。それ以外の記録では `0xffffffff` |

0x10 の記録時刻は、86 ファイルについて USER セクションの `date` 文字列（ローカル時刻）と
突き合わせたところ **差はすべて時（hour）単位ちょうど** になり、内訳も
UTC+9 が 47 件・UTC+8 が 22 件・UTC+7 が 4 件…と実在のタイムゾーン分布として自然だった。
th10-th18 と同じ「固定長 name の直後に epoch」という並びで、name が 16 バイトである点だけが
違う（th17/th18 と同じ幅）。

0xfc は、**th20 でスペルプラクティスの記録を判別できる唯一の手掛かり**である。th08 は USER
セクションに `カード名\tNo. 87 恋符「ノンディレクショナルレーザー」` とカード名まで書き込むが、
th20 は**ファイルのどこにもカード名を持たない**（USER セクションはカードが属する面を
`Stage 6` と書くだけで、同じ面のステージプラクティスと区別がつかない）。手元の
スペルプラクティス記録1件では 0xfc = 99 で、ゲーム内のスペルプラクティス一覧では
No.100（Lunatic 「不生不滅の石の女神」）——つまり**ゲームの表示番号は 0xfc + 1**。
他の94ファイルはすべて `0xffffffff` だった。

### 3.2 ステージレコード（0x2a0 バイト固定）

**このレコードはステージ「開始時点」のスナップショット**（th10-th18 と同じ規約）。
したがって Stage N 行のスコアは「Stage N-1 終了時のスコア」であり、ゲーム内リプレイ選択
画面の Stage N 行の表示と一致する。全クリアなら 6 レコード（Extra は stage=7 の 1 レコード、
プラクティスはそのステージ 1 レコードのみ）で、**最終ステージ終了時点のレコードは存在しない**。

| オフセット | 型 | 内容 | 実装での扱い |
| --- | --- | --- | --- |
| 0x000 | u32 | ステージ番号（1〜6、Extra は 7） | `splits[].stage` |
| 0x004 | u32 | 乱数シード | 未使用 |
| 0x008 | u32 | このステージのフレーム数 | `splits[].frameCount` |
| 0x00c | u32 | 直後に続く入力ログのバイト長 | 走査と健全性チェック |
| 0x010 / 0x014 | u32 | 自機座標らしき値（1/128 固定小数。ステージ1では X=中央・Y=400） | 未使用 |
| 0x070 | u64 | ステージ開始時スコア ÷ 10 | `splits[].score` |
| 0x0a0 | u32 | 霊力 ×100（開始時 100=1.00、上限 400=4.00） | `splits[].power` |
| 0x0a4 | u32 | 霊力上限 ×100（常に 400） | 未使用（不変を検証済み） |
| 0x0ac | u32 | グレイズ数（通算。ステージ1では常に 0） | `splits[].graze` |
| 0x0b0 | u32 | 常に 10000 | 未使用 |
| 0x0b4 | u32 | **異変値 ×5000**（上限 1,000,000 = 表示上の 200.00） | `splits[].piv` |
| 0x0b8 | u32 | 常に 5000（異変値の表示スケール） | 未使用 |
| 0x0d4〜0x0e0 | u32×4 | 石の色別ゲージ（0〜1000） | 未使用 |
| 0x0e4〜0x0f0 | u32×4 | 石の色別の所持数らしき値（0〜4） | 未使用 |
| 0x0f4〜0x100 | u32×4 | **石の色別レベル（赤・青・黄・緑の順）** | `splits[].additional.stones` |
| 0x104 | u32 | 石のレベル合計（上記4つの和に必ず一致） | `splits[].additional.stonesTotal` |
| 0x128 | u32 | 残り人数 | `splits[].lives.count` |
| 0x12c | u32 | 残り人数の上限（常に 7。HUD のハート枠数と一致） | 検証のみ |
| 0x130 | u32 | 残り人数（かけら）0〜2 / 3 | `splits[].lives.pieces` |
| 0x134 | u32 | 被弾（ミス）回数の通算。ステージ1では常に 0 | `splits[].additional.misses` |
| 0x13c | u32 | スペルカード（ボム）数 | `splits[].bombs.count` |
| 0x140 | u32 | スペルカード（かけら）0〜2 / 3 | `splits[].bombs.pieces` |
| 0x148 | u32 | スペルカード数の上限（常に 7） | 検証のみ |

0x0f4〜0x100 の4つの値の並び順（＝どのスロットが何色か）は、**ゲーム内のステージリザルト
画面が表示する異変敵ごとのレベルと突き合わせて確認した**結果、**赤・青・黄・緑**の順だった。
実装では配列ではなく `{ red, blue, yellow, green }` のオブジェクトとして返しており、
利用側が順序の知識を持たなくて済むようにしてある。

**未同定のまま残した主なフィールド**:

- 0x01c〜0x06c: ステージ2以降では 3〜8 個の 800万〜2000万程度の値が並び、残りが 0 埋め。
  ステージ1のレコードでは同じ領域が等差数列状のゴミ（未初期化）になっている。
- 0x0cc / 0x0d0: 前者は不定値、後者は必ず 50 の倍数で上限 5000。異変値の獲得レート関連か。
- 0x138 / 0x14c / 0x150: **ステージ1のレコードで既に 0 でない**（例: 49 / 7873 / 7）。
  同一プレイヤーの3日前のリプレイでは 6 / 603 / 1 と小さく、ラン中も単調増加するので、
  セーブデータ側の累積統計をスナップショットしたものと思われる。
- 0x298 / 0x29c: f32。0.3〜0.8 程度の値。

### 3.3 入力ログ

1フレームあたり 6 バイト（`[u16 現在の入力][u16 押した瞬間][u16 離した瞬間]` に見える並び）に
加えて、**30 フレームごとに 1 バイトの区切り**が入る。すなわち

```
入力ログ長 = 6 × フレーム数 + ceil(フレーム数 / 30)
```

これが 420 レコードすべてで厳密に成立した（フレーム数が 30 の倍数のときだけ `+1` ではなく
`ceil` になる、という境界も実際に十数レコードで踏んでいる）。**フレーム数とログ長は冗長なので、
この式が破れたら「もうステージレコードを見ていない」と判断できる**。実装では
`isPlausibleRecord()` がこれを走査の停止条件に使っている。

## 4. 検証

### 4.1 構造の検証（88 ファイル / 420 レコード）

- 0x100 から `0x2a0 + INPUT_SIZE` を足しながら辿ると、**全ファイルで展開後本体の末尾に
  ちょうど着地した**（余りも不足も 0 バイト）。
- レコード数はすべてヘッダ 0xd4 の値と一致。
- 出現したステージ列は `(1,2,3,4,5,6)` `(1,2,3,4,5)` `(1,2,3,4)` `(1)` `(5)` `(6)` `(7)` のみ。
  それぞれ全クリア・5面ゲームオーバー・4面ゲームオーバー・1面ゲームオーバー・
  プラクティス（該当ステージ1件）・Extra に対応する。
- 0x18 のスコアは 86 ファイルすべてで USER セクションのスコア文字列と一致。
- 不変を確認した定数: 霊力上限 400 / 残機上限 7 / ボム上限 7 / 0x0b0=10000 / 0x0b8=5000。
- 単調性: スコア・グレイズ・ミス回数はいずれも減少しない。石のレベル合計は必ず 0x104 に一致。

### 4.2 フレーム数の検証（録画動画との突き合わせ）

ジョブ `c5b06095`（100,410 フレーム）のステージ別フレーム数を 60fps で秒に直すと
191.9 / 217.7 / 272.5 / 280.0 / 349.5 / 361.9 秒。利用者が動画から読み取った各ステージの
長さは 193 / 218 / 273 / 280 / 352 / 362 秒で、**6ステージすべてが数秒以内で一致**した。
動画全体は 102,737 フレームで、リプレイの 100,410 フレームとの差 2,327 フレーム（38.8 秒）は
録画開始時のメニュー操作とリプレイ終了検知の遅れに相当する。

ジョブ `a1ef72c0` は 1〜4面の境界が同様に一致した一方、利用者の「6面開始 34:47」という
読み取りだけが約200秒ずれていた。動画の該当区間を10秒刻みで抜き出して確認したところ、
**5面ボス撃破後の会話シーンは 31:40 前後（1900 秒付近）に現れ、その直後に背景が完全に
別のステージへ切り替わっていた** ——
レコードから計算される境界（累積 112,284 フレーム = 31:11、＋録画開始オフセットと
ステージ間のドリフト）と一致する。利用者側の読み取りの方が誤りで、レコードは正しい。

### 4.3 HUD 表示との突き合わせ

ジョブ `c5b06095` の2面開始フレーム（スコア表示が 55,919,200 でレコードの
`score` と厳密に一致するフレーム）の HUD と、同ジョブ・`a1ef72c0` の他の境界フレームを
目視で読み取り、レコードの値と突き合わせた。

| 項目 | HUD | レコード |
| --- | --- | --- |
| 残り人数 | 2（かけら 2/3） | 0x128=2 / 0x130=2 |
| スペルカード | 2（かけら 2/3） | 0x13c=2 / 0x140=2 |
| 霊力 | 4.00 / 4.00 | 0x0a0=400 / 0x0a4=400 |
| 異変値 | 24.96 | 0x0b4=124,837 → ÷5000 = 24.967 |

`a1ef72c0` 側（残り人数 3・かけら 1/3、スペルカード 7・かけら 0/3、霊力 4.00、
異変値 200.00）も同様に一致し、異変値が上限 200.00 で頭打ちになることと
0x0b4 が 1,000,000 で頭打ちになることも対応した。

## 5. 考察・既知の限界

- **0x134 =「ミス回数」は状況証拠による**。ステージ1で必ず 0・単調増加という性質に加えて、
  この値が大きく増えたステージの直後だけ霊力が最大値を割っている（th20 では被弾で霊力が
  下がる）という対応がある。ただし 338 回のステージ遷移のうち 19 回で「残機の減少幅 >
  ミス回数の増分」となっており、**th20 には被弾以外に残機を消費する要素がある**と考えられる
  （その分の内訳は特定できていない）。フレーム単位で被弾を数え直す検証はしていない。
- **スペルカード番号からカード名への対応は未解決**。§3.1 のとおり番号は取れるが、名前は
  リプレイファイルにもゲーム本体の実行ファイルにも平文では入っておらず（`th20.dat` は
  THA1 アーカイブで圧縮・暗号化されている）、名前表を持つには外部データが要る。
  ゲームフォルダに同梱されている thprac には th20 のカード名50件が UTF-8 で埋め込まれており
  （E/N 用37件＋H/L 用13件）、そのうち 「不生不滅の石の女神」 は48番目（0始まり）だった。
  一方リプレイ側の番号は 99 なので、**thprac の名前リストの添字とゲームの番号は一致しない**
  （難易度ごとに枝分かれするぶん番号が増えていると思われるが、対応規則を確定させるには
  検証用のスペルプラクティス記録が1件では足りない）。加えて thprac は GPL-3.0 であり、
  MIT で公開している本パッケージへ表を取り込むかはライセンス面の判断も要る。
  現状は `stage` に `Stage 6 (Spell Practice No. 100)` と番号だけを出している。
- **プラクティス記録のステージ番号は、ゲーム内のリプレイ一覧の表示と食い違うことがある**。
  同梱フィクスチャ `th20_07.rpy`（Hard の6面のみをプラクティスでクリアした記録）は、
  実機のリプレイ一覧では「St5」と表示されるが、USER セクションもステージレコードも
  `Stage 6` / `stage=6` で、**実際のプレイ内容（6面）と一致するのはこちら**。
  一覧の「St5」がどのフィールドから来ているかは特定できていない（ヘッダ 0x098 が
  この記録だけ 5 になっているが、他の記録では全クリアでも 0〜9 とばらつくので無関係）。
- **録画動画と照合できたのは本番ジョブ5件だけ**。ただし入力ログ長の式（§3.3）が
  フレーム数の独立した裏取りになっており、これは 420 レコードすべてで成立している。
- th20 の HUD のスコア表示は 9,999,999,990 で頭打ちになる（`a1ef72c0` の実スコアは
  19,247,977,000）。**MOD がゲーム内スコアを読んでデシンクを判定する仕組み
  （Issue #103、`worker/recording/modlog.py`）が、この桁あふれで誤検知していないかは
  別途確認した方がよい** ——本調査の範囲外だが、`a1ef72c0` は実際に
  `desyncDetected: true` が付いている。
