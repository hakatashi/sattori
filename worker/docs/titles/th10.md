# th10（東方風神録）対応の技術的背景（Issue #75、touhou-recorder reports/56〜60）

TH10エンジン初出のタイトル。**th11とは異なりDirectInput経由の入力注入を使う点、
「バグマリ」修正オプションの取り扱い、終了検知テンプレートを絞り込み領域に限定する
必要がある点**がここに集約されている。sattori本体の`record_th10.py`でのローカル実機
検証結果は
[`docs/reports/2026-08-29-th10-local-recording-verification.md`](../../../docs/reports/2026-08-29-th10-local-recording-verification.md)。

touhou-recorder での事前検証（reports/56〜60）を踏まえた設計:

- **入力注入はth06/07/08と同じPressKey（DIKスキャンコード経由）**: th10.exeはth11/th20と
  異なり、DirectInputの`GetDeviceState`が実際に56〜60Hzでポーリングされることを実機で
  確認済み（`FpsMonitor`ログ）。TH10エンジン初出のこのタイトルはまだ`GetKeyboardState`
  方式に切り替わっていない（`InstallKeyboardStateHook`は不要、reports/56）。
- **タイトル画面の"PRESS ANY BUTTON"表示をEnterで消す必要がある**: th06/07/08には無い
  ステップ。タイトルロゴ演出中に送った入力はバッファされず単純に無視されるため、早すぎる
  Enterはタイトル消しに失敗し、後続のDown/Enterが「まだ表示されているPRESS ANY BUTTON」を
  消す動作+メインメニューの項目確定に化けて、Game Start経由の別ルート（Rank Select/
  Player Select）に迷い込む。6000ms待つことで安定して機能する（reports/56・59）。
- **リプレイ一覧はth06/07/08と同じ番号スロット方式**: ファイル名の数字がそのままスロット
  番号（No.NN）に対応し、th11/th20の`_ud0000`タブ切替方式ではない。MODは常に1番目の
  スロットを選ぶ固定シーケンスのため、`canonical_slot="th10_01.rpy"`に正規化する
  （`record_th10.py`）。
- **VsyncPatch（`vpatch_th10.dll`）を`extra_dlls`で導入する**: th06と同じ仕組みで
  `injector.exe`がhook_dllより先に注入する。VsyncPatch本体は同梱の`vpatch.ini`で挙動が
  決まる。
- **「バグマリ」修正（`BugFixTh10Power3`）は記録時の設定と必ず一致させる必要がある**:
  東方風神録の既知バグ「バグマリ」（魔理沙Bのパワーが3.00〜3.95の間にあるとき
  ショット火力が異常上昇する）をVsyncPatchが修正できるが、記録リプレイと異なる設定で
  再生するとリプレイずれ（デシンク）が起きることを4パターン（パッチ有効/無効 ×
  記録時パッチ有効/無効のリプレイ）全てで実機確認済み（reports/58）。**リプレイファイル
  自体にはこの設定情報が含まれないため、録画側は記録時の設定を自動判別できない。**
  この判別不能性への対応方針は
  [`docs/decisions/0036`](../../../docs/decisions/0036-th10-bugfix-marisab-self-report.md)
  にまとめてある。Sattoriではページ A の詳細設定オプション
  （`RecordingOptions.th10BugfixMarisaB`、既定`false`）で利用者に自己申告してもらい、
  `TH10_BUGFIX_MARISA_B`環境変数経由で
  `record_th10.py`が起動直前に`vpatch.ini`の`BugFixTh10Power3`を書き換える
  （`recording_common.apply_vpatch_ini_overrides()`、`GameConfig.vpatch_ini_overrides`）。
  誤った申告のリプレイは依然としてデシンクしうる（`docs/known-limitations.md`参照）。
  このオプションは「th10かつ魔理沙B」の組み合わせでしか意味を持たないため、ページAは
  それ以外の組み合わせでグレーアウトする（`apps/web/src/components/UploadForm.tsx`）。
- **終了検知はテンプレート照合だが、絞り込み領域と専用閾値が必要**: リプレイ選択画面は
  背景全体が常時アニメーションしており画面静止検知が使えない一方、th06/07/08の既定領域
  （上部帯全体）を使うと背景アニメーションに引きずられて同一画面同士でもMADが上振れし
  誤判定を招く。リプレイ内容に依存しない左上の"REPLAY"見出し部分（元のウィンドウ座標系で
  `(0,0)-(244,76)`）だけに絞り込み、閾値も専用の値（25.0、既定の15.0より緩い）を使う
  （`GameConfig.end_template_rect`/`end_template_mad_threshold`、
  `recording_common.build_end_template_mask()`、reports/56）。この一般化の経緯は
  [`docs/decisions/0037`](../../../docs/decisions/0037-end-template-restricted-region-for-th10.md)。
- **スコア・ステージ番号の監視RVA**: thprac（`thprac_th10.cpp`）の`enum ADDRS`・
  `THGuiPrac::State()`由来。基点RVA`0x74c00`から`score`は`+0x44`（内部値は画面表示値の
  1/10、他タイトルと同じ×10系列）、`stage`は`+0x7c`、`lives`は`+0x70`。グレイズは
  th10エンジンに実装が見当たらない（thprac側も`THPracParam`にフィールドが無い）ため
  計測しない。フル尺録画（`th10_24.rpy`、Lunatic 1〜6面通し）で記録スコア
  150,277,360との完全一致を実機確認済み（reports/57）。
- **fps暴走の検知・処理落ちの早期検知・自動リトライ・音声/映像の別プロセス録画**は
  他タイトルと共通の実装（`recording_common.py`）をそのまま使う。

## 残っているリスク

- 「バグマリ」修正オプションの申告が誤っている場合のデシンクは録画側では検知できない
  （事後のスコア突き合わせ`desyncDetected`が不一致として警告表示するのみ）。
- 低速録画（Issue #68）はth10では未対応。MOD自体はth20と同じ`fps_limiter_hook`/
  `dsound_hook`が技術的に適用可能なことを touhou-recorder で確認済み（reports/59）だが、
  Sattori側のMOD・`SLOW_MOTION_SUPPORTED_GAME_IDS`には未実装（Issue #75のスコープ外）。
