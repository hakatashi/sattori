# th15（東方紺珠伝）対応の技術的背景（Issue #82、touhou-recorder reports/82）

GPU EC2導入・カスタムAMI固定方式の根拠は
[`decisions/0046`](../../../docs/decisions/0046-gpu-ec2-instance-and-fixed-ami.md)。
自宅ワーカーへオファーしない理由は
[`decisions/0047`](../../../docs/decisions/0047-no-gpu-titles-for-home-worker.md)。
GPU系専用ECRリポジトリを新設した理由は
[`decisions/0048`](../../../docs/decisions/0048-separate-ecr-repo-for-gpu-workers.md)。
th15をGPU系インスタンスに固定した理由（原理的な必須要件ではなく品質優先の選択である
ことの根拠）は
[`decisions/0050`](../../../docs/decisions/0050-th15-gpu-instance-despite-not-strictly-required.md)。

th15（東方紺珠伝 ～ Legacy of Lunatic Kingdom.）はth20と同世代のエンジン（960p相当の
内部描画解像度・`%APPDATA%/ShanghaiAlice/th15/`配下のcfg/リプレイ）だが、**入力
ポーリング方式・GPU描画の必要性の両方でth20とは異なる**——`GameConfig`・MODを
触る前に必ずここを読むこと。

## 入力ポーリング方式はth11/th20ではなくth06/07/08/10と同じ（最重要）

「TH10以降のエンジンはGetKeyboardStateでポーリングする」という既存の経験則
（th20導入時に確立、`mods/th20_replay_autoplay/dllmain.cpp`）を鵜呑みにしてth20の
MODをそのまま移植したところ、**メニュー操作が一切反映されなかった**（`AutoPlayThread`の
ログは正常に完走するが、実際の画面は無操作のままアトラクトデモに遷移する）。
`PressVKey`（GetKeyboardState方式）を`PressKey`（DIKスキャンコード、GetDeviceState
方式、th06/07/08/10と同じ）に切り替えたところ正しく動作した（touhou-recorder
reports/82）。**「th10以降のエンジンはGetKeyboardState」という前提はth15には当てはまらない**
ため、他の未検証タイトルに移植する際もこの前提を鵜呑みにせず実機確認が必要。

## GPU描画は必須ではないが、Extraステージの処理落ち対策として採用する

th06nc（GPU描画が無いと原理的に60fpsへ届かない）とは事情が異なる。th15は
wined3d（D3D9→OpenGL）で描画しており、**Xvfb+llvmpipe（ソフトウェア描画）でも
メニュー・通常ステージ（Hard、全クリア）はネイティブfps付近で動作し、理論尺比較で
+1.2%程度の良好な結果が出る**。問題はExtraステージの高負荷演出区間（強力な閃光
エフェクトを伴うボス攻撃）に限定され、ここでゲーム内蔵fpsカウンターが実測30fps
前後まで低下する処理落ちが発生する（理論尺超過+6.1%）。

この処理落ちは**CPUコア数を増やしても解消しない**ことを実機確認済み（ローカル
4vCPU相当とAWS c7i.4xlarge(16vCPU)で、同一スペルカード演出の複数地点サンプリングが
平均43.6fps/44.1fps・最低17.9fps/15.2fpsとほぼ同水準）。一方、**GPU
（wined3d+OpenGL、g6f.2xlarge）に切り替えると全地点で59.9〜60.0fpsに改善し、
理論尺超過も+0.89%まで改善する**ことを実機確認した。低速録画
（`FPS_LIMIT_TARGET_HZ=30`）も代替手段として機能する（理論尺超過+1.4%、フレーム
抽出で30.0fps安定を確認）ことを確認済みだが、**本番はth06ncと同じ運用（GPU系
`g6f`インスタンス固定）に揃える**ことをユーザーが選択した。低速録画・自宅ワーカー
ルーティングは提供しない（`SLOW_MOTION_SUPPORTED_GAME_IDS`に含めない、
`apps/api/src/workerRouting.ts`の`GAME_ROUTING_POLICIES.th15.offerToHomeWorker = false`）。

- インスタンス: `g6f.xlarge`・`g6f.2xlarge`（th06ncと共通の`GPU_CANDIDATE_INSTANCE_TYPES`、
  `apps/api/src/ec2.ts`）。
- ワーカーイメージ: th06ncと共通の`worker/Dockerfile.gpu`・ECRリポジトリ
  （`sattori-worker-gpu`）をそのまま使う（タイトル追加のための変更は`entrypoint.py`の
  `RECORDING_SCRIPTS`・`record_th15.py`のCOPY行のみ）。
- ヘッドレス画面: `recording/gpu_display.py`（th06ncと共通）。
- **DXVKは使わない**（`GameConfig.dxvk_dll_overrides`は指定しない）。th15はD3D9タイトル
  で元々wined3dが使える上、**DXVK v3.1.1がこのGPU（GRIDドライバのVulkan実装）を
  `Skipping: Device does not support required feature 'khrLoadStoreOpNone'`で拒否し
  `No adapters found`になる**ことを実機確認した（原因未特定、32bit版`vulkan-tools`が
  無く32bit側から直接`vulkaninfo`で機能確認する手段が無かったため）。wined3d
  （OpenGL）のままGPUを使うことで解消する。
- CRTCモード: Xorg+nvidia環境ではウィンドウが期待の1280x960ではなくCRTCの既定モード
  （1024x768）に縮小される（th06ncの1080p検証時と同じ既知の症状）ため、
  `GameConfig.crtc_mode="1280x960"`で明示的に切り替える。

## スコア・残機・グレイズのRVA

`thprac`（`thprac/src/thprac/thprac_th15.cpp`）の`th15_patch_main`フック（プラクティス
モード開始時の初期値書き込み処理）から、以下の絶対アドレスへの書き込みを確認した:

```cpp
*(int32_t*)(0x4E740C) = (int32_t)(thPracParam.score / 10);  // スコア(内部値、表示は×10)
*(int32_t*)(0x4E7450) = thPracParam.life;                     // 残機
*(int32_t*)(0x4E741C) = thPracParam.graze;                    // グレイズ
```

th15.exeのImageBaseは標準の`0x400000`のため、RVAは`baseRva=0xE7400`
（`=0x4E7400-0x400000`）を基点に`scoreOffset=0x0C`・`livesOffset=0x50`・
`grazeOffset=0x1C`とした（`mods/th15_replay_autoplay/dllmain.cpp`の
`ScoreMonitorConfig`、`baseIsPointer=false`。th20の`GlobalsSide`構造体のような
ポインタ間接参照は不要で、モジュール直下の静的領域に直接配置されている）。
フル尺録画（Hard・Extra）双方でリプレイ記録スコアとの完全一致を実機確認済み
（スコア倍率×10、th07/th08/th10/th11/th20と同じ分類、`recording/modlog.py`の
`GAME_SCORE_MULTIPLIERS`）。

ステージ番号を保持する単純な変数は`thprac_th15.cpp`全体を確認した範囲では見つから
なかった（`CalcSection()`による区間IDの動的計算のみ）ため、`stageWidth`は未指定
（監視しない）。

## メニュー操作シーケンス

Extra Startが常にグレーアウトしている（未クリア救済措置が無い）ため、Down×2で
Replayに到達する（th20はDown×3）。以降はth20と同じ`_ud`タブ方式
（`th15_ud0000.rpy`固定）:

```
Buffering 10000ms(scaled) → Down×2(250ms間隔) → Enter → Right → Enter → Enter
```

## 終了検知

テンプレート画像は未整備。画面静止のみでの判定に頼るが、リプレイ終了後の
「再生終了/ゲームを終了/もう一度再生する」メニューのテキスト全体
（1280x960のウィンドウ座標系で`(81, 350)`〜`(470, 800)`）を静止判定から除外する
（`GameConfig.still_detect_exclude_rect`）。

## 低速録画のスケーリング閾値バグ（他タイトル共通、発見済み）

低速録画（`FPS_LIMIT_TARGET_HZ=30`）動作確認中、録画完了後の重複フレーム率判定
（`--max-duplicate-rate`、既定30.0%）が、30fps録画で理論上発生する意図的な重複
（実測58.3%）を「処理落ちの疑い」と誤判定する不具合が見つかった。touhou-recorder
側では`scripts/25`の該当デフォルト値を`MENU_TIME_SCALE`に応じてスケールする
修正で解消したが、**sattoriの録画パイプラインにはこの閾値のスケーリング機構自体が
無く**、本対応ではth15を`SLOW_MOTION_SUPPORTED_GAME_IDS`に含めていないため
sattori側では未検証・未修正のまま残っている。将来th15または他タイトルで低速録画を
sattoriに導入する場合は、`worker/recording/pipeline.py`の重複フレーム率判定が
低速録画時にも正しく機能するか確認すること。

## ローカル検証について

このマシン（HakataMatrix）にはNVIDIA GPUが無く、`recording/gpu_display.py`は
NVIDIAドライバ専用（Xorg設定に`Driver "nvidia"`を直書き）のため、th06ncと同じく
GPU描画経路（`gpu_display=True`）はこのマシンでは実行できない
（`verify-recording-locally` skill §0.0参照）。sattori側のコードでのMOD・録画
パイプライン結合検証（メニュー自動操作・スコア監視・終了検知・出力動画の生成)は
`gpu_display=False`（Xvfb+wined3d、ソフトウェア描画）へ一時的に切り替えて実施した
（短尺リプレイ`th15_09.rpy`、`docs/reports/`の実施記録参照）。GPU描画による
Extraステージの処理落ち解消自体はtouhou-recorder側で実機検証済み（reports/82、
AWS g6f.2xlarge）であり、本番相当のGPU E2E録画（sattoriのコード・AWSインフラ経由)は
本対応の時点では未実施。

**【重要】本番E2E検証を試みた際、GPU描画必須タイトル用の既存Dockerfile
（`worker/Dockerfile.gpu`）にwine32が無くth15(32bit)が起動できない不具合と、
EC2 Launch Templateの`$Default`バージョンがCDKデプロイで更新されない不具合
（th15に限らずSattori全体の既存バグ）を発見し修正済み。加えてGPU用カスタムAMIに
32bit互換NVIDIAドライバを追加する試みがXorg起動不能を招き、th06ncへの影響を避ける
ためロールバックして中断した——GPU描画経路（`gpu_display=True`）は本対応の時点でも
まだ本番で動作確認できていない。詳細・次回への引き継ぎ事項は
[`docs/reports/2026-09-17-th15-production-e2e-attempt.md`](../../docs/reports/2026-09-17-th15-production-e2e-attempt.md)
を必ず読むこと。次にth15の録画品質を調査する際は、まずAWS実機でGPU系インスタンスが
確保できているかを確認すること（th06ncもg6f系のSpot在庫枯渇で検証が長期間ブロック
された前例がある、`docs/titles/th06nc.md`）。**
