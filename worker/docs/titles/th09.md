# th09（東方花映塚）対応の技術的背景（Issue #73、touhou-recorder reports/68〜69）

th09は対戦形式（1人プレイ時はCPU戦）のシューティングで、これまでの対応タイトルと
ゲームシステムが異なる（1P/2P split-screen、ボム・グレイズ相当の概念が無い、残機は
0.5刻み）。ただし**この違いは画面表示・ゲームルールの話であり、録画パイプライン
（Wine起動・入力注入・終了検知・音声分離・変換）には影響しない**。ストーリーモード・
マッチモードいずれのリプレイもth11/th12と同じ「ud0000タブ」方式の自動再生で扱える。

touhou-recorder での事前検証（reports/68〜69）を踏まえた設計:

- **入力注入はth06/07/08と同じPressKey（DIKスキャンコード経由）**: 実機の`FpsMonitor`
  ログで起動直後から100Hz超の`GetDeviceState`呼び出しを確認し、th11/th20の
  `GetKeyboardState`方式ではないことを確かめた（reports/68。th12の教訓通り、
  `WaitForHookActive()`はどちらの経路でも成立してしまうため、この確認を省略すると
  誤った経路でも起動エラーにならず気づけない）。
- **メニュー遷移シーケンスはth11/th12と同じ「ud0000タブ」方式**: Down×2 → Enter
  （Replay確定、直ちにリプレイ選択画面へ遷移）→ Right（ユーザーリプレイタブへ
  切替）→ Enter（1件目選択）→ Enter（再生確定）。**th10にある「PRESS ANY BUTTON」
  表示を消すステップは無い**。タイトル画面バッファは1500ms（th08と同じ）。
- **投入リプレイは`th9_ud0000.rpy`という固定名で配置する**（`GameConfig.canonical_slot`）。
  **実行ファイル名は`th09.exe`だが、リプレイファイル名の接頭辞は`th9_`（`th09_`ではない）**。
  誤って`th09_ud0000.rpy`を配置するとゲーム側がユーザーリプレイとして認識せず、
  リプレイ一覧が全スロット空欄のまま再生されない（実機検証で発覚。sattori本体の
  ゲームデータに同梱されている既存リプレイも全て`th9_NN.rpy`形式）。
- **終了検知はテンプレート照合（絞り込み領域）**: リプレイ選択画面「映花一覧」の
  見出し部分のみを比較する（`end_template_rect=(0, 0, 230, 88)`）。既定の「上部帯
  全体」比較だとリプレイごとに内容が変わる0000スロットの行（スコア・日付）まで
  含んでしまい誤判定するため、th10と同じ絞り込みが必要（reports/68）。
- **P1残機（life）のみ監視、スコアは監視しない**: thprac(`thprac_th09.cpp`)の
  `TH09Tools::OnContentUpdate`から得たRVA（絶対VA `0x4a7d94`=P1状態構造体ポインタ、
  image base `0x400000`、+0xa8がlife=0.5刻みの残機を2倍した整数）で`baseIsPointer=true`。
  **スコアのRVAは実機でのメモリ全域スキャン（プレイヤー構造体・弾幕マネージャ構造体・
  BSS領域をint32/int64/floatで解釈）を尽くしても特定できなかった**（thprac_th09.cppに
  スコア表示/編集UIが無く、既知のRVAが無いため。reports/68）。`ScoreMonitorConfig.
  scoreWidth=0`でスコア読み取り自体をスキップし、`baseResolved`のみをログ出力の
  ゲートにする（`mods/common/score_monitor.h`参照。他タイトルは全て`scoreWidth`を
  明示的に4等へ設定しているため後方互換）。**th09のリプレイずれ事後検知
  (`JobRecord.desyncDetected`)はscoreを見ないため機能しない**（`docs/known-limitations.md`
  参照）。P2側は`ScoreMonitorConfig`が単一のstage/lives/graze欄しか持たない構造上、
  自分側(P1)のみ監視する。
- **fps暴走検知の閾値は既定300.0Hz（`recording/modlog.py`）のまま変更不要**: th09は
  健全な状態でもGetDeviceStateポーリング周波数がタイトル画面〜メニュー中に100〜190Hz
  程度まで達することを実機確認したが（reports/68）、既定の300Hz閾値を下回るため
  誤検知しない。
- **VsyncPatch（`vpatch_th09.dll`）は録画では使わない**: ゲームデータに同梱されて
  いるが「不具合時のみ使用」する位置づけで、実機検証では常時無効のまま処理落ち・
  デシンクなく録画できた。`extra_dlls`は指定しない（th12のような常時有効化はしない）。
- **cfg/リプレイの配置はゲーム本体ディレクトリ直下**（th10/th12と同じ、th20のような
  `%APPDATA%`配下ではない）。
- **推奨インスタンスタイプはc7i.xlarge（4vCPU、既定の候補群）**: ローカル実機・AWS
  実機（c7i.xlarge）いずれもMatch/Story/Extraの3種で重複フレーム率3.1%以下と良好
  （reports/68）。上位インスタンスタイプへのステップアップ検証は不要と判断した。
- **低速録画フックは実装済みだがユーザー向けには非公開**（Issue #101のスコープ）:
  th09はDirect3D8エンジンのため、th10/th12/th20が使う`fps_limiter_hook.h`（D3D9版）
  ではなく新規の`mods/common/fps_limiter_hook_d3d8.h/.cpp`を使う（vtable番号は
  D3D9よりCreateDeviceが1つ・Presentが2つ小さい、ヘッダのコメント参照）。画面上の
  fpsカウンター表示補正は、th20と異なり`QueryPerformanceCounter`ではなく
  `WINMM.dll!timeGetTime`（rva=`0x00031701`）を使っていることが`timer_probe_hook`
  による実機調査で判明し（reports/69）、`InstallFpsDisplayCorrectionHookTimeGetTime()`
  を新規追加した。実機で`FPS_LIMIT_TARGET_HZ=30`設定時に画面上fps表示が
  「60.00fps」に補正されることを確認済み（reports/69）。**`SLOW_MOTION_SUPPORTED_
  GAME_IDS`には含めていない**ため、ページAからは選択できず、`FPS_LIMIT_TARGET_HZ`
  はth09には渡らない。Issue #101で対応タイトルを広げる際は、この2フックの追加は
  不要でオプションの許可リストに加えるだけでよい。
- **ホスト負荷への感度が他タイトルより高い**: 低負荷時は重複フレーム率0.3%だった
  同一リプレイが、ホストの別プロセス負荷（load average 15〜23）下では30〜42%まで
  悪化した（reports/68）。th09固有のバグではなくXvfb+wined3d(llvmpipeソフトウェア
  レンダリング)がCPU負荷に敏感なことを示す実例で、自動リトライ機構が正しく異常を
  検知して破棄した。ローカル実機検証時は`uptime`でホスト負荷を確認すること。

## 残っているリスク

- スコアRVAが未特定のため、th09だけリプレイずれの事後検知（スコア突き合わせ）が
  機能しない。lifeの監視は動いているが、デシンクの検知手段としては弱い。
- Extraステージでの低速録画・fps表示補正の実機検証は未実施（Match/Storyでのみ
  確認済み。ロジック自体はモード非依存のため動作するはずだが未確認、reports/69）。
- th09固有のウィンドウ座標バグ（ウィンドウ強制移動を行うとキャプチャ領域にOS
  ウィンドウ装飾が混入する現象）の根本原因は未特定のまま（reports/68）。sattori本体の
  `recording/pipeline.py`は元々「画面内に収まっていれば移動をスキップする」汎用ロジック
  を持っており、th09の初期検出座標がXVFB_SCREEN範囲内に収まるため実害は無い。
