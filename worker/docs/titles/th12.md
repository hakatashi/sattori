# th12（東方星蓮船）対応の技術的背景（Issue #76、touhou-recorder reports/61〜67）

th10 と th11 のどちらとも完全には一致しない、**入力注入はth10方式・メニュー遷移構造は
th11方式**というハイブリッド仕様である点がここに集約されている。

touhou-recorder での事前検証（reports/61〜67）を踏まえた設計:

- **入力注入はth10と同じPressKey（DIKスキャンコード経由）**: th12.exeはth11とは異なり、
  DirectInputの`GetDeviceState`が実際に56〜60Hzでポーリングされることを実機で確認済み
  （`FpsMonitor`ログ、reports/61）。最初にth11用の`PressVKey`（`GetKeyboardState`フック
  経由）で実装したところ、ビルド・注入・「sequence complete」ログ出力までは正常に完了した
  にもかかわらず、実際にはメニュー操作が一切反映されずタイトル画面のアトラクトデモの
  ままだった（`WaitForHookActive()`は`GetDeviceState`/`GetKeyboardState`いずれかの
  呼び出しがあれば成立してしまうため、この誤りは起動時エラーとして検出できない）。
  `PressKey`（`worker/mods/th10_replay_autoplay/dllmain.cpp`と同じ経路）に切り替えて
  解消した。
- **メニュー遷移シーケンス自体はth11と同じ**: Down×2 → Enter（Replay確定）→
  Right（ユーザーリプレイタブへ切替）→ Enter（1件目選択）→ Enter（再生確定）。
  **th10にある「"PRESS ANY BUTTON"表示をEnterで消す」ステップは無い**（th12のタイトル
  画面はth11型で、この表示自体が存在しない）。th10のシーケンスをそのまま流用すると
  ステップが1つずれて誤ったメニュー項目に迷い込むので注意。
- **リプレイ一覧の「ユーザーリプレイ」タブ**: th11と同じく、実際のプレイヤー録画
  リプレイは右キーで切り替わる別タブに属する。投入リプレイは`th12_ud0000.rpy`という
  固定名で配置する（`GameConfig.canonical_slot`）。
- **タイトルロゴアニメーション待機は6000ms**（reports/61、th11と同じ値）。
- **ゲームウィンドウが最小化(Iconic)状態で作成される既知の不具合**: 他タイトルには
  無い、th12固有の挙動。`recording.window.find_window()`の`xwininfo`判定は`IsViewable`
  を見るため、最小化状態のウィンドウを検出できずウィンドウ検出ループがタイムアウト
  する。`GameConfig.force_window_map=True`を指定すると、`find_window()`が検出した
  全ウィンドウへ`xdotool windowmap`を発行してから判定するようになる（reports/61）。
  cfg自体のウィンドウモード設定（`th12.cfg`のbyte0=`0x01`）は正しく機能している
  （誤って`0x03`に書き換えると初回起動時の画面モード選択ダイアログに退行することを
  reports/61で確認済み）。
- **VsyncPatch（`vpatch_th12.dll`）を`extra_dlls`で常時導入する**: ユーザー指示に
  よりth12は録画時に常にVsyncPatchを有効化する。**th10の`BugFixTh10Power3`のような
  ini切替オプションは存在しない**——`vpatch.ini`にオン/オフを切り替えるオプション項目
  自体が見当たらず、DLL自体に固定で組み込まれた修正と推測される（reports/64）。
  VsyncPatchはth12の既知バグ「スコア表示オーバーフロー」（獲得スコアが
  2,147,483,647を超えると画面表示が壊れる。桁区切りのカンマが消え縮んだ値になる）を
  修正するが、内部の生スコア自体（int32）はオーバーフローしておらず、`score_monitor`
  が読み取る値やリプレイ再生の同期には影響しない（reports/64、VsyncPatch有無の両方で
  デシンクなし・記録スコアと完全一致を確認済み）。
- **終了検知はテンプレート照合を使わず、画面静止検知のみで運用する**: th11と同じ理由
  （終了画面が「直前のゲームプレイ画面がそのまま静止し、半透明のPause Menuが
  オーバーレイ表示される」構造で、内容非依存のテンプレート照合の前提が崩れるため）。
  `end_template_path`を意図的に用意しない（ワーカーイメージに
  `assets/replay_end_templates/th12.png`を含めない）ことで、`load_end_template()`が
  自動的にNoneを返し、画面静止のみ判定にフォールバックする。
- **Pause Menu画面の明滅を静止判定から除外する**: `GameConfig.still_detect_exclude_rect
  =(48, 214, 203, 430)`（元のウィンドウ座標系）。th11と同様の対策（reports/61）。
- **スコア・ステージ番号の監視RVA**: thprac（`thprac_th12.cpp`）の`THAdvOptWnd`内、
  プラクティスモードパラメータ書き込みコードから収集した絶対VA（image base
  `0x400000`）を、基点`0x4b0c44`（RVA`0xb0c44`）からのオフセットに整理したもの。
  score(表示値の1/10、他タイトルと同じ×10系列)はoffset+0x00、stage(STAGE_NUM)は
  +0x6c、livesは+0x54、grazeは+0x98。th10・th11と同じくポインタ間接参照は不要
  （`baseIsPointer=false`）。フル尺録画（通常・Extraステージ両方）で記録スコアとの
  完全一致を実機確認済み（reports/62）。
- **cfg/リプレイの配置はゲーム本体ディレクトリ直下**（th10と同じ、th20のような
  `%APPDATA%`配下ではない。`uses_appdata_profile`は指定不要、reports/65）。
- **推奨インスタンスタイプはc7i.2xlarge（8vCPU）**: 当初c7i.xlarge（4vCPU）で実機
  検証したところ重複フレーム率は良好（0.6%）だったが、**「重複フレーム率」だけでは
  処理落ちを過小評価する**ことが判明した——mpdecimateベースの重複フレーム率は
  「フレーム内容が完全に同一のまま複数回キャプチャされる」現象しか検出できず、
  背景アニメーションが常に変化し続けるth12では「ゲーム全体の進行が実時間に対して
  間延びする」タイプの処理落ちを見逃す。リプレイの`frameCount`（60fps基準の理論尺）
  と実測プレイ時間を比較したところ、c7i.xlargeでは通常ステージで**理論尺超過+2.11%**
  という深刻な処理落ちが判明し、c7i.2xlargeでは+0.16%まで改善した（reports/67）。
  **th20と同じ「1タイプのみ実機検証済み」パターン**を採る（`c7a`/`m7i`の`.2xlarge`系は
  未検証）。
- **fps暴走の検知・自動リトライ・音声/映像の別プロセス録画**は他タイトルと共通の
  実装（`recording/`パッケージ）をそのまま使う。
- **低速録画（Issue #68）はth12では未対応**。MOD自体はth10・th20と同じ
  `fps_limiter_hook`/`dsound_hook`/`fps_display_hook`が技術的に適用可能なことを
  touhou-recorderで確認済み（reports/63・64）だが、Sattori側のMOD・
  `SLOW_MOTION_SUPPORTED_GAME_IDS`には未実装（Issue #76のスコープ外）。

## 残っているリスク

- 局所的な瞬間的処理落み（3面スペルカード・6面ボス戦の高負荷演出）は、c7i.2xlargeでも
  最小40fps相当まで落ち込む区間が残る（reports/67）。実プレイに深刻な影響は無いと
  判断し許容しているが、品質要求が上がった場合は`.4xlarge`帯や低速録画の追加検証が
  選択肢になる。
- th12の既知バグ「スコア表示オーバーフロー」対応としてVsyncPatchを常時有効化して
  いるが、VsyncPatchのオン/オフでゲーム内の処理内容が変わりリプレイずれのリスクが
  あるかどうかは、reports/64で検証した1本のリプレイ（デシンクなし）以外の追加検証は
  行っていない。
