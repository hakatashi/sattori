# ページAの録画オプションとタイトル別注意書き（`components/UploadForm.tsx`）

ページA（`/`）でリプレイを解析した後に出す各録画オプションと**th20の注意書き
（Issue #87）**の仕様。フロー全体は`apps/web/README.md`「ページAのフロー」を参照。

## 1. th20の注意書き（Issue #87）

th20のリプレイを解析したときだけ、STEP2のプレビュー直下に注意書きを出す。**メールアドレスを
入力して録画を依頼してしまう前に**知らせるのが目的:

- **デシンク（リプレイずれ）が頻発する**: リプレイファイル・ゲーム本体側の現象で、
  録画側では検知できない（touhou-recorder reports/45）。再録画しても同じ結果。
  あわせて、**プレイ時に有志製パッチ [thprac](https://github.com/touhouworldcup/thprac)
  を導入しておくとリプレイずれを回避できる**ことを案内する。

### 1.1 ワーカーがthpracを適用した後もこの注意書きを残す理由（Issue #105）

録画ワーカーはth20の録画時にthpracをアタッチするようになった（reports/50、
[`docs/decisions/0009`](../../../docs/decisions/0009-thprac-post-attach.md)）。それでも
**「プレイ時にthpracを入れてください」という案内は消してはいけない**。両者が効く場所が
違うためである。

| 汚染が起きた場所 | 直せるのは | Sattoriの対応 |
| --- | --- | --- |
| 再生時の非決定性（よくある方） | 再生側のthprac | ワーカーが自動でアタッチする（reports/50で3/3解消） |
| 記録時のANM再利用バグ | **プレイ時のthpracのみ**（事後の修復は不可能） | この注意書きでユーザーに案内する |

デシンクの主因である ANM 再利用バグは**プレイ中にランダムに発火する**ため、thprac 無しで
プレイした回に発火すると、保存されたリプレイ自体が「再現不能な状態を通過した記録」になる。
**再生側の対処（サーバー側のthpracも、thprac自身の `TH_REPFIX` によるタイマーオフセット
調整も）では直せない** —— 詳細と thprac 自身の UI テキストによる裏付けは
[`docs/decisions/0009`](../../../docs/decisions/0009-thprac-post-attach.md)「補足: 録画側の
thprac では直せないずれがある」にある。

したがってこの注意書きは、①ユーザーに録画依頼前の期待値を持ってもらう（予期しない
リプレイずれへの不満の緩和）ことに加えて、②**今後保存するリプレイを汚染させない
唯一の手段をユーザーに伝える**という、サーバー側では代替できない役割を持つ。

## 2. th06ncの1080p録画オプション（廃止、Issue #241・#317）

th06nc限定で1080pを選べるオプションがあったが、CPUの段（1/2倍速）を足すにあたって廃止した
（[`docs/decisions/0066`](../../../docs/decisions/0066-recording-fallback-plan-as-config.md)）。
UIから消し、`POST /magic-links`も古いフロントエンドのキャッシュが送るtrueを無視する。

## 3. 録画速度は選ばせない。完了の目安だけを出す（Issue #288・#317）

録画速度（倍速録画、[`0058`](../../../docs/decisions/0058-speedup-recording-on-gpu-instances.md)）は、
タイトルごとの録画の段（`packages/shared/src/recordingPlan.ts`）が決める。ユーザーは選ばない
（[`0066`](../../../docs/decisions/0066-recording-fallback-plan-as-config.md)）。かつては4択のラジオボタンと
「おすすめより速い」警告があったが、GPUが枯渇すると選んだ速度が実現しなかった（Issue #317）。

- 送信ボタンの直上に「録画完了までの目安: 約N分」を1行だけ出す。最初の段で録れたときの値
  （`estimateRecordingCompletionSeconds()`。th15のExtraのような難易度ごとの速度も反映する）。待ち行列の
  待ち時間と、混雑で後の段（等倍・低速）へ進んだときの延びは含まないので、「混雑時はさらにかかる」と添える。
- リプレイの尺（`estimatedDurationSeconds`）が分からなければ出さない。
- ジョブページは最終的に割り当てた段の速度だけを出し、フォールバックしたことは伝えない
  （`JobProgress.tsx`）。
